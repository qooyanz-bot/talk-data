````
## なぜ「合同会社」で検索するとおかしくなったのか

例えば、

```
合同会社
```

と検索すると、

SQLは単純に書くと

```sql
SELECT *
FROM companies
WHERE name ILIKE '%合同会社%';
```

になります。

`ILIKE '%文字%'` は先頭に `%` が付いているため、
通常のB-treeインデックスが使えません。

つまり

```
576万社
↓
1件ずつ全部見る
↓
合同会社が入っている？
```

という処理になります。

これを

**全件走査（Full Table Scan）**

と言います。

576万件なら数秒〜数十秒かかります。

Cloudflare Workerは数秒でタイムアウトするため、

```
検索途中で終了
↓
結果がおかしい
```

という状態になります。

---

# pg_trgmとは？

PostgreSQLには

```
pg_trgm
```

という拡張があります。

これは

```
トライグラム検索
```

です。

例えば

```
合同会社
```

を

```
合同
同会
会社
```

のような文字列の集合として扱います。

「大阪市中央区」

なら

```
大阪
阪市
市中
中央
央区
```

のようになります。

---

これに対してGINインデックスを作ると

```
576万件全部見る

↓

合同を持っている会社だけ見る
```

になります。

つまり

```
576万件

↓

数千件
```

くらいまで一気に絞れます。

速度は

```
数秒

↓

数十ms
```

になります。

---

## 作成したインデックス

例えば

```sql
CREATE INDEX company_name_trgm
ON companies
USING gin (name gin_trgm_ops);
```

住所も

```sql
address gin_trgm_ops
```

を作っています。

なので

```
大阪
```

と入力すると

住所インデックスだけを見るので

```
大阪市
大阪府
```

を高速に取得できます。

---

# なぜ「大阪」は住所優先なのか

普通に

```
大阪
```

と検索すると

候補は

```
会社名

住所

法人番号
```

全部になります。

例えば

```
株式会社大阪商事

東京都・・・

```

も出ます。

しかし

ほとんどの人は

```
大阪にある会社
```

を探しています。

そこで

検索ロジックを

```
住所

↓

会社名

↓

法人番号
```

という優先順位にしています。

つまり

```
大阪
```

なら

まず

```
住所 LIKE '%大阪%'
```

を見ます。

だから期待通りの結果になります。

---

# 重複除去

例えば

```
株式会社大阪商事

住所
大阪府大阪市
```

だと

```
名前でもヒット

住所でもヒット
```

します。

そのままUNION ALLすると

```
株式会社大阪商事

株式会社大阪商事
```

になります。

なので

```
UNION
```

または

```
DISTINCT
```

で

1件だけ表示しています。

---

# なぜ50件しか返さないの？

例えば

```
合同会社
```

は何十万件あります。

全部返すと

```
576万件検索

↓

100万件返す

↓

ブラウザ死亡
```

になります。

だから

```
LIMIT 50
```

にしています。

画面では

```
50+
```

と表示します。

つまり

```
もっとあります
```

という意味です。

---

# なぜ総件数を表示しない？

例えば

```
合同会社
```

の件数だけ欲しいとしても

```
COUNT(*)
```

は非常に重い処理です。

```
SELECT COUNT(*)
FROM companies
WHERE name ILIKE '%合同会社%'
```

これも

結局かなりのデータを読む必要があります。

毎回これをやると

CPUを大量消費します。

なので

```
50+
```

だけ表示しています。

これは

Googleも

GitHubも

GitLabも

同じ考え方です。

---

# EnterpriseOSならさらに改善できる

現在の検索でも十分高速ですが、EnterpriseOSの規模（将来的に1,000万社以上）を考えると、さらに一段進められます。

優先順位は次のようになります。

| 優先度 | 改善内容 | 効果 |
|--------|---------|------|
| ★★★★★ | 検索語を自動分類（法人番号・会社名・住所・都道府県・業種） | 不要な検索を減らし精度向上 |
| ★★★★★ | 検索専用インデックス（`tsvector`＋`pg_trgm`の併用） | 日本語検索を高速・高精度化 |
| ★★★★☆ | 人気検索をCloudflare KVでキャッシュ | 「東京」「大阪」「合同会社」などはDBアクセス不要 |
| ★★★★☆ | 検索順位スコアリング | 完全一致→前方一致→部分一致→住所一致の順で表示 |
| ★★★☆☆ | Elasticsearch / OpenSearchへの分離 | 5,000万〜1億社規模になっても対応可能 |

私ならEnterpriseOSでは、**PostgreSQLを正としつつ、検索だけを専用サービス化**します。

```
PostgreSQL
      │
      ├── Hyperdrive
      │
      ▼
検索API
      │
      ├── 法人番号
      ├── 会社名
      ├── 住所
      ├── 業種
      ├── 代表者
      ├── AIタグ
      ▼
Cloudflare KV（人気検索キャッシュ）
      ▼
UI
```

この構成なら、将来的に5,000万〜1億社へ拡張しても検索性能を維持しやすく、AIによる自然言語検索（例:「名古屋でAI開発をしている新設法人」）への発展もしやすくなります。
````
