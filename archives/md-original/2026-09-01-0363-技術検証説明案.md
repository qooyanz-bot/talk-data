````
## 対外回答案

### 1. 13万パラメータ以下のモデル構成

本システムは、0.13Mパラメータの単一モデルで自然言語・世界知識・汎用推論をすべて再現するものではありません。

小型モデルは、以下のような限定された役割を持ちます。

| 構成要素 | 役割 | 現在の位置づけ |
|---|---|---|
| State Compiler | 入力を状態・目的・制約へ変換 | 19,712パラメータは設計候補値 |
| Interface Compiler | ツールやデータ形式を選択 | 29,184パラメータは設計候補値 |
| Transformation Executor | 状態変換・計算・分類 | 仕様凍結前 |
| Knowledge Store | 事実・出典・時刻・関係を保存 | ニューラル重みではなく外部データ |
| Verification Layer | 出力の型・根拠・矛盾・安全性を検査 | 決定論的処理を中心に設計 |
| Language Adapter | 必要に応じて自然言語へ変換 | 使用モデルと版を固定予定 |

「13万パラメータ」は、1個の汎用モデルの性能を意味するのではなく、小型の学習モジュールを構成する際の規模上限として扱います。総パラメータ数、外部メモリ容量、実行コード量、CPU計算量は別々に報告します。

処理は概念的には次の流れです。

```text
入力
 → 状態抽出
 → 目的・制約の確定
 → 型付き実行計画
 → 検索・計算・コード・記憶の実行
 → 根拠と安全性の検証
 → 応答生成
```

数学的には、

\[
x \rightarrow s \rightarrow g \rightarrow p
\rightarrow y \rightarrow v \rightarrow r
\]

と表せます。

ここで、\(x\) は入力、\(s\) は状態、\(g\) は目的、\(p\) は実行計画、\(y\) は実行結果、\(v\) は検証結果、\(r\) は最終応答です。

一般的なLLMが大量の重みの中に知識と処理規則を同時に保持するのに対し、本方式では、

- 小型モデル：状態判断・ルーティング
- 外部メモリ：知識
- 実行器：計算や検索
- 検証器：誤り・矛盾・安全性の判定

へ分解します。

したがって、これは「13万パラメータだけでGPT級の世界知識を記憶する」という主張ではありません。限定されたタスクに対して、モデルの重みに依存する計算を減らす設計仮説です。

現時点で言える「新しい原理」は、物理法則ではなく、

> 知性の一部をニューラル重みから、明示的な状態表現・外部記憶・実行プログラム・検証層へ移し、必要な処理だけを動的に組み合わせる

というアーキテクチャ仮説です。

### 2. GPT‑5.6相当97%という数値について

「GPT‑5.6相当97%」は、現時点でMMLU、MATH、HumanEvalなどを用いて算出した客観的なベンチマーク結果ではありません。開発過程の予測値または目標値であり、対外的には確定性能として扱うべきではありません。

現在存在する実測に近いデータは、以下のような限定的な合成実験です。

- Memory ISA v0.2  
  604件の二言語発話、302件の学習指示、138件の評価発話、69個の未見タプル。
  - Factorized exact accuracy：97.10%
  - Slot accuracy：99.40%
  - CPU中央値遅延：1.874ms
  - Typed Rule baseline：100%
  - 二言語タプル成功率：65/69、94.20%

ただし、この結果は合成データ上の開発結果であり、独立再現前です。自由会話、GPT同等性、長期記憶、実世界ロボット制御を実証したものではありません。

また、Vision Stage‑0では、

- 5 seed
- 3種類の合成世界
- 2,000フレーム
- 64×64入力
- テスト32/32
- 監査45/45
- ピクセル量比0.09754375

を確認しています。しかし、これは画素量削減の実験であり、リアルタイム動画認識やCPU消費電力の実証ではありません。

したがって、今後「97%」を公表するには、最低限以下が必要です。

- MMLU、MATH、HumanEvalなどの固定版
- 5 seed以上
- 未公開ホールドアウト
- モデルID、revision、license、重みHash
- プロンプト・データセットHash
- 推論時間、メモリ、電力、コスト
- 独立した再実行者によるReplay
- 失敗例と棄権率

### 3. 動画・音声処理と遅延

高解像度映像をCPUだけで数十ms以内に処理できるとは、現時点では断定できません。

RGB映像だけでも、データ量は次の通りです。

| 入力 | 1フレーム | 30fps/60fps |
|---|---:|---:|
| 1920×1080 RGB | 約6.2MB | 約187MB/s・373MB/s |
| 3840×2160 RGB | 約24.9MB | 約1.49GB/s（60fps） |

これは画素転送だけの値で、動画デコード、メモリコピー、推論、追跡、I/Oは含みません。

現実的な設計は、次のような段階処理です。

1. ハードウェアデコード
2. 低解像度フレームで常時追跡
3. 高解像度解析はイベント時・ROI限定
4. 重い検出器は毎フレームではなく一定間隔
5. 軽量トラッカーをフレーム間に使用
6. p50ではなくp95・p99遅延を測定

したがって、CPUまたはT4で可能性があるのは「解像度・対象・処理頻度を制限したリアルタイム認識」です。高解像度の完全な意味理解を常時数十msで処理するという意味ではありません。

遅延補正についても、予測値を真実として扱いません。

\[
\hat{x}_{t+\Delta}=F(\hat{x}_t,u_t,\Delta)
\]

で未来位置を推定し、同時に予測誤差 \(P\) を更新します。誤差が閾値を超えた場合は、

- ロボットを減速
- 動作を停止
- センサーを再取得
- 不確実な対象を障害物として扱う
- 操作を人間確認へ戻す

という動作に切り替えます。

予測器はアクチュエータへ直接命令できません。独立した安全層が、速度制限、衝突判定、ウォッチドッグ、デッドマン、物理非常停止を管理します。

### 4. 16TB HDDと知識データベース

「16TBのHDDを20〜100msで検索できる」という表現は、冷たいランダムアクセスを含む保証ではありません。

HDDの総時間は、

\[
T =
T_{\text{queue}}
+T_{\text{seek}}
+T_{\text{rotation}}
+T_{\text{transfer}}
+T_{\text{decode}}
+T_{\text{CPU}}
+T_{\text{network}}
\]

です。

代表的な7200rpm HDDでも、平均シーク約8.5〜9.5ms、平均回転待ち約4.16ms程度が仕様例として示されています。[Seagate仕様](https://www.seagate.com/files/www-content/product-content/_cross-product/en-us/docs/7200rpm-drive-spec-mb578-7-1201us.pdf)

よって、20〜100msという値は、

- 検索キーの索引がRAM上にある
- HDDへのアクセス回数が少ない
- 連続ブロックを読む
- ホットデータがキャッシュされている
- SSDにメタデータを置く

という条件での目標値です。16TBという容量自体が高速検索を保証するわけではありません。

想定する経路は、

```text
問い合わせ
 → RAM上のキー索引
 → セグメント番号・オフセット
 → HDDから限定ブロック読込
 → 出典・Hash・時刻を検証
 → 応答
```

です。コールドなランダムアクセスのp95・p99は、実機測定なしには保証しません。

Wikipediaの20GBを100MBにするという説明も、可逆圧縮ではありません。

正確には、

- HTMLや重複の除去
- エンティティ・関係・属性への分解
- 辞書符号化
- 重要主張だけの抽出
- 出典と時刻の保存

を行った「タスク特化型の意味表現」です。

元の20GBを100MBだけで完全復元できるなら可逆ですが、そうでなければ情報を削った非可逆表現です。したがって、元データまたは証拠本文は別保存し、100MB側には出典、該当箇所、時刻、信頼度、矛盾情報を保持します。

### 5. 共同記憶の安全性

共同記憶は、全端末の情報を即時に全体へ反映する方式にはしません。

```text
投稿
 → 隔離
 → 署名・権限・出典検査
 → 矛盾・毒性・異常検査
 → 段階公開
 → 監視
 → 必要なら即時Rollback
```

必要な対策は以下です。

- 端末・ユーザー・テナント単位の権限分離
- データの署名、Hash、出典、作成時刻
- 信頼度・有効期限・適用範囲
- 未検証データの隔離領域
- 重要情報への二者承認または独立検証
- 変更履歴とスナップショット
- 汚染時のロールバック
- 暗号化、アクセスログ、削除権
- 未知の情報を直接モデル重みへ学習しない設計

合意数が多いだけでは、真実性は保証できません。出典、再検証、適用範囲、反証情報を保持する必要があります。

### 6. 3か月の現実的なロードマップ

「同等性能」は、GPT全般との同等ではなく、固定した限定タスク群でのベースライン同等と定義します。
````

````
```text
````

````
## 絶対原則

1. ラベル一致率、トークン一致率、スロット抽出率、Factorized exact accuracyだけから、推論能力・知能・汎用性を主張してはいけません。

3. AddressまたはConcept Addressはルーティング用の識別子であり、それ自体を意味理解・推論の証拠として扱ってはいけません。
4. 未知、低信頼、同率、矛盾、根拠不足の状態では、推測で埋めず、`unknown`、`conflict`、`abstain`、または追加質問を返してください。
5. 生ラベル、埋め込み近傍、未検証の推測を意味記憶へ保存してはいけません。
6. 記憶する場合は、`Concept`、`Relation`、`Value`、`Scope`、`Time`、`Evidence`、`Provenance`、`VerificationStatus`を持つ型付きレコードとして保存してください。
7. テストデータ、ストレスデータ、失敗事例を後から学習データへ混入させてはいけません。

## 必須の反ショートカット評価

学習後は、通常のテストだけでなく、以下を必ず実施してください。

1. ラベル・トークンの完全な置換  
   ラベル名を無作為に変更しても、構造的な回答が維持されるか確認する。

2. 表層表現の変更  
   言い換え、語順変更、表記揺れ、別の自然言語表現で評価する。

3. 関係の反転  
   「AがBにある」と「BがAにある」を区別できるか確認する。

4. 否定・命令反転  
   実行命令と禁止命令、肯定と否定を区別する。

5. 無関係な妨害情報  
   正解に不要な物体、発話、記憶、イベントを追加する。

6. 欠損・矛盾情報  
   情報が不足または競合した場合に、誤った確定をせず保留できるか確認する。

7. スコープ分割・統合  
   同じ名前の対象が異なるスコープに属する場合を区別する。

8. 同一ラベル・異なる構造  
   同じラベルでも内部構造が異なる例を用意する。

9. 異なるラベル・同一構造

12. ラベル事前分布の反転
````

````
問題は、ラベル暗記で高得点を取っただけなのに「推論できる」「知能が高い」と判断してしまうことです。

| 状態 | 評価 |
|---|---|
| 固定されたラベルを正しく返す | 分類・ルーティング機能として有用 |
| ラベルをAPI形式へ変換する | 実用上問題なし |
| 未知の組み合わせや関係変更にも対応する | 推論性能の証拠になり得る |
| ラベル名を変えたら性能が崩れる | ラベル暗記の可能性が高い |

例えば、学習データが、

```text

「赤い箱は青い箱の右」→ LABEL_B
```

- 物体名を変える
- 言い方を変える
- 左右を反転する
- ラベル名を入れ替える
- 無関係な情報を追加する
- 情報が不足したら `unknown` と返す
````

```
## Safety and promotion gate

No checkpoint may be promoted to production integration when:

- its provenance is missing;
- its model ID is duplicated;
- its checkpoint is unavailable;
- its manifest is invalid;
- its evaluation is contaminated;
- deterministic replay fails;
- it is only a recorded output;
- it is marked `trained=true` without executable evidence;
- it relies on unsafe side effects;
- it has not passed the required audit status.

No actuator, motor command, production write, or external side effect is permitted during this audit or retraining evaluation.
```
