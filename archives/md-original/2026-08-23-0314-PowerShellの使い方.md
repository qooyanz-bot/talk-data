Playwrightでは、1つの`browser context`の中に複数の`page`を作ります。`page`が実質「タブ」です。

```python
from playwright.async_api import async_playwright
import asyncio

async def run_job(page, url):
    await page.goto(url)
    print(await page.title())

async def main():
    async with async_playwright() as p:
        browser = await p.chromium.launch(headless=False)

        context = await browser.new_context()

        page1 = await context.new_page()
        page2 = await context.new_page()
        page3 = await context.new_page()

        await asyncio.gather(
            run_job(page1, "https://example.com/a"),
            run_job(page2, "https://example.com/b"),
            run_job(page3, "https://example.com/c"),
        )

        await browser.close()

asyncio.run(main())
```

ここで重要なのが`asyncio.gather()`です。

```text
順番実行

Tab1
 ↓ 完了
Tab2
 ↓ 完了
Tab3

ではなく

Tab1 ───────→
Tab2 ───────→
Tab3 ───────→

を同時進行
```

にできます。

はい。ここで出てきた **Python + Playwright + asyncio** の関係を整理すると、かなり分かりやすくなります。

Pythonは「全体を制御するプログラミング言語」、Playwrightは「Chromeなどのブラウザを自動操作するライブラリ」、asyncioは「複数の作業を同時進行させる仕組み」です。

たとえば今のSemrush作業なら、Pythonが司令塔になって、Playwrightに「タブを3つ開け」「各タブで別のキーワードを検索しろ」「CSVを保存しろ」と命令します。さらにasyncioを使うと、それらを順番ではなく並行して進められます。

イメージはこうです。

```text
Python
  │
  ├─ Playwright
  │    ├─ Chrome Tab 1 → Semrush JP
  │    ├─ Chrome Tab 2 → Semrush US
  │    └─ Chrome Tab 3 → 別キーワード
  │
  └─ asyncio
       └─ 3タブを同時進行させる
```

普通のPythonだと、処理は基本的に順番です。

```python
page1.goto("URL-A")
page2.goto("URL-B")
page3.goto("URL-C")
```

これは概念的には、

```text
Aを開く
↓
Aの読み込み完了
↓
Bを開く
↓
Bの読み込み完了
↓
Cを開く
```

となります。

一方、asyncioを使うと、

```python
await asyncio.gather(
    task_a(),
    task_b(),
    task_c(),
)
```

として、

```text
A ───────────────→
B ───────────────→
C ───────────────→
```

のように、待ち時間を重ねられます。

ここで重要なのは、**CPUで3つの処理を本当に同時に計算しているわけではない**という点です。

ブラウザ自動化では多くの時間が、

```text
ページ読み込み待ち
サーバー応答待ち
ダウンロード待ち
```

です。

この「待っている時間」に別のタブを動かすので、asyncioとの相性が非常に良いです。

### `browser`、`context`、`page`の違い

Playwrightではこの3段階を理解すると一気に分かります。

```text
Browser
└─ Context
   ├─ Page
   ├─ Page
   └─ Page
```

`Browser`はChromeそのものです。

```python
browser = await p.chromium.launch()
```

`Context`は「独立したブラウザ環境」です。Cookie、LocalStorage、ログイン状態などを保持します。

```python
context = await browser.new_context()
```

`Page`がタブです。

```python
page1 = await context.new_page()
page2 = await context.new_page()
```

つまり、

```python
context = await browser.new_context()

page1 = await context.new_page()
page2 = await context.new_page()
```

なら、

```text
Chrome
└─ 同じログイン環境
   ├─ Tab 1
   └─ Tab 2
```

になります。

Semrushにはこの形が向いています。同じログインCookieを3タブで共有できるからです。

逆に、

```python
context1 = await browser.new_context()
context2 = await browser.new_context()
```

とすると、

```text
Chrome
├─ Context 1
│   └─ Cookie A
│
└─ Context 2
    └─ Cookie B
```

となり、完全に別ブラウザのように扱えます。

### 800kqで考えるとかなり重要です

現在はSemrush取得程度ですが、将来の800kq処理ではPythonを単なる「スクリプト言語」ではなく、**データ収集工場の制御システム**として使えます。

たとえば、

```text
                  Python Controller
                         │
               ┌─────────┴─────────┐
               │                   │
         Query Queue          Result Queue
               │                   │
       ┌───────┼───────┐           │
       ↓       ↓       ↓           │
    Worker1 Worker2 Worker3         │
       │       │       │           │
       ↓       ↓       ↓           │
     Browser Browser Browser        │
       │       │       │           │
       ↓       ↓       ↓           │
      SERP    SERP    SERP          │
       └───────┬───────┘           │
               ↓                   │
          URL Deduplication
               ↓
           Crawl Queue
               ↓
       Graph/Ontology処理
```

という構成に発展できます。

ここでは、単純に「100個タブを開く」より、**Queue + Worker方式**にした方が圧倒的に安定します。

たとえば検索対象が100件あったとしても、

```text
100個タブを一斉に開く
```

のではなく、

```text
仕事100件
   ↓
Queue
   ↓
Worker 1
Worker 2
Worker 3
Worker 4
```

として4ワーカーだけ動かします。

1件終わったWorkerが次の仕事をQueueから取ります。

```text
Worker1 → query A → 完了 → query E
Worker2 → query B → 完了 → query F
Worker3 → query C → 完了 → query G
Worker4 → query D → 完了 → query H
```

この設計が実務では強いです。

### `Semaphore`が何をしているのか

前に出した、

```python
semaphore = asyncio.Semaphore(3)
```

は「同時に最大3仕事まで」という交通整理です。

例として100件仕事があっても、

```text
同時実行 3
待機     97
```

になります。

1件終了すると、

```text
同時実行 2
↓
待機中から1件投入
↓
同時実行 3
```

に戻ります。

コードではこうなります。

```python
sem = asyncio.Semaphore(3)

async def worker(query):
    async with sem:
        await do_search(query)
```

さらに、

```python
await asyncio.gather(
    *(worker(q) for q in queries)
)
```

とすると、100件登録しても最大3件しか同時実行されません。

これはSemrushだけでなく、今後のSERP、Web取得、LLM APIにもそのまま使えます。

### 「タブ並列」と「プロセス並列」は別物です

800kq規模になるとここが重要になります。

Playwright + asyncioは主に、

```text
ネットワーク待ち
Webアクセス
APIアクセス
```

に強いです。

一方、

```text
HTML解析
Embedding生成
大量テキスト処理
Ontology生成
圧縮
```

のようなCPU負荷が高い処理は、asyncioだけでは速くなりません。

その場合は、

```text
asyncio
+
multiprocessing
```

にします。

イメージは、

```text
Process 1
 ├─ async Worker A
 ├─ async Worker B
 └─ async Worker C

Process 2
 ├─ async Worker D
 ├─ async Worker E
 └─ async Worker F
```

です。

これが以前話した**「multiprocessing + asyncioのハイブリッド」**です。

ただし、今のSemrushパイロットではそこまで必要ありません。現時点なら、

```text
Python
+
Playwright async
+
asyncio
+
Semaphore(2〜3)
```

で十分です。

そしてこの構成を理解しておくと、後でSERP取得、クロール、Graph化の規模を拡大するときも同じ考え方で設計できます。

一番大事なのは、**Pythonに100件を直接処理させるのではなく、「Queueに仕事を積み、少数のWorkerが順番に処理する」設計にすること**です。これが800kqの収集基盤を安定させる基本になります。memcite
