## 結論

Cloudflareの**EmDash CMS**を指している前提なら、小規模な企業サイトの年間インフラ費は、現実的には**約1.2万〜1.6万円／年**です。

為替変動、消費税、カード会社の為替手数料まで考慮した予算取りなら、**年2万円**を確保しておけば概ね足ります。これは**制作費・更新作業・会社メール費用を除いた金額**です。

| 構成 | 年間コストの目安 |
|---|---:|
| プラグインなし・無料枠運用 | 約2,000〜5,500円 |
| プラグインあり・通常の企業サイト | 約12,000〜16,000円 |
| 為替・税・軽微な従量課金込みの予算枠 | 約20,000円 |

### 内訳

**EmDash本体：0円**

EmDashはMITライセンスのオープンソースです。ただし、プラグインを安全なサンドボックスで動かすDynamic WorkersはCloudflareの有料プランが必要です。プラグインを無効化すれば無料プランでも動かせます。 citeturn681627view0

**Cloudflare Workers Paid：月5ドル、年60ドル**

2026年7月10日の日銀中心相場である1ドル162.09円を使うと、年間約**9,725円**です。Workers Paidはサイト単位ではなくCloudflareアカウント単位の最低料金です。 citeturn681627view3turn545658view0

**独自ドメイン：年間約1,800〜5,500円**

目安は以下です。

- `.com`：約1,800〜2,200円
- `.jp`：約3,000〜4,000円
- `.co.jp`：約3,500〜5,500円

したがって合計は、`.com`なら約11,500〜12,000円、`.jp`なら約12,700〜13,700円、`.co.jp`なら約13,200〜15,200円です。 citeturn842329search11

**アクセス・画像・データベース：通常は追加0円**

Workers Paidには月1,000万リクエスト、D1には月250億行の読み取り・5GBのストレージ、R2には月10GBの無料ストレージ枠などがあります。一般的な中小企業サイトであれば、これらの枠を超える可能性は低いため、通常は追加料金なしと見積もれます。これは小規模サイトを前提にした推定です。 citeturn681627view3turn681627view4turn681627view5

## 含まれない費用

上の約1.2万〜1.6万円に、次の費用は含まれていません。

- デザイン、コーディング、原稿作成
- 問い合わせフォームのメール送信サービス
- `info@会社名.co.jp`などの会社メール
- アクセス解析、監視、バックアップ
- 更新作業や障害対応を外注する保守費
- 写真撮影、SEO、法務チェック

したがって、自分で制作・更新するなら**初年度も実費約2万円以内＋自分の作業時間**です。制作会社に任せる場合は、年間インフラ費よりも制作・保守の人件費の方が圧倒的に大きくなります。

## 採用判断としての注意点

EmDashは現在も公式に**ベータプレビュー**扱いです。企業サイトで最も重いコストはサーバー代ではなく、仕様変更への追従、障害調査、デプロイ、担当者が辞めた後の引き継ぎです。 citeturn481851search3

率直に言えば、5〜10ページ程度で更新頻度が低い企業サイトなら、EmDashを入れること自体が過剰です。Astroなどで静的サイトを作り、Cloudflareに置けば、ドメイン代だけで運用でき、故障箇所も減ります。一方、複数担当者が管理画面から事例・ニュース・採用情報を頻繁に更新するなら、EmDashを使う意味があります。

なお、**emdash.shのAI開発環境**を指している場合は別計算です。そちらはEmdash本体がApache-2.0のオープンソースで無料であり、主な年間費用は利用するAIコーディングエージェント、ホスティング、ドメインです。 citeturn203889search1

## 結論

**限定採用なら賛成、DealVaneの中核基盤としての全面採用には反対**です。

EmDashはDealVaneの「AIが企業サイトを生成する部分」ではなく、**生成したサイトを顧客が更新・運用するCMS層**として使うのが適切です。

EmDash自身も「ページビルダーではなく、構造化コンテンツを管理し、見た目はAstroコンポーネントで構築するもの」と明示しています。つまり、DealVaneが必要とする「業種や企業情報に応じてページ構成・デザイン・コピーを自動生成する機能」は、結局DealVane側で作る必要があります。さらに、2026年7月11日時点ではEmDashはベータプレビューで、最新版は前日の7月10日に公開された0.29.0です。1.0は最初の安定版として計画されていますが、公開時期は未定です。citeturn539984view3turn466591view0turn341363view0

## EmDashがDealVaneに合う部分

### 1. AIが構造化コンテンツを生成しやすい

EmDashはPortable Textベースの構造化コンテンツ、コレクション、フィールド、メニュー、リダイレクト、設定、再利用セクションなどを扱えます。初期構築時にはJSONのseedデータからサイトを立ち上げられるため、

- 企業概要
- サービス
- 強み
- 導入事例
- よくある質問
- 採用情報
- ニュース
- SEO情報

をDealVaneがJSONとして生成し、EmDashへ流し込む構成は作りやすいです。MCPやREST APIも用意されており、生成後のAI編集にも接続できます。citeturn466591view1turn539984view1turn539984view2

### 2. 顧客自身による更新機能を早く提供できる

DealVaneが独自にCMSを作り始めると、実際には次の機能が必要になります。

- ログインと権限管理
- 下書きと公開
- 改訂履歴
- 予約公開
- メディア管理
- コンテンツ型定義
- 入力バリデーション
- プレビュー
- API
- 管理画面

これらはAI生成とは別の、地味で重い開発です。EmDashには相当部分が既にあります。DealVaneの初期顧客が「会社概要を一度作ったら終わり」ではなく、ニュース、実績、採用情報を継続更新するなら、EmDashの価値はあります。citeturn466591view1

### 3. 顧客への引き渡し・脱ロックインに向いている

EmDashはMITライセンスなので、商用利用、改変、再配布の大きなライセンス障壁はありません。DealVaneから「Astro＋EmDashの自己所有可能なサイト」としてエクスポートできれば、顧客にとっても安心材料になります。citeturn288658view0

これはDealVaneの差別化として強いです。

> DealVaneを解約しても、作った会社サイトは失われない。

このメッセージは、中小企業向けサービスではかなり有効です。

## EmDashがDealVaneに合わない部分

### 1. EmDashはマルチテナントSaaS基盤ではない

DealVaneでは、企業A、企業B、企業Cのコンテンツ、ドメイン、ユーザー、ストレージ、権限を分離する必要があります。

しかし、現行のEmDashは基本的に個別サイトへのデプロイを中心とした設計です。公開されている議論でも、ネイティブなマルチテナンシーは完成済みの中核機能ではなく、「顧客ごとにWorkerを持たせる」といった外部アーキテクチャで対処する方向が検討されています。citeturn367743view2turn367743view3

Cloudflare Workers for Platformsを使えば、顧客ごとにWorkerを分離し、それぞれ異なるD1、R2、KVなどを割り当てられます。そのため技術的には成立します。citeturn573964search0turn469532search10turn573964search1

ただし、その場合にDealVane側で必要になるのは次です。

- テナント作成
- Workerのプロビジョニング
- D1/R2の作成と紐付け
- カスタムドメイン設定
- SSL証明書
- EmDashバージョン管理
- スキーマ移行
- 全テナント一括更新
- ロールバック
- バックアップと復元
- 障害監視
- 顧客削除時のデータ処理

つまり、**EmDashを採用しても、SaaSのコントロールプレーンはDealVaneが自前で作る必要があります。**

ここが最大の盲点です。EmDashを入れればCMS開発は減りますが、代わりに**大量のEmDashインスタンスを管理する仕事**が発生します。

### 2. スキーマのテナント間ドリフトが起きる

EmDashのseedデータは基本的に初回セットアップ用です。既存データベースに対してseedファイルを変更しても、そのまま反映されるものではありません。稼働後のスキーマやコンテンツ変更は管理画面やAPIで行います。citeturn539984view0

顧客が管理画面から独自フィールドを追加したり、コレクション構造を変更したりすると、

- 顧客Aは旧スキーマ
- 顧客Bは独自スキーマ
- 顧客Cは最新版スキーマ

という状態になります。

10社なら手作業で直せます。500社になると破綻します。

そのため、DealVaneで使う場合は、顧客にEmDashの完全な管理者権限を与えるべきではありません。顧客にはコンテンツ編集権限だけを与え、**スキーマはDealVane側で固定管理**する必要があります。

### 3. 再利用セクションがグローバル同期されない

EmDashの再利用セクションは、ページに挿入した時点でコンテンツがコピーされます。元のセクションを変更しても、既存ページへ自動反映される仕組みではありません。citeturn642295view1

DealVaneで「全企業サイトのCTAデザインを新しいものに変更する」「法令対応でフッターを一括変更する」といった更新をする場合、EmDashのコンテンツセクションに依存すると管理が難しくなります。

共通デザインはEmDash内のコピーされたブロックではなく、**バージョン管理されたAstroコンポーネント**として実装すべきです。

### 4. まだプロダクション中核に置くには不安が残る

EmDashの1.0ロードマップには、スキーマ安全性、監査・来歴、編集上の安全性、API/MCP、プラグイン、Cloudflare本番運用、セキュリティ、パフォーマンス、移行など、DealVaneに直結する項目が残っています。citeturn341363view0

これは「EmDashが悪い」という意味ではありません。むしろ活発に開発されています。

問題は、DealVaneがEmDashを中核依存にすると、DealVaneのロードマップがEmDashのロードマップに引っ張られることです。

## 推奨アーキテクチャ

EmDashのデータ構造をDealVaneの正本にしてはいけません。

DealVane独自の中間フォーマットを持たせます。

```text
企業情報・既存資料・ヒアリング
              │
              ▼
     DealVane AI生成パイプライン
     ・事実抽出
     ・業種判定
     ・コピー生成
     ・SEO生成
     ・表現チェック
              │
              ▼
        DealVane SiteSpec v1
        ・brand
        ・company
        ・pages
        ・sections
        ・assets
        ・seo
        ・legal
        ・locales
              │
       ┌──────┴────────┐
       ▼               ▼
DealVane標準レンダラー   EmDashアダプター
Astro/Cloudflare        seed/API/MCP
       │               │
       ▼               ▼
通常プランのサイト      高度編集・引き渡し用サイト
```

SiteSpecは、例えば次のような制約付きJSONにします。

```json
{
  "schemaVersion": "1.0",
  "brand": {
    "companyName": "株式会社サンプル",
    "tone": "professional",
    "primaryColor": "#123456"
  },
  "pages": [
    {
      "slug": "/",
      "template": "corporate-standard-v2",
      "sections": [
        {
          "type": "hero",
          "variant": "split-image",
          "headline": "地域の物流を、もっと滑らかに。",
          "cta": {
            "label": "お問い合わせ",
            "href": "/contact"
          }
        },
        {
          "type": "service-grid",
          "variant": "three-columns",
          "serviceIds": ["service-1", "service-2", "service-3"]
        }
      ]
    }
  ]
}
```

重要なのは、AIに自由なAstroコードを書かせないことです。

AIに許すのは、

- 定義済みセクションの選択
- バリアントの選択
- テキストと画像の入力
- セクション順序の決定

までです。

実際のHTML、アクセシビリティ、レスポンシブ対応、構造化データ、CSSは、検証済みのコンポーネントで生成します。

これにより、AIの出力が多少不安定でも、レイアウト崩壊や任意コード実行を防げます。

## EmDashを採用するなら、この境界を守るべきです

### 初回生成

`SiteSpec → EmDash seed.json`へ変換し、固定スキーマと初期コンテンツを作ります。

### 2回目以降の再生成

seedを再適用するのではなく、現在のコンテンツとの差分を計算し、EmDash APIで更新します。

各レコードにはDealVane側の永続IDを持たせます。

```text
dealvaneEntityId: "page_home_01"
dealvaneGenerationId: "gen_20260711_003"
dealvaneTemplateVersion: "corporate-standard-v2.4"
```

これがないと、AIが再生成するたびに重複レコードが増えたり、顧客の手動修正を上書きしたりします。

### AIからの更新

EmDashのMCPは便利ですが、モデルへ直接MCP認証情報を渡すべきではありません。

EmDashの`content:write`スコープには作成・更新だけでなく、削除や公開操作も含まれます。したがって、

```text
AI
 ↓
DealVaneバックエンド
 ↓ 検証・権限判定・監査ログ・下書き強制
EmDash API/MCP
```

というプロキシ構成にします。通常のAI生成は必ず下書きにし、最終公開は人間または別権限のサービスが行うべきです。citeturn539984view2turn341363view0

企業サイトでは、存在しない実績、誤った所在地、許認可、料金、顧客名、法律上の表記をAIが公開すると、単なる品質問題では済みません。

## 現実的な採用プラン

### パイロット段階

小規模な検証では、顧客ごとにEmDashを1インスタンス用意して構いません。ただし、以下を固定します。

- EmDashのバージョンを完全固定する
- 全顧客で同一スキーマを使う
- プラグインは無効、または自社製のみ許可する
- 顧客にはスキーマ変更権限を渡さない
- AIは下書きしか作れない
- デザインは共通のAstroコンポーネントで管理する

非対話型のCLIプロビジョニングも改善されているため、自動セットアップの土台はあります。citeturn861992view0

### スケール段階

顧客数が増えたらWorkers for Platformsを使い、同一コードのWorkerを顧客ごとにデプロイし、D1やストレージだけを分離する構成が候補です。

ただし、CloudflareのUser Workerでは段階的デプロイがサポートされていないため、DealVane側で、

- 内部テナント
- テスト顧客
- 一部の本番顧客
- 全顧客

というデプロイ群を管理する必要があります。citeturn469532search5

全顧客へ一斉更新して全サイトを壊す構成は避けるべきです。

Workers for Platformsは現在、月25ドルの基本料金からで、一定数のスクリプトと実行量が含まれます。したがって、純粋なCloudflare利用料より、バージョン移行、障害調査、監視、バックアップといった運用コストの方が問題になります。citeturn469532search0

## 採用判断の合格条件

全面採用に進む前に、最低でも以下が自動化されている必要があります。

1. 新規企業を無人でプロビジョニングできる  
2. 全テナントへ同じアップデートを適用できる  
3. 失敗したテナントだけロールバックできる  
4. D1と画像データをテナント単位で復元できる  
5. 顧客の手動編集を保持したままAI再生成できる  
6. 企業Aのデータが企業Bへ混入しないことを自動テストできる  
7. EmDashを外してもSiteSpecからサイトを再構築できる  

特に7番が重要です。

EmDashに障害や破壊的変更があっても、DealVaneの顧客データと生成ロジックがEmDashから独立していれば、別のCMSや独自ランタイムへ移行できます。

## 最終提案

DealVaneのMVPでは次の位置づけが最も合理的です。

**標準プラン**

- DealVane独自SiteSpec
- 固定されたAstroコンポーネント
- Cloudflare上の軽量ランタイム
- 簡易な文章・画像編集
- 全サイトを中央管理

**上位プランまたはエクスポート機能**

- EmDash管理画面
- ニュース、事例、採用情報などの高度なCMS
- 顧客専用インスタンス
- 自己ホスティング可能なソースコード引き渡し

率直に言うと、現時点でEmDashをDealVaneの全面的な基盤にすると、**顧客が本当に欲しいAIサイト生成より、CMSインスタンスの管理に開発時間を奪われます**。それは技術的には面白くても、事業上は寄り道です。

DealVaneの競争力になるのはCMSそのものではありません。

- 少ない入力で正確な企業情報を抽出する
- 業種に合った構成を選ぶ
- 嘘のない文章を生成する
- 信頼感のあるデザインへ落とす
