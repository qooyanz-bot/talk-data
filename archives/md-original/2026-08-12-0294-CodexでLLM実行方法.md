今のCodexで他社LLMを動かせる仕組みは、端的にいうと **「Codexをエージェント実行基盤として使い、LLM部分だけをModel Providerとして差し替える」構造**です。

OpenAI公式ドキュメントでは、Codexの **Model Provider** が「どのモデルへ、どのBase URLで、どのAPI形式・認証方式・HTTPヘッダーを使って接続するか」を定義します。つまり、Codex本体のファイル操作・ターミナル実行・差分編集・エージェントループなどはそのままで、推論先だけを別LLMにできます。citeturn711593search1turn711593search14

概念的にはこうです。

```text
Codex CLI / Codex App
        │
        │ Agent Loop
        │
        ├─ ファイルを読む
        ├─ コードを編集
        ├─ shell commandを実行
        ├─ テスト結果を読む
        └─ 次の行動を判断
        │
        ▼
   Model Provider
        │
        ├─ base_url
        ├─ API key
        ├─ model name
        └─ API protocol
        │
        ▼
 ┌───────────────┐
 │ OpenAI        │
 │ OpenRouter    │
 │ DeepSeek      │
 │ Gemini        │
 │ Mistral       │
 │ xAI           │
 │ Ollama        │
 │ 自社Gateway   │
 └───────────────┘
```

特に重要なのは、現在のCodexは **OpenAI製モデル専用のクライアントではない**という点です。公式のModelsドキュメントでも、Codexを **Chat CompletionsまたはResponses互換のモデル／プロバイダーへ向けられる**と説明されています。citeturn711593search6

したがって、のりあきさんがCodex上で他社LLMを動かしている場合、技術的にはおそらく以下のどれかです。

1. **OpenRouter経由**
   
   Codex → OpenRouter API → Claude / Gemini / DeepSeek / Qwen等

2. **各社APIへ直接接続**
   
   Codex → DeepSeek API  
   Codex → Gemini互換Endpoint  
   Codex → Mistral等

3. **OpenAI API互換Gateway経由**
   
   Codex → 自前Gateway → 各LLM

4. **ローカルLLM**
   
   Codex → Ollama等 → Qwen / DeepSeek / Llama

ここでDataQorixとの関係がかなり重要です。

今Codexがやっている **Model Provider abstraction** は、ほぼそのままDataQorixの「検索版」に置き換えて考えられます。

```text
Codex
 │
 ├── Model Provider
 │      ├ OpenAI
 │      ├ Claude
 │      ├ Gemini
 │      └ DeepSeek
 │
 └── Search Provider ← DataQorixが狙える場所
        ├ Exa
        ├ Tavily
        ├ Brave
        ├ Perplexity
        ├ Firecrawl
        ├ 業界DB
        └ 顧客専用DB
```

さらに一段進めるなら、

```text
Codex
   │
   ▼
DataQorix Gateway
   │
   ├── LLM Router
   │      Claude
   │      GPT
   │      Gemini
   │      DeepSeek
   │      Qwen
   │
   └── Search Router
          Exa
          Tavily
          Brave
          SERP
          DB
          Scraper
```

という **「Model Gateway + Search Gateway」** にできます。

この構造だと、Codex側から見るとほぼ単一のOpenAI互換Endpointに見せながら、裏側で

**モデル選択 → 検索先選択 → DB選択 → クロール → RAG → 回答**

までルーティングできます。

これはDataQorixにかなり示唆があります。**Codexがすでに証明しているModel Provider abstractionを、Search/Data Provider abstractionへ拡張する**という説明ができるからです。citeturn711593search1turn711593search6

そしておそらく一番重要なのは、**Codexそのものを作る必要はない**ことです。

DataQorix側が、

```text
OpenAI-compatible API
Responses API compatible
MCP
```

の3つを入口として持てば、

**Codex / Claude Code / Cursor / OpenClaw / Hermes / 自社Agent**

から共通の検索・DBオーケストレーターを利用できる設計にできます。

DataQorixの現在の方向性から見ると、これはかなり筋が良いアーキテクチャです。memcite
