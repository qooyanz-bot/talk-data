10ワーカー構成は、単純に「botを10個起動する」という話ではありません。

重要なのは**1つの巨大な仕事を、10人の作業員に重複なく分担させる**ことです。

あなたのEnterpriseOSのように数百万件規模のデータを継続収集する場合、この方式が一般的です。

## 全体構成

```text
                    Coolify
                       │
        ┌──────────────┼──────────────┐
        │              │              │
     Worker1       Worker2       Worker3
        │              │              │
     Chromium      Chromium      Chromium
        │              │              │
        └──────────────┼──────────────┘
                       │
                 PostgreSQL
                       │
        URL Queue / Job Queue
                       │
          未処理URL・状態管理
```

これを10台まで増やします。

```text
Worker1
Worker2
Worker3
...
Worker10
```

全員が同じDBを見ています。

---

# PostgreSQLが司令塔になる

例えばDBに

|id|URL|status|
|---|---|---|
|1|A店|pending|
|2|B店|pending|
|3|C店|pending|
|4|D店|pending|

が入っています。

Worker1が起動すると

```sql
SELECT *
FROM tabelog_restaurant_urls
WHERE status='pending'
LIMIT 1;
```

ではなく

```sql
FOR UPDATE SKIP LOCKED
```

を使います。

つまり

```
Worker1
↓

A店をロック
```

になります。

その瞬間

Worker2は

```
A店
```

を取得できません。

代わりに

```
B店
```

を取得します。

Worker3

↓

```
C店
```

Worker4

↓

```
D店
```

となります。

---

## SKIP LOCKEDとは？

例えば100万件URLがあるとします。

普通なら

```
Worker1
↓

12345番取得

Worker2

↓

12345番取得

重複
```

になります。

SKIP LOCKEDなら

```
Worker1

12345

Worker2

12346

Worker3

12347
```

になります。

つまり

**同じ店舗を二度取得しません。**

これが大量クローリングでは必須です。

---

# Workerは何をする？

例えばWorker5。

```
URL取得

↓

Playwright起動

↓

Chrome起動

↓

店舗へアクセス

↓

DOM解析

↓

JSON生成

↓

PostgreSQL保存

↓

status=done
```

終了すると

またDBから

```
pending
```

を取得します。

つまり

```
取得

↓

取得

↓

取得

↓

取得
```

を永遠に繰り返します。

---

# Coolify側

Coolifyでは

```
scraping-platform
```

というDockerイメージを作ります。

そこから

```
Worker1

Worker2

Worker3

...

Worker10
```

を起動するだけです。

全員

```
node worker.js
```

を実行します。

コードは全員同じです。

違うのは

```
DBから取得したURL
```

だけです。

---

# 処理速度

例えば

1店舗

```
5秒
```

なら

100万店舗

```
5,000,000秒
```

ですが

10並列なら

```
500,000秒
```

になります。

理論上

約10倍高速になります。

---

# さらに100ワーカーにすると？

実は簡単です。

```
Worker1

Worker2

...

Worker100
```

を起動するだけです。

コードは変更不要です。

DBだけが

```
次のURL

↓

次のURL

↓

次のURL
```

と配るだけになります。

---

# EnterpriseOS向けならさらに改善できる

あなたのように数百万件規模を扱う前提なら、私は「URLキュー」だけでなく、役割ごとにワーカーを分ける構成を勧めます。

```text
URL Discovery Workers（10台）
    │
    ▼
URL Queue

    │
    ▼
Detail Workers（30台）

    │
    ▼
PostgreSQL

    │
    ▼
Change Detection Workers（10台）

    │
    ▼
EnterpriseOS DB

    │
    ▼
AI Enrichment Workers（10台）

    │
    ▼
Embedding / RAG

    │
    ▼
Static Page Generator（10台）

    │
    ▼
Cloudflare R2

    │
    ▼
Cloudflare Workers
```

このようなパイプラインにすると、URL発見・詳細取得・変更検知・AIによる要約やタグ付け・静的ページ生成がそれぞれ独立してスケールします。

EnterpriseOSの最終目標が「500万社以上の企業情報を継続的に更新するAIプラットフォーム」であることを考えると、この**ジョブキュー＋ワーカー分散**の設計は、食べログだけでなく企業DB、採用情報、プレスリリース、ニュース収集など、すべてのスクレイピング基盤に共通して利用できる構成です。memcite
