# ① 中央DB公開VIEWとは？

通常のPostgreSQLには

```
company_directory.company2_companies
```

があります。

ここには

- raw JSON
- 監査情報
- 内部ID
- 将来追加するAI分析
- 編集履歴

など全部あります。

しかし公開サイトは

```
企業名
住所
概要
法人番号
```

だけ見えれば十分です。

そこで

```
company_public_api.companies
```

というVIEWを作っています。

イメージすると

```
company2_companies
─────────────────────────────
id
raw_json
source_url
internal_note
ai_score
・・・
company_name
address
・・・

      ↓

company_public_api.companies
────────────────────
company_name
address
corporate_number
summary
slug
```

つまり

**公開してよい列だけ抜き出した仮想テーブル**

です。

# ② なぜVIEWを使うの？

例えば将来

```
AI評価

メール
```

を追加しても

VIEWを変えなければ

公開サイトには一切見えません。

つまり

```
中央DB
↓
VIEW
↓

```

という境界になります。

これはかなり一般的な設計です。

# ③ Hyperdriveとは？

ここが一番重要です。

普通ならWorkerから

```
PostgreSQL
```

へ直接接続します。

```
Worker
    ↓
5432
    ↓
Postgres
```

でもこれだと

- 接続数爆発
- セキュリティ
- レイテンシ
- 接続確立が遅い

という問題があります。

Cloudflareが用意しているのが

**Hyperdrive**

です。

イメージは

```
Worker

↓

Hyperdrive
(接続プール)

↓

PostgreSQL
```

Hyperdriveが

```
1000リクエスト
```

来ても

```
DB接続は5～10本
```

くらいにまとめてくれます。

だから高速です。

---

# ④ Hyperdrive Bindingとは？

Workerの設定で

例えば

```toml
[[hyperdrive]]
binding = "HYPERDRIVE"
id = "xxxxx"
```

という設定をします。

するとWorkerの中では

```ts
env.HYPERDRIVE
```

が使えるようになります。

今はこれがありません。

だからコードは

```ts
if (env.HYPERDRIVE) {

    中央DBを読む

}
```

となっていても

実際は

```
env.HYPERDRIVE == undefined
```

なので

中央DBへ行けません。

# ⑤ D1フォールバックとは？

コードは

```

↓

YES
中央DB

↓

NO

↓

D1
```

という流れになっています。

つまり

```

    return postgres

}

return d1
```

です。

現在はHyperdriveが無いので

常に

```

```

が使われています。

# ⑦ 企業ページ生成の流れ

本来完成形は

```
企業ページアクセス

↓

↓

Hyperdrive

↓

↓

HTML生成

↓

Cloudflare Cache

↓

```

例えば

```

```

へアクセスすると

```sql

FROM company_public_api.companies

```

を実行し

結果からHTMLを生成します。

静的ファイルを577万枚持つ必要はありません。

## EnterpriseOS向けにさらに改善するなら

現状の「Worker → Hyperdrive → PostgreSQL」は企業詳細ページには適していますが、577万社規模を考えると一覧・検索まで毎回PostgreSQLに問い合わせるのは非効率です。

私なら役割を分けます。

- **PostgreSQL**：577万社の原本・更新・AI分析・営業シグナル。
- **Hyperdrive**：企業詳細ページや管理画面など、最新性が必要なデータ取得。
- **Cloudflare KV**：法人番号→slug、検索補助、人気企業などの超高速キー検索。
- **D1**：検索インデックスや新設法人一覧など、公開用の軽量データ。
- **Cloudflare Cache**：企業詳細HTMLをエッジでキャッシュ。

この構成なら、577万社を超えて数千万社規模になっても、公開サイトの速度と運用コストを抑えやすくなります。
