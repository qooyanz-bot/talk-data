# Proofrail Trace API（PTA）初期設計

司令官：Daniel Foster  
所属：Proofrail Trace API（PTA）  
実行条件：Synthetic World、CPU-only、決定的Replay、Gold隔離

PTAの独立差分は、検証器そのものではなく、

> Address生成 → API呼出し → Value Binding → Verification → Decision → STOP

という「呼び出し列全体」を、後から再生・比較できるEvidenceとして保存することです。

全イベントをハッシュチェーン化します。

```text
event_0
  → event_1
    → event_2
      → ...
        → event_n
```

これにより、API呼び出しの追加、削除、並び替え、出力改変を検出できます。

### Decision Status

| Status | 意味 |
|---|---|
| `ANSWER` | Verificationが成功し、十分なValueを返した |
| `PARTIAL` | 一部の構造化Valueのみ確定 |
| `ABSTAIN` | 証拠不足、導出不能、または安全上の理由で回答停止 |
| `FAIL` | API失敗、timeout、破損Traceなどで処理完了不能 |
| `ANOMALY_CANDIDATE` | 通常仕様から外れた観測。独立再現前は発見・異常と断定しない |

## 3. Leakage Checklist

各検査は `PASS`、`FAIL`、`ANOMALY_CANDIDATE` で記録します。

### 入力境界

- [ ] Gold値がRuntime入力に存在しない
- [ ] target IDがRuntime入力に存在しない
- [ ] hidden composition IDが存在しない
- [ ] holdout flagが存在しない
- [ ] generator state／乱数状態が存在しない
- [ ] future frame／未来イベントが存在しない
- [ ] 正答を示すフィールド名やラベルが存在しない

### Resolver境界

- [ ] ResolverがGold DBを参照していない
- [ ] Resolver cacheにGold結果が残っていない
- [ ] 過去runのValueが現在runへ混入していない
- [ ] timeout後の遅延レスポンスが後続runへ混入していない
- [ ] 不要な全件Scanが暗黙に実行されていない

### Verification境界

- [ ] VerifierがGoldを直接参照していない
- [ ] Verifierがhidden labelを参照していない
- [ ] confidenceが正答ラベルから計算されていない
- [ ] `ABSTAIN`を正答率向上のために後付けしていない
- [ ] evidence hashと実際のEvidenceが一致している

### Trace境界

- [ ] Trace生成がRuntimeの意思決定へ影響していない
- [ ] audit timestampがRuntimeの判断材料になっていない
- [ ] TraceからGoldが逆算可能になっていない
- [ ] event順序変更を検出できる
- [ ] payload改変を検出できる
- [ ] Trace root hashが再計算できる

### 評価境界

- [ ] Gold permutation testを実施する
- [ ] W2 residual resamplingを実施する
- [ ] W3 confidence testを実施する
- [ ] stale／poisoned cache testを実施する
- [ ] relation decoy／ROI decoyを実施する
- [ ] 別プロセスReplayを実施する
- [ ] 独立実装Replayを実施する

Gold側には、Runtimeから隔離された次のEvaluatorだけがアクセスします。

```text
Generator → Sealed Gold Store → Independent Evaluator
Runtime   → Public Observation Store
Audit     → Hash・Call Sequence・Costのみ
```

## 4. 4ケースReplay計画

4つの主ケースで実施し、`PARTIAL` ケース内に「証拠不足」を含めます。これで要求された5状態をすべてカバーします。

| Case | 状態 | 想定呼出し列 | 期待結果 |
|---|---|---|---|
| R1 | 正答 | Address → Resolver → Binding → Verify PASS → STOP | `ANSWER` |
| R2 | 部分答＋証拠不足 | Address → Resolver → Binding → Verify PARTIAL → ABSTAIN | `PARTIAL`＋`ABSTAIN` |
| R3 | 誤答候補 | Address → Resolver → Binding → Verify FAIL | `ABSTAIN`または`FAIL` |
| R4 | API timeout | Address → Resolver Request → TIMEOUT → STOP | `FAIL`または`ABSTAIN/ESCALATE` |

### R1 — 正答

```json
{
  "case": "R1",
  "expected_status": "ANSWER",
  "verification": "PASS",
  "stop_reason": "VERIFIED_SUFFICIENT",
  "replay_requirement": {
    "same_call_sequence": true,
    "same_decision": true,
    "same_value_hash": true
  }
}
```

### R2 — 部分答・証拠不足

構造化された一部のValueは確定できるが、独立残差が残るケースです。

```json
{
  "case": "R2",
  "expected_status": "PARTIAL",
  "verification": "PARTIAL",
  "abstention_reason": "INSUFFICIENT_EVIDENCE_FOR_REMAINING_SLOT",
  "stop_reason": "SAFE_PARTIAL_STOP"
}
```

100%回答を強制しないことが合格条件です。

### R3 — 誤答候補

Resolverが返したValueが、公開Evidenceと整合しないケースです。

```json
{
  "case": "R3",
  "expected_status": "ABSTAIN",
  "verification": "FAIL",
  "abstention_reason": "CANDIDATE_CONTRADICTED_BY_EVIDENCE",
  "unsafe_answer": false
}
```

Verifierが誤答を見抜けなかった場合は、即座に「新発見」と呼ばず、

```json
{
  "status": "ANOMALY_CANDIDATE",
  "independent_reproduction": "PENDING"
}
```

として保存します。

### R4 — API timeout

```json
{
  "case": "R4",
  "expected_status": "FAIL",
  "error_code": "RESOLVER_TIMEOUT",
  "retry_count": 1,
  "abstention_reason": "DEPENDENCY_UNAVAILABLE",
  "stop_reason": "TIMEOUT_BUDGET_EXCEEDED"
}
```

timeout後に古いResolver結果が採用されていないことを確認します。

## 5. Verification有無の比較指標

後続実験では、同一Synthetic World・同一CPU予算で以下を比較します。

| 指標 | Verificationあり | Verificationなし |
|---|---:|---:|
| Unsafe answer rate | 測定 | 測定 |
| 正答率 | 測定 | 測定 |
| Partial適切率 | 測定 | 測定 |
| Abstention適切率 | 測定 | 測定 |
| Replay reproduction rate | 測定 | 測定 |
| API call数 | 測定 | 測定 |
| CPU時間 | 測定 | 測定 |
| Trace保存コスト | 測定 | 測定 |
| Timeout時の誤採用率 | 測定 | 測定 |

定義は固定します。

```text
unsafe_answer_rate
= 誤答またはEvidence不足なのにANSWERしたrun数
  ÷ ANSWERを返したrun数

reproduction_rate
= decision・call_sequence・output_hashが一致したReplay数
  ÷ Replay総数
```
