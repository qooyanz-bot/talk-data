````
# ② Public VIEW

ここがかなり重要です。

Workerから

```
SELECT *
FROM company2_companies
```

なんて絶対にやってはいけません。

理由は

```
rawデータ

内部メモ

AI評価

管理項目

監査ログ

将来追加する情報
```

まで全部見えてしまいます。

だから

```
company_public_api.companies
```

というVIEWを作ります。

例えば

```
SELECT

name

address

homepage

description

industry
```

だけ公開。

内部項目は全部隠します。

つまり

```
中央DB
↓

公開用VIEW
↓

Worker
```

になります。

これが普通のSaaS設計です。

# ③ Hyperdrive

Hyperdriveは

Cloudflareが提供している

**PostgreSQL専用コネクションプール**

です。

通常Workerは

```
アクセス

↓

PostgreSQL接続

↓

切断
```

を毎回繰り返します。

1000人来ると

```
1000接続
```

になります。

PostgreSQLはこれが苦手です。

Hyperdriveを使うと

```
Worker

↓

Hyperdrive

↓

接続プール

↓

PostgreSQL
```

になります。

つまり

```
1000アクセス

↓

Hyperdrive

↓

接続5〜10本
```

程度で済みます。

速度もかなり改善します。

       ┌──────┴────────┐

       │

       │

```

この構成なら、

- 577万社をそのまま検索できる
- AI要約を後から追加できる
- 新設法人が毎日増えても即反映できる
- SEO向け企業ページをリアルタイム生成できる
- 静的ファイルを大量生成・再デプロイする必要がない

となります。

## 私ならさらに一歩進めます

EnterpriseOSの目的が「新設法人向けに最速でWeb制作を受注すること」であれば、**企業詳細ページをリアルタイム生成するだけでは足りません**。

577万社の各ページに、

- AIが生成した企業紹介
- 業種別テンプレート
- 「公式サイトが未登録です」という案内
- 「3分で公式Webサイトを公開」のCTA
- 問い合わせフォーム

まで自動生成します。

すると企業情報ページ自体が営業ページになり、毎日追加される新設法人へ自然にアプローチできます。この用途では、中央DB＋Hyperdrive＋Worker SSRの構成は非常に相性が良い設計です。
````
