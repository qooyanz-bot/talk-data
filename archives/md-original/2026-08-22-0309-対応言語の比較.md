### まず「対応言語」には3種類あります

| レベル | 意味 | 例 |
|---|---|---|
| UI対応 | メニューや設定画面をその言語で表示できる | Claudeの日本語UI |
| モデル対応 | その言語を入力して理解・生成できる | Claudeに中国語で質問→中国語で回答 |
| 高品質対応 | 推論・要約・検索・RAGなどを実用水準で処理できる | 日本語で専門的な技術質問に正確に回答 |

# DataQorixでは「対応言語数」で判断しない方がいい

ここが事業上は重要です。

LLM向け多言語検索基盤を作る場合、

> Gemini 109言語  
> OpenAI 58言語  
> Claude 11言語

だから、

> Gemini > OpenAI > Claude

とは評価できません。

これは比較軸が混ざっています。

むしろDataQorixで測るべきなのは次のようなものです。

| 指標 | 何を見るか |
|---|---|
| Language Understanding | 質問を正しく理解できるか |
| Retrieval Recall | その言語の文書を検索できるか |
| Cross-lingual Retrieval | 日本語質問→英語/中国語資料を検索できるか |
| Citation Recall | 正しい根拠を引用できるか |
| Answer Quality | 回答品質 |
| Entity Resolution | 固有名詞を正しく統合できるか |
| Translation Loss | 言語変換で情報が落ちないか |
| Token Efficiency | 同じ情報量に必要なtoken |
| Cost | 1問あたりAPI費用 |
| Latency | 応答速度 |

これを、

**言語 × LLM × Embedding × Search Engine**

で測った方がはるかに価値があります。

例えば、

> 日本語質問  
> ↓  
> 日本語Web検索  
> + 英語Web検索  
> + 中国語Web検索  
> ↓  
> Evidence Fusion  
> ↓  
> GPT / Gemini / Claudeのうち最適モデルへRouting  
> ↓  
> 日本語回答

という構造です。

これは単なる「多言語対応」より一段上の、**Cross-Lingual RAG / Cross-Lingual Search Routing**になります。

### 特に面白いのは低リソース言語です

英語・日本語・中国語・スペイン語などは3社ともかなり強いので、差別化が難しい。

一方、

**クメール語 → 英語資料  
ラオ語 → タイ語＋英語資料  
スワヒリ語 → 英語資料  
ウズベク語 → ロシア語＋英語資料**

のように、質問言語と情報量の多い検索言語を分離すると、DataQorix側に大きな役割が生まれます。

つまり、

**「LLMが何語を話せるか」より「その言語の質問に対して、世界中のどの言語の情報を探せば最高品質になるか」**

をRouterが判断する。

これはかなり重要な設計思想です。
