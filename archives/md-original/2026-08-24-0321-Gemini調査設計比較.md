あなたが作ろうとしているデータ資産では、**Deep Researchそのものの文章を集めるより、「Deep Researchを使って発見した情報源・主張・反証・時系列」を構造化する方が価値が高い**です。

ではなく、最終的には、

**Query → Intent → Claim → Evidence → Source → Entity → Relation → Contradiction → Temporal Confidence**

という「研究プロセスのデータセット」にした方が商材として強くなります。

## 1. Gemini API無料枠について

以前の

> Gemini API (Flash) 無料枠: 1日1,500リクエスト → 月45,000回

は正確ではありません。

現在のGoogle公式料金では、Gemini 2.5 Flash / Flash-Liteの無料枠で**Google Search Groundingは最大500 RPD**です。有料Tierでは1,500 RPDまで無料、その後は1,000 grounded promptsあたり$35です。citeturn0search2turn0search3

したがって無料で検索付き処理をするなら理論上、

**500回/日 × 30日 = 15,000 grounded prompts/月**

が一つの基準になります。

ただし、これもGoogle AI StudioのUIにある「Deep Research」を15,000回実行できる、という意味ではありません。

**Gemini Flash + Google Search Grounding ≠ Gemini Deep Research**

です。

ここはデータ取得設計上かなり重要です。

## 3. OpenRouter「ほぼ無制限」も訂正

これは明確に間違いでした。

現在のurlOpenRouter公式料金turn0search1では無料アカウントは、

**50 requests/day**

です。

さらに$10以上のクレジットを入れたアカウントでは、無料モデルについて**1,000 requests/day、20 RPM**まで引き上げられるとOpenRouter自身が説明しています。citeturn0search9

したがって、

50 × 30 = **1,500回/月**

または条件を満たした場合、

1,000 × 30 = **30,000回/月**

程度です。

「ほぼ無制限」ではありません。

OpenRouterには現在25以上の無料モデルがありますが、公式にも無料モデルは低いrate limitでproduction向けではないとされています。citeturn0search1turn0search4

# 4. DeepSeekの「3万回=$42」も計算方法が違う

現在のurlDeepSeek API公式料金turn0search0ではDeepSeek V4 Flashは、

| 処理 | 100万token |
|---|---:|
| Input・cache miss | $0.14 = 約0.002万円 |
| Input・cache hit | $0.0028 |
| Output | $0.28 = 約0.004万円 |

です。citeturn0search0

しかし料金は**「1リクエストいくら」ではなくtoken量**で決まります。

例えばDeep Research相当の処理を自作して、

- Input 20,000 tokens
- Output 5,000 tokens

使ったと仮定します。

1回：

20,000 × $0.14 / 1M  
＋  
5,000 × $0.28 / 1M

≒ **$0.0042**

3万回なら、

**約$126 = 約2.0万円**

です。

逆に1研究あたり10万〜50万tokenを食わせれば、当然もっと高くなります。

したがって、

> DeepSeek APIなら3万回で$42

とは固定できません。

# 5. ここからが重要：Deep ResearchデータはSERPより価値が高いか

**単純比較なら高いです。ただしSERPとは別の商品です。**

SERPは、

> Query → ranked URL

です。

Deep Researchは、

> Query  
> → Subquery  
> → Source discovery  
> → Reading  
> → Claim extraction  
> → Cross-source comparison  
> → Synthesis

になります。

あなたが欲しいGraphに極めて近い。

そこで私は「DeepResearch結果」という単位を捨てることを勧めます。

### Research Graphにする

例えば、

```text
Research Topic
│
├── Search Intent
│
├── Sub Questions
│
├── Claims
│    ├── Supporting Evidence
│    └── Contradicting Evidence
│
├── Entities
│
├── Relations
│
├── Sources
│
├── Source Authority
│
├── Published At
│
├── Retrieved At
│
└── Temporal Confidence
```

これならかなり面白いデータになります。

# 6. 特に追加すべきなのが「Contradiction Graph」

Graph Knowledge + Ontologyだけでは、競争力としてまだ弱いです。

例えば、

**DeepSeek V4 → beats → Model X**

というEdgeだけ保存するのでは不十分です。

実際には、

```text
Claim:
DeepSeek V4 > Model X

Evidence A:
Benchmark AAA → Supports

Evidence B:
Benchmark BBB → Contradicts

Evidence C:
Independent evaluation → Partially supports

Confidence: 0.72

Valid:
2026-07-15 ～ ?

Last verified:
2026-08-24
```

まで持つ。

これがLLM事業者には非常に重要です。

単なるKnowledge Graphではなく、

**Evidence Graph**

になります。

# 10. 私なら3種類の商品に分けます

ここは事業上かなり重要です。

**① Query Graph Dataset**

8,000万検索クエリ。

Intent / Ontology / Query relations中心。

**② Web Knowledge Graph Dataset**

SERPから取得したURLとWeb本文を処理。

Entity / Relation / Source / Temporal情報中心。

**③ Research Evidence Graph Dataset**

Deep Research型Agentによる多段探索。

Claim / Evidence / Contradiction / Confidence / Query Expansion中心。

そして三つをIDで接続します。

```text
80M Query Graph
        │
        ▼
SERP / URL Graph
        │
        ▼
Web Knowledge Graph
        │
        ▼
Research Evidence Graph
        │
        ▼
Temporal + Confidence Layer
```

これなら単なる「検索データセット販売会社」ではありません。

**「人間とAIがWebを調査するときの知識探索過程を構造化したデータ資産」**

になります。

私はこの方向の方が、単純に「8,000万検索クエリ＋8億URL」を大量販売するより、データ会社に説明しやすく、評価データ・RAG・Agent training・Search trainingなど複数用途へ展開しやすいと考えます。

そして重要なのは、Gemini/OpenRouter/DeepSeekなどの利用規約と再配布権をサービスごとに確認して、**第三者モデルの生成文そのものを主商品にしない設計**にすることです。ソースURL・自前抽出・独自Graph・provenanceを中心に据える方が、データ資産としても法務DD上も強くなります。memcite
