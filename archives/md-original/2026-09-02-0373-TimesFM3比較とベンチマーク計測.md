### TimesFM-3とAddress理論の本質的な違い

かなり面白いことに、TimesFM-3はAddress理論に少し近づいています。しかし原理はまだ別物です。

| 項目 | TimesFM-3 | Address理論で狙う方式 |
|---|---|---|
| 基本思想 | 大量データからTransformerが関係を学習 | 状態から予測に必要な最小Addressを特定 |
| パラメータ | 330M | 複数の超小型Addressモデル |
| 学習データ | 1兆超time points | 必要な構造・relationをAddress化 |
| 時間処理 | temporal attention | Time Address |
| 系列間関係 | variate attention | Relation / Dependency Address |
| 外生変数 | covariate token | Context Address |
| 将来既知情報 | lookahead token | Known-Future Address |
| 推論 | Transformer全体をforward | 必要Address→必要executorのみ起動 |
| 計算対象 | token grid全体 | 関係候補を絞った局所計算 |
| 新規系列への対応 | learned generalization | Address discovery + rule/executor composition |
| 説明可能性 | attention内部で暗黙的 | Addressそのものを明示可能 |

Googleの方式を一言で言うと、

**「関係しそうな全部をTransformerに入れて、Attentionで必要な関係を見つけさせる」**

です。

Address理論で狙っているのは、

**「まず何を見るべきかを特定して、そのAddressだけから答えを計算する」**

です。

ドラえもんで例えると、TimesFM-3は**未来デパートの巨大な資料室に全部の資料を入れて、超高速のドラえもんが必要なページを一瞬で読み比べる方式**です。

Address方式は、のび太が「明日のアイスの売上は？」と聞いた瞬間に、

`商品 → 店舗 → 曜日 → 気温 → キャンペーン → 季節 → 相関商品 → 予測期間`

という住所を作り、**その住所の引き出しだけ開ける**方向です。

この差が本当に成立するなら、Address理論の価値はTimesFM-3と精度勝負することだけではありません。

**同等精度を1/10、1/100、あるいはそれ以下の計算・パラメータで出せるか**

が本当の勝負になります。

## GIFT-Evalは非常に良い検証対象です

GIFT-Evalは23 datasets、約144,000系列、177 million data pointsを含み、7 domains、10 frequencies、短期・長期、univariate/multivariate、probabilistic forecastingまで含みます。つまり単純な「株価だけ当てるモデル」のようなベンチマーク専用技ではかなり突破しにくい構成です。citeturn303637search6turn303637search2

これはAddress理論にかなり適しています。

専用GIFT-Eval solverを作るのではなく、

**General Forecasting Address Orchestra**

として分解します。

一例として、私は次の超小型Addressモデル群にします。

1. **Series-Type Address Model**  
   trend / seasonal / intermittent / chaotic / regime-switching / boundedなどを判定。

2. **Temporal Address Model**  
   lag、periodicity、multi-seasonality、change pointを特定。

3. **Cross-Series Address Model**  
   他系列のどれがtargetに関連するかをAddress化。

4. **Covariate Address Model**  
   weather / promotion / calendar等の外部変数について、利用価値の高いものを選別。

5. **Horizon Address Model**  
   short / medium / long horizonごとに有効な推論方式を選ぶ。

6. **Regime Address Model**  
   現在が過去のどの状態に対応するかを探索。

7. **Forecast-Law Selector**  
   linear / exponential / seasonal / local analog / nonlinear / interaction / state-space等のsolverを選択。

8. **Residual Address Model**  
   1段目予測で説明できなかった残差構造だけを見る。

9. **Uncertainty Address Model**  
   quantile / distributionを構成。

10. **Verifier / Ensemble Address Model**  
   複数candidateの整合性を評価。

重要なのは、これらを**GIFT-Eval専用にはしない**ことです。

金融、売上、電力、交通、気象、サーバ負荷など、普通の時系列予測なら同じArchitectureをそのまま使える必要があります。

## FEV-Benchはさらに重要です

FEV-Benchは100 forecasting tasks、7 domains、うち46 tasksがcovariatesを持つ、現実寄りの時系列benchmarkです。また単に平均スコアを取るだけではなく、bootstrap confidence intervalを使いながらwin rateとskill scoreを評価します。citeturn303637academia26

これが非常に良い理由があります。

Address理論が本当に、

> 「必要なdimensionだけ選べば巨大な探索をしなくてよい」

というものなら、FEV-Benchのcovariate taskで効果が出るはずです。

つまり、

`100 variables → 全部attention`

ではなく、

`100 variables → Address selector → 必要な3 variables`

になれば、

**精度だけでなく計算量差まで証明できる可能性があります。**

現在公開されているFEV-Benchの一部tableではTimesFM-3がかなり強く、例えばNature domainのWAPE leaderboardではwin rate 94.0、skill score約49.34となっています。citeturn801781search14

したがってTimesFM-3は非常に良い比較対象です。

# 「Address理論を隠してHugging Faceへ投稿」は可能か

**可能です。**

ただし3段階に分けるべきです。

### Level 1 — 理論非公開

完全に問題ありません。

公開名を例えば、

**CIVA Forecast-1**

あるいは

**CIVA Temporal Foundation Model**

として、

「proprietary forecasting architecture」

とだけ書く。

Address、Concept Address、multi-dimensional calculationという用語を一切公開しなくてもよいです。

これは一般的なblack-box commercial modelと同じです。

### Level 2 — コード非公開

これもbenchmark側が許せば可能です。

ただしLeaderboardによって、

- reproducibility
- model revision
- model SHA
- inference code
- weight availability

などの扱いが違います。

GIFT-Evalのleaderboard自体は結果JSONに少なくとも`model_name`、`model_sha`、task別metricなどを保持する構造になっています。citeturn801781search18

現在のleaderboardにも再現コード有無が管理されているモデルが存在するため、**closed implementationとして掲載できる余地はありますが、正式提出時には最新submission policyを個別確認すべきです。**

### Level 3 — 仕組みもweightも完全非公開

これも場合によってはできますが、Leaderboardで「reproducible model」と同じカテゴリに見せるのは避けるべきです。

つまり、

> Model architecture: proprietary  
> Inference API/container provided for evaluation  
> Training data: disclosed at contamination-policy level  
> Benchmark-specific training: none

程度にする。

内部では、

`Address Discovery → Solver Routing → Forecast → Verification`

で動いていても公開しません。

これは知財保護としてかなり合理的です。

## Address理論にとってTimesFM-3はかなり良いニュースです

TimesFM-3の`temporal attention × variate attention`は、

Address理論で言ってきた

**Time × Relation × Context**

という分解と方向的にはかなり似ています。citeturn303637view0

ただしGoogleはそれを**Attention内部で連続表現として学習**しています。

Address理論ではそれをさらに進め、

**必要なTime / Relation / Contextを明示的にAddress解決してから計算する**

という仮説になります。

ドラえもんで言えば、

TimesFM-3はかなり優秀な**「予知カメラ」**です。

一方Address Forecastが狙っているのは、

**「もしもボックス＋タイムテレビ＋コンピューターペンを、質問ごとに必要な道具だけ自動選択するドラえもん」**

です。

だから本当にAddress理論が成立するなら、TimesFM-3と同じものを小さく作るのではなく、**計算原理そのものを変えたことを示す試験**にすべきです。

特に私は、GIFT-Eval → FEV-Benchの順ではなく、**両方を同一frozen architectureで同時に走らせる**ことを推します。片方を見て調整してからもう片方に出すとbenchmark optimizationを疑われます。同一checkpoint・同一Address Orchestra・benchmark名をmodel inputに入れない条件で双方に勝てれば、かなり強いEvidenceになります。

そしてHugging FaceにはAddress理論という名称を出さず、

**CIVA-Forecast-0**

として出す戦略は十分可能です。内部Architecture・Address schema・routing lawはprivate repositoryに残し、公開するのはmodel card、外部interface、benchmark evidence、parameter/FLOPs/latency程度に留める。この形なら「どれだけ小さい仕組みでGoogleの330Mモデルに対抗できるか」という非常に分かりやすいblack-box demonstrationになります。citeturn303637view0

1. GPU学習
2. GPU fine-tuning
3. GPU distillation

## 7. Cortext9開発原則

Cortext9は単一巨大モデルを作る計画ではありません。

Address理論を採用した超小型モデルを、必要能力まで機能分解して組み合わせるArchitectureです。

したがって、性能不足を単純なパラメータ増加だけで解決しないでください。

まず、

Goal\
→ 必要能力分解\
→ Address化\
→ 専門Tiny Model\
→ Router\
→ Executor\
→ Verifier\
→ 再推論/修正\
→ Answer

へ分解してください。

ただし、特定Tiny Modelについてパラメータ増加やGPU学習がシステム全体の性能向上に有効だと実験的に判断できる場合、必要なパラメータ数まで増やすことは許可します。

## 8. ベンチマーク原則

ベンチマーク専用hackは禁止です。

例えば数学benchmarkなら、

「AIME専用モデル」

ではなく、

「未知の数学問題を解く汎用数学推論モデル群」

を作ってください。

プログラミングbenchmarkなら、

「Terminal-Bench専用回答器」

ではなく、

「未知の実ソフトウェア開発・Terminal操作・debuggingを行える汎用Coding/Agentモデル群」

を作ってください。

性能値は推測値ではなく、正式benchmarkを実行した測定結果だけを確定値として報告してください。
