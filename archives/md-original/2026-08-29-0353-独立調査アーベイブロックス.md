- `version`はリソース単位の単調増加整数。

## 3. Version・競合・再試行規則

### Optimistic concurrency

```text
GET version=10
      ├─ Client A patch base_version=10 → COMMITTED version=11
      └─ Client B patch base_version=10 → CONFLICT
```

同じVersionから始まった変更を自動マージしません。初期実験では、異なるフィールドへの変更でも厳密競合とします。

理由は、暗黙のマージによるLost Update隠蔽を避けるためです。

### Idempotency

同一`idempotency_key`について：

| 条件 | 結果 |
|---|---|
| 同じkey・同じpayload | 最初の結果を再返却。Version増加なし |
| 同じkey・異なるpayload | `409 IDEMPOTENCY_KEY_REUSE` |
| 新しいkey | 通常処理 |

### Rollback

Rollbackは過去Versionへの履歴書き換えではありません。

```json
{
  "namespace": "personal",
  "subject_id": "syn:identity:001",
  "base_version": 9,
  "idempotency_key": "idem:rollback:001",
  "operation": "rollback",
  "target_version": 7
}
```

結果：

```text
version 7 → version 10
```

Version 8・9は削除されず、Version 10に「Version 7を復元した」という補償変更を記録します。

すべての操作について、次のイベントをappend-onlyで保存します。

```json
{
  "audit_event_id": "audit:008",
  "resource_id": "st_syn_001",
  "namespace": "personal",
  "operation": "PATCH",
  "outcome": "COMMITTED",
  "version_before": 7,
  "version_after": 8,

  "idempotency_key": "idem:test:001",

  "before_digest": "sha256:...",
  "after_digest": "sha256:...",

```

`operation`には少なくとも以下を使用します。

```text
READ
PATCH
OVERWRITE
ROLLBACK
DELETE
EXPIRE
CONFLICT
FAIL
APPEND
RECALL
```

失敗時も以下を残します。

- 失敗理由
- request digest
- actor
- idempotency key
- base version
- 現在Version
- 変更が発生しなかったこと

## 6. Namespace保持境界

| Namespace | 許可対象 | 禁止事項 |
|---|---|---|
| Personal | Synthetic Identity本人のState、Goal、Episode | 他Identityの個人Stateを直接変更 |
| Shared | Synthetic Identity間のRelationship、共有Episode | Personal属性の暗黙コピー |
| Public | 合成Fixture、公開Schema、再現用テストデータ | Personal／Sharedデータの直接公開 |

境界はデフォルト拒否です。

Namespace間のコピーは、通常のPatchではなく、明示的な`export_fixture`操作として扱います。今回は実装対象外とし、誤越境が発生した場合は`FAIL`として記録します。

## 7. TTLと削除

初期Toy実験の保持期間：

| 対象 | 初期TTL |
|---|---:|
| Personal State | 7日 |
| Shared State | 30日 |
| Public Fixture | 90日 |
| Unconfirmed Memory | 24時間 |
| Confirmed Memory | 30日 |
| Audit metadata | 365日 |

削除要求の処理：

1. Stateを論理削除。
2. 通常のGet/Recallから即時除外。
3. State本体を物理消去。
4. 監査履歴にはdigestと削除事実だけ残す。
5. 削除後は元データのRollback不可。

つまり、削除後も「削除された」という証跡は残りますが、個別内容は復元できません。

## 8. 全再計算方式との比較軸

比較対象は次の3方式です。

| Backend | 特徴 |
|---|---|
| Session-only | メモリ上のみ。再起動で消失 |
| KV-like | 最新StateとAuditをKey-Value保存 |
| SQLite-like | State、Version、Memory、Auditをトランザクション保存 |

比較ベースライン：

```text
Full Recompute:
全Episode・全Memoryを毎回読み直し
→ Stateを最初から再構築
```

測定項目：

- Read latency
- Write latency
- CPU時間
- 読み取りレコード数
- 書き込みバイト数
- Patch payloadサイズ
- Auditイベント数
- Retry回数
- Conflict検証時間
- Rollback時間
- TTL掃除時間
- State再現に必要な総データ量

CSEの仮説は「常に高速」ではありません。

小規模ではFull Recomputeとの差は小さく、Version履歴・部分更新・競合検出・再現可能な過去Stateが増えたときに、State Exchange方式の利点が現れるかを検証します。
