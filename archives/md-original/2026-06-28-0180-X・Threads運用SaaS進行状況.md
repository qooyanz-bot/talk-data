```
# 初期MVPの売り込み方

## 1. 最初に売る相手

最初のターゲットは以下に絞る。

- 人材紹介会社
- 求人広告代理店
- RPO会社
- SES会社
- AI導入支援会社
- 営業代行会社

最初から大手SaaS企業を狙わない。  
理由は、導入審査・セキュリティ確認・CRM連携要求が重く、MVP段階では商談が長引くため。

初期は「営業先に困っているが、営業リスト作成に時間を使っている中小BtoB営業会社」を狙う。

---

## 2. 売り文句

### メインコピー

毎朝、今日営業すべき20社と、その営業理由を届けます。

### 補足コピー

求人・採用ページの変化を検知し、  
「なぜ今その会社に営業すべきか」  
「何を提案すべきか」  
「最初に何と送るべきか」  
までAIが整理します。

営業リストではなく、営業理由付きの商談候補リストです。

---

## 3. 刺さる課題

営業リストはある。  
でも、営業理由がない。

その結果、

- とりあえず一斉メールを送る
- 古いリストに電話する
- 担当者が毎朝検索している
- 求人サイトを手作業で見ている
- 営業メールが薄い
- アポ率が低い

という状態になっている。

この問題に対して、SignalOSは「企業の変化」を営業理由に変える。

---

## 4. 初期オファー

### β版プラン

月額 30,000円

内容：

- 毎週または毎朝の営業候補リスト
- 20社〜50社
- 採用シグナル
- 根拠URL
- 推定ニーズ
- 提案切り口
- 初回営業文面
- CSV納品
- Slack通知またはメール納品

最初はSaaS画面を売らない。
```

````
# 4層の定義

## 1. Why

**なぜ必要か**を書く層です。

ここには機能説明を書かない。  
事業上・顧客価値上・競争優位上の理由を書く。

### 書く内容

```txt
- 解決する顧客課題
- 事業上の意味
- 競合との差別化
- この機能がない場合の損失
- 成功時の顧客価値
- 成功時の事業価値
- KPIへの影響
```

### 例

```md
# Why

営業担当者は企業リストを持っていても、「なぜ今日その企業に営業すべきか」が分からない。

この問題を解決しない限り、SignalOSは単なる営業リストツールになる。

Recommendation Engineは、企業シグナルを商談機会へ変換し、毎朝「今日営業すべき20社」を提示するための中核機能である。

この機能が成立すれば、顧客は営業先選定の時間を削減し、営業活動の質を高められる。

# ドキュメント管理ルール

## Rule 1

**Whyがない機能は作らない。**

機能を追加したい場合、最初にWhyを書く。  
Whyが弱い機能は後回し。

---

## Rule 2

**Whatに書かれていないものはMVPに入れない。**

思いつき実装を防ぐ。  
MVPの膨張を防ぐ。

---

## Rule 3

**HowにDB/API/Jobがないものは実装しない。**

仕様が曖昧なままCodexに投げない。  
AIに任せるほど、設計の曖昧さはバグになる。

---

## Rule 4

**AI TasksにAcceptance Criteriaがないタスクは実行しない。**

完了条件がないタスクは、AI開発で必ず壊れる。

---

## Rule 5

**AI Tasksは1タスク1成果物にする。**

悪い例：

```txt
推薦機能を作る
```

良い例：

```txt
daily_recommendationsテーブルを作る
RecommendationRepositoryを作る
GET /api/recommendations/today を作る

# 最重要ルール

この管理方式にすると、ドキュメントは「資料」ではなくなります。

**事業判断 → 要件 → 技術設計 → AI実装**までを一直線に接続する実行基盤になります。

今後SignalOSでは、何かを作る前に必ずこの順序で判断します。

```txt
Why
↓
What
↓
How
↓
AI Tasks
↓
Implementation
```

この順序を守らないと、また機能過多のSaaSになります。  
特に初期MVPでは、Whyが弱い機能は切ってください。  
今作るべきなのは「多機能な営業SaaS」ではなく、**商談を増やす最小の仕組み**です。
````

## user / 2026-06-28T19:50:02.0000000Z

```
ドキュメントの詳細を詰めて下さい
```

## assistant / 2026-06-28T19:50:27.0000000Z

```
まず初期MVPに直結する中核ドキュメントへ絞り、商談創出に関係しない資料は後回しにします。Why→What→How→AI Tasksが実装へ落ちる粒度で詰めます。
```

## assistant / 2026-06-28T19:52:23.0000000Z

```
null
```

## assistant / 2026-06-28T19:53:06.0000000Z

```
null
```

## assistant / 2026-06-28T19:53:06.0000000Z

````
了解です。  
ここからは、SignalOSを**「商談を増やすAI Revenue Operating System」**として進める前提で、ドキュメントを実装可能な粒度まで詰めます。

まず重要なのは、**全ドキュメントを同じ粒度で作り込まないこと**です。  
最初から26カテゴリすべてを詳細化すると、開発前にドキュメント沼になります。

初期MVPに必要なものを **P0**、β版に必要なものを **P1**、将来拡張を **P2** として分けます。

## why.md に書くこと

# Why

営業現場には、営業先リスト、CRM、MA、メール配信ツールはすでに存在する。

しかし、それでも新規商談が安定して増えない理由は、「今どの企業に、なぜ営業するべきか」が分からないからである。

SignalOSは、企業活動の変化を検知し、AIが営業理由・提案切り口・接触文面に変換することで、営業担当者が商談創出に集中できる状態を作る。

SignalOSの目的は情報提供ではない。

商談を増やすことである。

# What

## Mission

企業の変化を商談機会に変換する。

## Vision

AIが毎朝、今日商談につながる可能性が高い企業と営業理由を提示する世界を作る。

## Product Definition

SignalOSは、営業リストツールではない。

SignalOSは、企業シグナルをもとに商談創出を支援するAI Revenue Operating Systemである。

## Core Value

- 営業先選定時間を減らす
- 営業理由の質を上げる
- 初回接触の精度を上げる
- 商談化率を改善する
- 営業チームの再現性を高める
```

## how.md に書くこと

```md
# How

## Product Principles

1. 商談創出に直結しない機能は作らない
2. 顧客に大量データを渡さない
3. 毎朝「今日やるべきこと」を提示する
4. 根拠のない推定はしない
5. 自動送信よりも、まず営業判断支援を優先する
6. データ量ではなく、推薦精度で勝つ

## Decision Rule

新機能は以下の条件を満たす場合のみMVPに入れる。

- 商談数増加に直接関係する
- 営業担当者が毎週使う
- 顧客が月額5万円以上を払う理由になる
- 根拠データを提示できる

# 9. 最重要注意点

このドキュメント体系で一番危険なのは、また機能を増やしすぎること。

SignalOSは、最初からZoomInfoやClayを作るべきではない。

最初に作るべきものは、ただ一つ。

```txt
毎朝、今日営業すべき20社と、その理由を届ける仕組み

逆にこれが売れれば、後続機能は自然に売れる。
````

````
# なぜ必要か

SignalOSは「商談を増やす仕組み」を売るプロダクトです。

ならば、SignalOS自身の営業でも以下を実行すべきです。

```txt
企業シグナル収集
↓
見込み顧客抽出
↓
営業理由生成
↓
初回文面生成
↓
無料サンプル提案
↓
商談化
↓
受注
↓
学習
```

これを自社で回せば、次の3つが得られます。

1. **プロダクト検証**
   - 本当に営業先が見つかるか
   - 本当に営業理由が使えるか
   - 本当に返信率が上がるか

2. **販売実績**
   - 「自社でもSignalOSを使って商談を作っています」と言える

3. **改善データ**
   - どのシグナルが返信につながるか
   - どの文面が商談化するか
   - どの業種が最も買うか

これは強いです。

---

# ただし、やってはいけないこと

ここは厳しめに言います。

「SignalOSのマーケティング機能」まで作ろうとすると、また機能過多になります。

例えば、初期で以下を作るのは危険です。

```txt
SNS投稿管理
SEO記事生成
広告運用管理
LP A/Bテスト管理
MAツール
メール配信基盤
CRM完全連携
ステップメール
ウェビナー管理
リードスコアリング
```

これは別プロダクトです。

今作るべきではありません。

SignalOSの初期価値はあくまで、

```txt
今日営業すべき企業20社を出す
```

ことです。

Self-GTMは、それを**SignalOS自身の営業で使うための運用設計**に留めるべきです。

---

# Self-GTMの位置付け

SignalOS全体をこう整理します。

```txt
SignalOS Core

1. Signal Platform
   企業変化を取得する

2. Signal Score Engine
   営業優先度を判定する

3. Recommendation Engine
   今日営業すべき企業を推薦する

   上記を使ってSignalOS自身を売る
```

つまり、Self-GTMは新しい巨大機能ではありません。

既存の中核機能を、**自社営業用に使う運用レイヤー**です。
````

````
- Opportunity Score

## 8.5 Opportunity Score

100点満点で営業優先度を算出する。

### 加点

- 7日以内の新規シグナル：+20
- 営業職募集：+15
- エンジニア募集：+15
- 情シス募集：+15
- CS募集：+10
- 顧客の商材と一致：+20
- 根拠URLが明確：+10
- AI確信度が高い：+10

### 減点

- 根拠URLなし：-30
- シグナルが古い：-20
- 顧客の対象外業界：-30
- 除外企業：-100
````
