この構成は、**Cloudflareを分散ジョブ実行基盤として使い、Indeedの求人データを毎日自動収集するアーキテクチャ**です。

ただし、一点重要なのは、**Cloudflare側の処理能力と、Indeed側が実際に許容するアクセス量は別問題**ということです。Cloudflare側が1日1万ページ処理できても、対象サイト側の制限により同じペースで取得できるとは限りません。

## 全体像

```
Cron Trigger
      │
      ▼
検索条件を生成
      │
      ▼
Cloudflare Queue
      │
      ▼
Worker
      │
      ├─ Indeed検索
      ├─ HTML解析
      ├─ JSON化
      │
      ▼
Durable Object
      │
      ├─重複管理
      ├─進捗管理
      └─カーソル保存
      │
      ▼
R2 Storage
      │
      ├─JSON
      ├─JSONL
      └─CSV
```

これだけ見ると単純ですが、それぞれ役割があります。

---

# ① Cron Trigger

例えば

```
17 */6 * * *
```

なら

```
00:17
06:17
12:17
18:17
```

毎日4回動きます。

ここでは

```
営業 東京都

営業 大阪府

営業 愛知県

営業 福岡県
```

のような検索条件を作ります。

しかし全部一気にはやりません。

例えば

```
検索条件500件
```

あるなら

1回目

```
1〜10件
```

2回目

```
11〜20件
```

3回目

```
21〜30件
```

というローテーションになります。

---

# ② Durable Object

ここが一番重要です。

普通のWorkerは

```
実行終了
↓

メモリ消滅
```

になります。

つまり

```
今日はどこまで取得した？
```

が分かりません。

Durable Objectを使うと

```
現在

251番目の検索条件まで終了
```

を保存できます。

例えば

```
営業 東京

営業 大阪

営業 名古屋

営業 福岡
```

なら

```
cursor=2
```

なら

次回

```
営業 名古屋
```

から開始できます。

---

# ③ Queue

これが

```
仕事の整理係
```

です。

例えば

```
営業 東京
```

だけでも

```
1ページ

2ページ

3ページ

・・・

50ページ
```

あります。

これを

```
50件同時
```

にすると

Indeedに負荷が掛かります。

そこで

```
Queue

↓

1ページずつWorkerへ
```

送ります。

つまり

```
Page1

↓

Page2

↓

Page3

↓

Page4
```

順番になります。

---

# ④ Worker

Workerが実際に

```
https://jp.indeed.com/jobs?q=営業&l=東京都
```

を取得します。

HTMLを解析し

```
会社名

求人名

勤務地

給与

URL

企業ページ

仕事内容

掲載日
```

などを取り出します。

JSONへ変換します。

例えば

```json
{
 "company":"ABC株式会社",
 "title":"営業",
 "salary":"450万円",
 "location":"東京都",
 "url":"..."
}
```

になります。

# ⑤ R2

ここがデータベース代わりです。

例えば

```
2026/07/12/

営業東京

page1.json

page2.json

page3.json
```

のように保存できます。

CSVも作れます。

```
company,title,salary
```

という形です。

# なぜJSONLも保存する？

JSON

```
[
 {...},
 {...},
 {...}
]
```

は人が見るには便利です。

でもAIでは

```
{"company":"A"}

{"company":"B"}

{"company":"C"}
```

というJSONLの方が圧倒的に扱いやすいです。

将来

- ベクトルDB

- ナレッジベース

へ流し込むならJSONLが適しています。

# なぜDurable Objectが必要なの？

例えば

```
1000ページ取得
```

すると

途中で

```
503

タイムアウト

Worker終了
```

になります。

DOがあると

```
523ページまで終了
```

を覚えています。

次回

```
524ページ
```

から再開できます。

---

# Queueがある理由

Queueなし

```
500ページ

↓

500Worker同時起動
```

になります。

Queueあり

```
500ページ

↓

Queue

↓

Worker

↓

Worker

↓

Worker
```

となり、負荷を平準化できます。

# あなたのEnterpriseOSならさらにこう拡張できます

あなたが目指している **EnterpriseOS / DealVane** の企業データ基盤では、Indeedは収集元の一つに過ぎません。理想構成は次のようになります。

```
企業DB
        │
        ├── Indeed
        ├── Green
        ├── Wantedly
        ├── doda
        ├── マイナビ
        ├── PR TIMES
        ├── 官報
        ├── コーポレートサイト
        ├── 採用ページ
        ├── IR
        └── SNS
               │
               ▼
        EnterpriseOS
               │
        正規化・重複排除
               │
        AI分析
               │
        Sales Signal
               │
        Brand Intelligence
               │
        Hiring Intelligence
```

この構成にすると、「求人を集める」だけでなく、

- 採用人数の増減
- 新規事業への投資兆候
- 拠点拡大
- 技術スタックの変化
- 急成長企業の検知

といったシグナルを抽出でき、DealVaneの価値が大きく高まります。

そのため、EnterpriseOSの視点では、**求人クローラーはゴールではなく、企業インテリジェンス基盤を構成する複数のデータソースの一つ**として設計するのが最も拡張性の高いアプローチです。
