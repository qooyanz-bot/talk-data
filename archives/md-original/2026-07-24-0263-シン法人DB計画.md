| レイヤー | 主なデータ |
|----------|-----------|
| Level 1 | 求人票 |
| Level 2 | 企業基本情報 |
| Level 3 | Webサイト・サービス・商品・店舗情報 |
| Level 4 | プレスリリース・ニュース・SNS・IR・採用・ブログ |
| Level 5 | AIによる要約・分類・変化検知・営業シグナル・採用シグナル・企業プロフィール |

`migrations` は、データベースの**設計図（変更履歴）を管理する仕組み**です。

Cloudflare D1 はSQLiteベースなので、テーブルを作るSQLを直接実行することもできます。しかし、実際の開発では毎回手作業でSQLを打つのではなく、**「このプロジェクトのDBはどういう構造なのか」をファイルで管理**します。その役割を担うのが `migrations` フォルダです。

---

# migrationとは何か

例えば、最初に求人DBを作るとします。

最初の状態では何もありません。

```
D1 Database

(空)
```

そこで

```
companies
jobs
scrape_runs
```

を作ります。

そのSQLを

```
migrations/
    0001_init.sql
```

に保存します。

例えば

```sql
CREATE TABLE companies (...);

CREATE TABLE jobs (...);

CREATE TABLE scrape_runs (...);
```

です。

このSQLを

```
wrangler d1 migrations apply
```

で実行すると

```
D1

companies
jobs
scrape_runs
```

になります。

# bizDBで重要なのは「テーブルを増やす」より「スキーマを育てる」

`migrations` は、その**データベース設計の進化の履歴**を管理する仕組みです。

## bizDBで私が推奨する設計

現在の `0001_init.sql` は `companies`・`jobs`・`scrape_runs` の3テーブルですが、長期的には「機能単位」でマイグレーションを分けることを勧めます。

- `0001_init.sql` … 基本テーブル（companies・jobs）
- `0002_company_profile.sql` … 企業プロフィール拡張
- `0003_locations.sql` … 拠点情報
- `0004_contacts.sql` … 連絡先
- `0005_press_releases.sql` … プレスリリース
- `0006_products.sql` … 商品・サービス
- `0007_patents.sql` … 特許・知財
- `0008_financials.sql` … 財務・IR
- `0009_embeddings.sql` … ベクトル検索
- `0010_ai_signals.sql` … AIによる営業・採用シグナル

このように「ドメインごと」に分割しておくと、将来EnterpriseOSへ発展した際も、どの機能でどのDB変更が入ったかが明確になり、複数人や複数AIで開発する際にも管理しやすくなります。
