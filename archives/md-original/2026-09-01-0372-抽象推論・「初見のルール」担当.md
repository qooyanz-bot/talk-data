ARC向けには、モデルが直接グリッドを生成するのではなく、以下を実行します。

```text

→ Object Graph
→ Change Signature
→ Concept Address
→ Typed DSL Program
→ CPU Execution
→ Exact Verification
→ Output Grid
```

DSLには、物体抽出、回転、反転、移動、コピー、色変更、塗りつぶし、対称完成、拡大、反復、分割、結合、重力、線描画、カウント、並べ替え、条件分岐、経路生成を実装します。

ARC公式ガイドでも、離散プログラム探索、DSL合成、ニューラルモデルと記号推論の組み合わせが主要な方向性として説明されています。[ARC公式技術ガイド](https://arcprize.org/guide/1)

## アドレス理論の採用方法

テキスト推論：

```text
Address =
(domain, goal, unknown, entities, relations,
 scope, time, evidence, contradiction, output_type)
```

ARC推論：

```text
Address =
(background, object_selector, object_relation,
 invariant, geometry_op, color_op,
 canvas_op, composition_depth, verification_target)
```

Addressは答えを記憶する鍵ではなく、適切な推論器・DSL・メモリを選ぶルーティングキーとして使います。

色番号やタスクファイル名、ラベルを答えの意味として使うことは禁止します。

## 7. Cortext9開発原則

Cortext9は単一巨大モデルを作る計画ではありません。

Address理論を採用した超小型モデルを、必要能力まで機能分解して組み合わせるArchitectureです。

したがって、性能不足を単純なパラメータ増加だけで解決しないでください。

まず、

Goal\
→ 必要能力分解\
→ Address化\
→ 専門Tiny Model\
→ Router\
→ Executor\
→ Verifier\
→ 再推論/修正\
→ Answer

へ分解してください。

ただし、特定Tiny Modelについてパラメータ増加やGPU学習がシステム全体の性能向上に有効だと実験的に判断できる場合、必要なパラメータ数まで増やすことは許可します。

## 8. ベンチマーク原則

ベンチマーク専用hackは禁止です。

「AIME専用モデル」

ではなく、

「未知の数学問題を解く汎用数学推論モデル群」

を作ってください。

プログラミングbenchmarkなら、

「Terminal-Bench専用回答器」

ではなく、

「未知の実ソフトウェア開発・Terminal操作・debuggingを行える汎用Coding/Agentモデル群」

を作ってください。

性能値は推測値ではなく、正式benchmarkを実行した測定結果だけを確定値として報告してください。
