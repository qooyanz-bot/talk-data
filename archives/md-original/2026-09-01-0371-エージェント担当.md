## 2. Address理論による関数呼び出し表現

ツール名を直接覚えさせず、次のAddressへ変換します。

```json
{
  "domain": "calculation",
  "entity": "currency",
  "operation": "convert",
  "constraints": {
    "source": "USD",
    "target": "JPY",
    "amount": 100
  },
  "time": "current",
  "output": "converted_value",
  "side_effect": "none",
  "missing": [],
  "risk": "low",
  "tool_schema_fingerprint": "sha256:..."
}
```

Addressの構成要素は以下です。

- `domain`
- `entity`
- `operation`
- `relation`
- `constraints`
- `time`
- `output`
- `missing`
- `dependency`
- `side_effect`
- `risk`
- `schema_fingerprint`

この方式なら、ツール名を変更しても、

```text
currency_convert
convert_money
fx_exchange
```

を同じConcept Addressへ収束できます。

つまり「名前を暗記するモデル」ではなく、「目的と必要な関係からツールを検索するモデル」になります。

## 3. フロンティア級を目指す簡易ツール定義

ツールは単純でも、定義は厳密にします。

### 共通仕様

```json
{
  "name": "tool.name",
  "description": "One action only. Explicitly defines limits, units, defaults, and side effects.",
  "side_effect": "none",
  "requires_confirmation": false,
  "parameters": {
    "type": "object",
    "additionalProperties": false
  },
  "returns": {
    "type": "object"
  },
  "errors": [
    "INVALID_ARGUMENT",
    "MISSING_ARGUMENT",
    "NOT_FOUND",
    "EXECUTION_FAILED"
  ]
}
```

重要なのは、説明文に曖昧な表現を残さないことです。

- 「適切に」
- 「必要なら」
- 「近いもの」
- 「最近」
- 「通常」
- 「可能な場合」

のような曖昧語は、必ず定義へ変換します。

## 4. 100点用のテスト構成

独自ベンチマークを `CIVA-FC-100` として作ります。

| テスト群 | 内容 |
|---|---|
| Single Call | 1ツールを正確に呼び出す |
| Parallel Call | 独立した2〜4ツールを並列実行 |
| Sequential Call | 前の結果を次の引数へ接続 |
| Canonicalization | 日時、単位、通貨、表記ゆれ |
| Missing Argument | 不足情報を質問 |
| Ambiguity | 複数候補から勝手に決めず確認 |
| No-Tool | ツールが不要な依頼を拒否 |
| Missing Tool | 利用可能ツールにない要求を説明 |
| Error Recovery | 不正引数、Not Found、実行失敗から復旧 |
| State Dependency | 前ターンの状態を保持 |
| Safety Gate | 作成・更新・送信前に確認 |
| Schema Holdout | 未知のツール名・未見のスキーマ |

100点の判定は平均点ではなく、ケース単位の完全合格にします。

```text
case_pass =
  valid_json
  AND correct_tool
  AND exact_arguments
  AND correct_order
  AND correct_state
  AND correct_confirmation
  AND correct_final_response
```

最低条件は次の通りです。

- 1,200ケース以上
- 5 seed
- 20%以上を完全未見のツールスキーマ
- ツール名のランダム変更
- ツール定義順序の変更
- 類似ツールの同時提示
- 日本語・英語・混在入力
- Goldラベルを入力へ含めない
- 学習・検証・Holdoutの重複禁止

BFCLだけでなく、状態依存・不足情報・正規化が難所になるToolSandboxにも合わせます。[Apple ToolSandbox](https://github.com/apple/ToolSandbox) また、ポリシー・ツール・タスクを組み合わせた対話評価はτ-bench系の設計とも整合します。[τ²-bench](https://github.com/sierra-research/tau2-bench)

## 5. 学習方法

学習データは、ツール名と正解ラベルを直接覚えさせない構成にします。

1. ツールスキーマを自動生成  
2. フロンティアモデルを教師として、多様な依頼文を作成  
3. Address、引数、質問、実行順序を別々に教師信号化  
4. ツール名・説明・順番をランダム変換  
5. 反例ツールを追加  
6. エラー結果から復旧データを生成  
7. 未見スキーマでHoldout評価  

特に重要なのは、以下の反ショートカット試験です。

```text
tool name rename
description paraphrase
argument reorder
schema reorder
distractor injection
language switch
unit format switch
date format switch
irrelevant tool addition
```

これを通過して初めて、ラベル暗記ではなく関数呼び出し能力のEvidenceと認定します。

## 6. 目標性能

現実的な目標は三段階です。

- `CIVA-FC-Core`: 1ツール・明示引数で100%
- `CIVA-FC-Advanced`: 複数ツール、曖昧性、エラー復旧込みで100%
- `External Frontier Track`: BFCL、ToolSandbox、τ-benchで比較

CIVA独自ベンチマークで100点を取ることと、BFCL全体で100点を取ることは別です。外部ベンチマークの100点は、現在のフロンティアモデルでも容易ではないため、まずは「未見スキーマを含むCIVA-FC-Advancedで5 seed・全ケース完全合格」を最初の投資家向け証拠にするべきです。

ドラえもんで言えば、単に「道具の名前を言える」状態ではなく、

「依頼に合う道具を選び、足りない条件を聞き、危険な道具には確認を取り、使った結果を検査し、失敗したら別の道具へ切り替える」

## 提案するCIVA tiny-orchestra

前回の2,056-param Address routerはルーティングヘッドとして再利用します。ただし、前回の合成1,150ケース100%は外部ベンチマークの推論証拠ではなく、現在のclaim statusは`structural_evidence_partial`です。

| 専門モデル | 初期規模 | 役割 |
|---|---:|---|
| `AddressRouter` | 0.01–1M | Web、GUI、Terminal、Science、長期状態、危険操作を分類 |

## ベンチマーク別の重点開発順

1. **WebArena-Verified**  
   DOM・フォーム・状態遷移と決定論的検証の組み合わせが、超小型モデルに最も適しています。

2. **BrowseComp**  
   検索語生成を複数の小型モデルで並列化し、証拠グラフと回答検証器で統合します。公式採点器とは別に、引用証拠・再検索一致率も記録します。

3. **OSWorld 2.0**  
   Screenshot＋Accessibility tree＋イベント監視を統合します。長期状態の定期checkpoint、差分検証、途中の clarification を中核にします。

4. **Terminal-Bench**  
   `run → test → inspect → patch → rerun`の閉ループを決定論的に実装します。小型モデルには自由なコード生成より、環境インベントリ、既知レシピ、最小パッチ探索を担当させます。

5. **Agents’ Last Exam / Terminal-Bench-Science**  
   業務・科学領域の専門知識を小型モデルへ詰め込むのではなく、証拠付きレシピ、単位・次元検査、再現可能な実行、成果物検証に分解します。ここは最終到達目標であり、最初から満点を予測しません。

## 提案する汎用システム

名称は仮に、`CIVA General Software Work Orchestra`とします。

### 1. Universal Address Compiler

自然言語の依頼を、以下のAddressに変換します。

```json
{
  "goal": "implement|fix|refactor|test|explain|research",
  "artifact": "repository|file|module|symbol|environment",
  "relation": "depends_on|calls|implements|fails_at|produces",
  "scope": "string",
  "time": "before_change|after_change|regression",
  "constraints": ["string"],
  "evidence": ["user_request|spec|test|log|document"],
  "authority": ["string"],
  "risk": "low|medium|high",
  "confidence": "number",
  "verification_status": "unverified"
}
```

Addressは単なるラベルではなく、「何を、どの範囲で、何の証拠に基づいて、どのように変更するか」を指定する構造体です。

### 2. 超小型専門モデル群

1つの巨大モデルではなく、機能単位に分割します。パラメータ数は事前に固定せず、各能力に必要な最小十分量を試験で決めます。

| モデル | 役割 |
|---|---|
| `IntentCompiler` | 依頼をGoal・制約・成果物へ分解 |
| `AddressComposer` | 概念・ファイル・関数・依存関係をAddress化 |
| `RepositoryMapper` | AST、シンボル、import、呼び出し関係を構造化 |
| `EvidenceBinder` | 要件、仕様、ログ、テストを出典付きで結合 |
| `WorkGraphPlanner` | 作業を依存関係付きDAGへ変換 |
| `PatchSynthesizer` | 最小変更のコード・設定・テストを生成 |
| `EnvironmentMapper` | OS、言語、依存パッケージ、実行条件を確認 |
| `FailureClassifier` | compile、test、runtime、logic、environment等を分類 |
| `RepairPlanner` | 失敗原因から修復手順を生成 |
| `Verifier` | テスト、型、静的解析、差分、成果物を検証 |
| `SafetyAbstainer` | 不明・矛盾・危険操作を停止または質問 |
| `ResponseCompiler` | 実行結果と証拠を人間向けに報告 |

モデルのサイズを大きくすることは最後の手段とし、まずAddress、構造解析、決定論的実行、検証器で能力を補います。
