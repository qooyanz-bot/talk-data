# R6-C — Concept Address vs Value Reconstruction

## 1. Research Question

巨大なValue空間そのものを探索する代わりに、

**State / Context / Object metadata → Concept Address → Value**

という経路によって、対象Valueへ到達できる条件を検証する。

中心仮説：

> Concept Addressを一意に解決できる場合、Valueそのものを巨大空間から探索する必要はない。ただし、ValueまたはValueを再構成するための情報がAccessible State内に存在することを必要条件とする。

完全Synthetic Worldのみ使用する。

実在する暗号鍵、ウォレット、秘密鍵、API key、認証情報、credential datasetは一切使用しない。

---

# 2. Core Distinction

R6-Cでは以下を別の問題として扱う。

### Address Resolution

Concept Addressから対象objectを一意に特定できるか。

\[
A \rightarrow O
\]

### Value Reconstruction

対象objectに対応するValueを取得または再構成できるか。

\[
(A, AccessibleState) \rightarrow V
\]

重要：

\[
Address\ Uniqueness \neq Value\ Information
\]

Concept Addressがobjectを完全に特定しても、そのAddressにValueに関する情報が含まれているとは限らない。

# 4. Condition A — STORED

ValueをDB内に保存する。

```text
Concept Address
      ↓
Address Resolution
      ↓
Object
      ↓
stored value
```

SolverはConcept AddressからValueをlookupする。

## Expected Result

Addressがuniqueなら、

```text
Exact Value Recovery ≈ 1.0
```

であるべき。

これは、

**巨大Value空間を探索せずAddressingによってValueへ到達可能**

である証拠になる。

ただしValueを「生成した」ことにはならない。

---

# 5. Condition B — RULE-GENERATED

Value本体をDBへ保存しない。

代わりに生成規則を保存する。

```text
Concept Address
      ↓
rule lookup
      ↓
rule(parameters)
      ↓
Value
```

例：

```text
V = deterministic_rule(
    object_id,
    object_type,
    context,
    rule_parameters
)
```

Ruleは完全にdeterministicでなければならない。

Solverへ渡されるもの：

```text
Concept metadata
Rule database
Required public rule parameters
```

Solverへ直接Valueを渡してはならない。

## Expected Result

Ruleが正しくaddressableなら、

```text
Exact Value Recovery ≈ 1.0
```

となる。

これは、

**Value本体を保存しなくても、そのValueを決定する十分な情報をAddress可能なら再構成可能**

という証拠になる。

---

# 6. Condition C — RANDOM-UNSTORED

最重要Negative Control。

Generatorのみが各objectへ独立ランダムValueを割り当てる。

\[
V_i \sim Uniform(\{0,1\}^L)
\]

Solver / DBには以下を一切渡さない。

```text
value
seed
PRNG state
generation rule
value hash table
reverse lookup table
encrypted copy
compressed representation
derived representation sufficient for reconstruction
```

Solverへ渡すものはConcept metadataのみ。

```text
Concept Address
```

でobjectのidentity自体は特定できてもよい。

しかしValueを決定する情報はAccessible Stateに存在しない。

---

# 7. Critical Prediction for C

Value長をL bitとすると、完全独立なuniform random Valueに対する最良のexact推測確率は、

\[
P(\hat V = V)=2^{-L}
\]

256-bitなら、

\[
2^{-256}
\]

である。

したがって通常の情報理論ではConcept AddressだけからValueを復元できない。

Cで有意な復元が発生した場合は、まず新原理ではなく、

**Leakage / implementation bug / deterministic generator contamination**

を最優先仮説とする。

---

# 10. Candidate-space Reduction

Object検索空間について、

\[
CSR_{object}
=
1-\frac{|C_{final}|}{|C_{initial}|}
\]

Value空間については別に記録する。

これを混同してはいけない。

例えばCでは、

```text
Object candidates:
100,000 → 1

Value candidates:
2^256 → 2^256
```

が成立し得る。

これはR6-Cの非常に重要な結果になる。

つまり、

**対象objectの不確実性をゼロにしてもValueの不確実性は残る。**

# 11. Information Metrics

最低：

\[
I(A;V)
\]

Concept Address A と Value V のmutual informationを測定する。

ただしさらに重要なのは、

\[
I(V;AccessibleState \mid A)
\]

である。

### A — STORED

Concept Address自体とrandom Valueの統計的MIはほぼ0でもよい。

DB mappingが情報を保持しているため、

```text
A + DB state
```

からVを取得できる。

### B — RULE-GENERATED

RuleおよびparametersがVを決定するので、

```text
A + rule state
```

### C — RANDOM-UNSTORED

設計上、

\[
I(A;V)\approx0
\]

かつ、

\[
I(AccessibleState;V \mid A)\approx0
\]

でなければならない。

# 12. Critical Leakage Audit

Cは独立auditを実施する。

## 12.1 Value Leakage

DB / serialized files / logs / cache / metricsにValueそのものまたは部分列が存在しないか。

---

## 12.2 Seed Leakage

Generator seedがSolver accessible stateへ渡っていないか。

---

## 12.3 PRNG State Leakage

PRNG内部state、state snapshot、next-state情報が存在しないか。

Generator processとSolver processを物理的に分離することを推奨。

---

## 12.4 Object ID Encoding

object_idがValue生成に使用されていないこと。

Cでは、

```text
Value = f(object_id)
```

は禁止。

Value assignmentは独立random samplingとする。

---

## 12.5 Ordering Leakage

object生成順序とPRNG sequenceからValueを推測できないこと。

Solverへgenerator orderingを渡さない。

Datasetのobject orderは生成後に独立shuffleする。

---

## 12.6 Hash Lookup Leakage

Value hash、checksum、Bloom filter等が候補Value判定oracleとして利用できないこと。

CではValue由来fingerprintをSolverへ一切渡さない。

---

## 12.7 Generator-family Leakage

Valueに、

```text
prefix
format
length variation
character bias
template
class-dependent distribution
```

などConcept metadataと相関する特徴を入れない。

Primary Cでは全object同一uniform distributionを使用する。

> Concept Addressは巨大な対象空間から必要な情報へ到達する探索コストを大幅に削減できる。しかしAddressそのものが未知情報を生成しているわけではない。Value本体またはValueを決定するrule/structureがAccessible State内に存在するときにのみValueへ到達できる。

\[
P(\hat V=V)=2^{-256}
\]

# 19. C Leakage Audit — Mandatory Checks

Cについて最低7カテゴリーを全部PASSしなければならない。

## L1 Value Leakage

Solver View内にground truth Valueまたは完全一致substringが存在しない。

## L2 Seed Leakage

seed identifierだけでなくseed valueも検索。

禁止：

```text

rng_seed
random_seed
master_seed
```

等。

ただし単なるfield-name検索だけでは不十分。

Generator manifestとのbyte-level比較も行う。

---

## L3 PRNG State Leakage

Python random / NumPy / custom RNG stateのserializationを禁止。

---

## L4 Object-ID Encoding

統計検査：

\[
I(ObjectID;V)
\]

およびmetadata各dimensionとの依存性を検査。

---

## L5 Ordering Leakage

生成順とValue sequenceの対応をSolverへ渡さない。

Solver View export前に別RNGによるshuffleを行う。

このshuffle seedもValue生成seedとは完全分離。

## L6 Hash Oracle Leakage

以下禁止：

```text
SHA256(value)
MD5(value)
CRC(value)
checksum
Bloom membership
value prefix
value suffix
```

候補判定oracleになる情報もLeakageとして扱う。

---

## L7 Generator-family Leakage

metadata subsetごとのValue distributionに偏りがないか確認。

Primary Cでは、

\[
P(V|metadata)=P(V)
\]

が設計上成立すること。
