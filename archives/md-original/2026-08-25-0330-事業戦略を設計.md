# 1. Wikidata + Wikipedia + 学術APIの骨格

私は最初の骨格をこうします。

| Layer | データ源 | 役割 | 800kq側で保持 |
|---|---|---|---|
| Entity | Wikidata | 人・企業・製品・疾患・技術等のID統一 | QID、名称、alias、type、relation |
| Description | Wikipedia | Entityの意味・別名・概要 | paragraph/source/revision |
| Academic graph | OpenAlex | 論文・著者・機関・研究分野 | DOI/OpenAlex ID/citation/topic |
| DOI metadata | Crossref | DOI・出版社・訂正・撤回等 | DOI/date/license/relation |
| Claims | 独自生成 | 「AはBである」という原子的知識 | subject/predicate/object/evidence |
| Freshness | SERP/Web/API | 現在値・ニュース・価格・役職等 | valid_from/valid_to/observed_at |

Wikidataは全データのJSON/RDF dumpを提供しているため、基本的にはAPIを大量に叩くのではなく**dump→ローカル正規化**が正解です。JSON dumpは公式にも推奨されています。citeturn449017search9

学術分野ではOpenAlexがかなり800kq向きです。現在、OpenAlexは作品・著者・機関・出版元・トピックなどを結んだ巨大なKnowledge Graphを提供しており、全体snapshotは無料、四半期更新です。さらにAPIも無料枠があります。citeturn732154search3turn732154search4

しかも2026年8月時点でOpenAlexは約3.24億件のcore worksをAPI対象としており、singleton取得は無料、filterは$0.10/1,000 calls、searchは$1/1,000 callsです。citeturn732154search8turn732154search1

Crossrefもかなり重要です。Crossrefは論文本文ではなく、DOI、出版社、ライセンス、funding、ORCID、ROR、訂正・撤回などのメタデータを持っています。大半のメタデータは自由利用可能で、年次bulk dumpも提供されています。citeturn449017search0turn449017search2

# 2. Claim Graphは「文章DB」にしない

ここが800kqの技術的なコアになります。

例えばWikipediaに、

> Toyota launched the Prius in 1997.

という文章があるとして、その文章自体を主データにしません。

内部表現を、

```text
subject: Toyota Prius
predicate: first_launched
object: 1997
```

とします。

さらに証拠を別テーブル化します。

```text
claim_id
subject_entity_id
predicate_id
object_entity_id / literal_value

valid_from
valid_to
observed_at

confidence
consensus_score
freshness_score

source_count
contradiction_count
```

Evidence側は、

```text
evidence_id
claim_id

source_url
publisher
published_at
retrieved_at

source_type
license
language

quote_hash
content_hash

support_type
support_score
```

です。

非常に重要なのは、

**Claim ≠ Evidence**

とすることです。

同一Claimに、

```text
Wikipedia
Toyota公式
Reuters
論文
政府資料
```

という5本のEvidenceがぶら下がります。

すると800kqは単なるRAG corpusではなくなります。

```text
Entity
   ↓
Claim
   ↓
Evidence[]
   ↓
Source
```

というEvidence Graphになります。

そして反対意見も消してはいけません。

```text
Claim A
Toyota sold X vehicles in 2025

SUPPORT
 ├─ Toyota IR
 └─ Reuters

CONTRADICT
 └─ third-party estimate
```

という構造を残します。

これはLLM会社に対して非常に強い。

**「我々のDBには答えではなく、答えを組み立てるための検証可能な証拠グラフが入っています」**

と言えるからです。

# ヒット率60%の定義を変える

現在の、

> 自社データだけで答えられた割合

だけでは弱いです。

簡単な質問ばかり集めれば90%にできてしまうからです。

最低でも4指標にします。

| KPI | 定義 |
|---|---|
| Coverage Rate | 必要情報がDBに存在 |
| Answerable Rate | 外部検索なしで回答生成可能 |
| Evidence Rate | 回答中の主張をEvidenceで支持可能 |
| Freshness Pass Rate | 時点依存質問で必要鮮度を満たす |

そして最終指標を、

### Verified Answer Rate

にします。

例えば、

```text
VAR =
Answerable
× CitationCorrect
× FreshEnough
× NoCriticalContradiction
```

とします。

これなら営業資料で非常に強い。

単に、

> Hit Rate 72%

ではなく、

> 10万件の実ユーザークエリに対し、
> 72.4%を外部Web accessなしで回答。
> そのうち96.1%の主要主張に出典あり。

という数字になります。
