````
この内容は、**「Indeedを企業DB・求人DBとして長期運用できるスクレイピング基盤」**を作るための重要な設計になっています。単にHTMLを取得するのではなく、**数百万～数千万件規模でも運用できるアーキテクチャ**です。

# ① observation先行INSERT＋最新値UPSERT

これが一番重要です。

普通のスクレイパーは

```
求人を取得
↓
求人テーブル更新
```

だけです。

しかしこれでは

- 前回何が取得できたか
- HTTPだったかBrowserだったか
- 403だったか
- Cloudflareだったか
- HTMLサイズ
- 通信量

などが全部消えます。

そこで

```
取得

↓

ObservationテーブルへINSERT

↓

求人テーブル更新

↓

企業テーブル更新

↓

ObservationIDを保存
```

になります。

つまり

```
indeed_fetch_observations

id=1020
取得時刻
transport=browser
status=200
通信量=55KB
proxy=dataimpulse
取得時間
```

これをまず保存。

そのあと

```
indeed_jobs

latest_observation_id=1020
```

にします。

すると

いつ取得した求人なのか

が100%追跡できます。

これは企業DBではかなり重要です。

Indeed検索結果

東京都

25件
```

取得できる情報は

```

会社名

勤務地

```

つまり

```
詳細取得済み

ではない
```

だから

```
stub
```

になります。

---

検索結果内に

右側へ展開される詳細

があります。

ここでは

```

勤務地

福利厚生

```

などが取得できます。

でも

まだ全部ではありません。

これが

```
partial
```

---

viewjob

へアクセスすると

```

掲載日

JSON-LD

本文

全属性
```

まで取れます。

```
complete
```

です。

つまり

```

↓

partial

↓

complete
```

という品質管理をしています。

これをしないと

「詳細取得済み」

と思っていた求人が

実は

検索結果だけ

という事故が起きます。

## EnterpriseOS全体で見ると

あなたが目指しているEnterpriseOSでは、このIndeedスクレイパーは単独で完結するものではありません。約500万社規模の企業DBへ「求人シグナル」を供給するデータ収集エージェントの1つです。memcite

理想的な全体像は次のようになります。

```text
Indeed Bot (10並列)
        │
        ▼
Observation
（取得ログ・品質）
        │
        ▼
Writer
（同一トランザクション）
        │
        ├── indeed_jobs
        ├── indeed_employers
        ├── 履歴テーブル
        └── 欠損率・品質統計
                │
                ▼
EnterpriseOS Company DB
（500万社企業マスター）
                │
                ▼
Hiring Intelligence
Sales Intelligence
AI Research Agent
```

この構成にしておくと、Indeedだけでなく、求人ボックス、Green、Wantedly、各社採用ページなども同じObservation→Writer→企業DBというパイプラインへ追加できるため、運用と保守が大幅に楽になります。memcite
````
