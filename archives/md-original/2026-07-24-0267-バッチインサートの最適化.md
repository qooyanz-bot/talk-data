「**バッチインサート（Batch Insert）**」は、このシステムではかなり重要です。

ただし、「大量データを一気にINSERTする」という意味だけではなく、**Cloudflare D1(SQLite)の特性に合わせた設計**がポイントです。

---

# なぜ必要なのか

例えば求人を1000件取得したとします。

## 悪い例

取得するたびに

```sql
INSERT INTO jobs ...
```

を1000回実行します。

```
Worker1
 INSERT

Worker2
 INSERT

Worker3
 INSERT

Worker4
 INSERT
```

全員が同時に書き込みます。

SQLiteは

```
同時書き込みが苦手
```

です。

そのため

```
SQLITE_BUSY

database is locked
```

が発生します。

---

# 良い例

100件集めて

```
INSERT
INSERT
INSERT
...
100件
```

を

**1トランザクション**

で流します。

```
BEGIN

100件

COMMIT
```

これだけです。

---

# Cloudflare D1ではさらに重要

D1はSQLiteです。

つまり

```
書き込みは高速

でも

大量の同時書き込みには弱い
```

という特徴があります。

例えば

100 Worker

↓

全員が

```
INSERT
```

すると

```
100回ロック
```

になります。

---

一方

Workerが

```
100件取得

↓

batch()

↓

COMMIT
```

なら

```
ロック1回
```

になります。

---

# イメージ

悪い例

```
Worker A

INSERT

INSERT

INSERT

INSERT

INSERT



Worker B

INSERT

INSERT

INSERT

INSERT
```

ロック祭りになります。

---

良い例

```
Worker A

100件

↓

batch()

↓

COMMIT



Worker B

100件

↓

batch()

↓

COMMIT
```

ロック回数が激減します。

---

# Cloudflare Queueと組み合わせる

理想形は

```
Crawler

↓

Queue

↓

Consumer

↓

100件ためる

↓

batch()

↓

D1
```

です。

つまり

```
取得

↓

Queue

↓

整列

↓

まとめて保存
```

です。

---

# db.batch()とは

Cloudflare D1には

```ts
db.batch([
  stmt1,
  stmt2,
  stmt3,
])
```

があります。

例えば

```ts
await env.DB.batch([
    env.DB.prepare(
      "INSERT INTO jobs(title) VALUES (?)"
    ).bind("A"),

    env.DB.prepare(
      "INSERT INTO jobs(title) VALUES (?)"
    ).bind("B"),

    env.DB.prepare(
      "INSERT INTO jobs(title) VALUES (?)"
    ).bind("C"),
]);
```

一度の呼び出しでまとめて処理できます。

---

# もっと高速な方法は？

実はあります。

SQLiteには

```sql
INSERT INTO jobs
VALUES
(...),
(...),
(...),
(...),
(...);
```

という**マルチバリューINSERT**があります。

例えば

```sql
INSERT INTO jobs
(title,url)

VALUES

('A','a'),

('B','b'),

('C','c');
```

これは

100回INSERTするより

かなり高速です。

---

# EnterpriseOSなら私が採用する設計

500万社DB＋1800サイト規模なら、私は以下のパイプラインにします。

```text
Workers

↓

Queue

↓

Consumer

↓

JSON配列

↓

重複チェック

↓

100〜500件ごとにまとめる

↓

Multi Value INSERT

↓

db.batch()

↓

D1
```

さらに、

- URLや企業番号で重複排除
- 変更がないデータはINSERTしない
- 更新分だけUPSERTする

ことで、D1への書き込み量自体も減らせます。

---

## あなたのプロジェクトで気になる点

一つだけ補足すると、**D1を更新頻度の高いデータベースとして使い続ける設計は慎重に検証すべき**です。

EnterpriseOSでは数百万社に対して、求人・企業情報・プレスリリースなどが継続的に更新されます。もし毎日大量のUPSERTが発生するなら、D1は「インデックス・検索用メタデータ」に限定し、更新ログや生データはR2や別のストレージに寄せる構成の方がスケールしやすい可能性があります。

つまり、**バッチインサートは必須ですが、それ以前に「D1へ何を書き込むべきか」を明確に分離すること**が、長期運用ではさらに重要な設計ポイントになります。
