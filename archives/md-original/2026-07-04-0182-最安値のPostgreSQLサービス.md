結論：**Cloudflare Pagesに全企業分のHTMLを置く構想は不適です。**  
無料Pagesは**1サイト20,000ファイル上限**なので、全日本企業ページは即破綻します。Cloudflare Pages自体は無料で、500 builds/月・静的リクエスト/帯域は無制限ですが、ファイル数制限が致命的です。citeturn385945search0turn385945search1

## 最適構想

**静的HTMLを大量生成しない。**  
代わりに、URLは静的ページ風にして、Cloudflare WorkerがデータからHTMLを返す構成にします。

```txt
国税庁法人番号API / gBizINFO
        ↓ 毎日差分取得
GitHub Actions または Cloudflare Cron Worker
        ↓
Cloudflare R2：企業JSON保存
Cloudflare D1：法人番号・社名・都道府県など検索インデックス
        ↓
Cloudflare Worker
        ↓
/companies/法人番号
/companies/都道府県/会社名
```

| 拡張情報 | gBizINFO | 基本情報、届出、表彰、財務、特許、調達、補助金、職場情報などをAPI/CSV/JSONで取得可能。citeturn763319search0turn763319search1 |

## 専用エージェントは何を使うべきか

**AIエージェントは不要です。**  
これはLLMに判断させる仕事ではなく、**定期ETL**です。

無料候補は：

1. **GitHub Actions**
   - public repoなら無料
   - Python/Nodeで毎日差分取得
   - R2/D1へ反映

2. **Cloudflare Cron Triggers**
   - Workerを定期実行
   - 小規模差分なら無料枠で可能
   - ただし大量処理には不向き

3. **自宅PC + Task Scheduler**
   - 完全無料
   - 安定性は低い
   - 初期データ投入だけならあり

## 現実的な設計

**初回投入**
- 国税庁のダウンロードデータ、gBizINFOのCSV/JSONを取得
- 法人番号ごとにJSON化
- R2に保存
- D1には検索用の最小項目だけ入れる

**毎日更新**
- 国税庁APIの「取得期間指定」で変更差分を取得
- gBizINFOの更新分を取得
- 変更があった法人だけR2 JSONを更新
- D1の検索インデックスも更新

**表示**
- `/companies/1234567890123`
- WorkerがD1で法人番号確認
- R2からJSON取得
- HTMLテンプレートに流し込んで返す
- Cache APIで24時間キャッシュ

# 2. 厳しめの前提整理

## やってはいけないこと

**全法人に対して毎日AI要約を生成する設計は、無料では無理です。**

Cloudflare Workers AIには無料割当がありますが、無料枠は10,000 Neurons/dayで、それを超えるとWorkers Paid上で従量課金になります。つまり、全法人を毎日LLM処理する前提は破綻します。citeturn176809view0

正しい設計はこれです。

```txt
全企業：
  ルールベースで差分検知・構造化

重要企業 / 変更企業 / アクセスされた企業：
  AI要約

高価値ユーザー向け：
  深いAI分析
```

AIは全件バッチではなく、**差分・需要・重要度で絞って使う**べきです。

# 3. MVPの範囲

MVPでは、最初から「全企業を深く分析」しないほうがいいです。  
最初に作るべきは、**全法人の基本ページ + 毎日差分更新 + 一部企業のAI要約**です。

| 区分 | 機能 | MVP採用 |
|---|---|---:|

| 基本情報 | 商号、所在地、法人番号、状態、変更日 | 必須 |
| 変更履歴 | 社名変更、住所変更、閉鎖、新規指定 | 必須 |
| 検索 | 法人番号、社名、都道府県、市区町村 | 必須 |
| 更新表示 | 最終更新日、データソース、差分理由 | 必須 |
| AI要約 | 変更があった企業だけ短文要約 | 必須 |
| gBizINFO連携 | 補助金、調達、特許、認定、財務等 | MVP後半 |
| EDINET連携 | 上場企業の開示情報 | MVP後半 |
| 企業公式サイト巡回 | 公式サイトのニュース・採用情報 | 後回し |
| ユーザー登録 | お気に入り、通知、APIキー | 後回し |
| 課金 | 有料API、ウォッチリスト | 後回し |

## MVPでやらないこと

- 全企業のAI深掘り分析
- 全企業の公式サイトクロール
- SNS全量監視
- 人材・採用データの全量収集
- 企業スコアリングの自動断定
- 営業リスト販売機能

ここを欲張ると、確実に完成が遅くなります。  
MVPの目的は、**更新パイプラインが毎日壊れず回ることの証明**です。

# 4. データソース設計

## P0：必須データソース

### 1. 国税庁法人番号公表サイト

国税庁法人番号公表サイトでは、法人番号、商号または名称、本店または主たる事務所所在地の基本3情報を取得できます。citeturn280399search13

初回投入はWeb APIではなく、**全件データのダウンロード**を使います。国税庁のWeb APIは期間指定や法人番号指定には使えますが、APIでは全件データを取得できないと明記されています。citeturn155430view0

日次更新は、国税庁Web APIの期間指定取得を使います。指定期間内の法人番号指定、商号・所在地変更、登記記録閉鎖等を取得でき、取得期間は最大50日です。citeturn155430view0

注意点として、Web APIにはアプリケーションIDが必要で、発行費用はかかりませんが、発行に2週間から1か月程度かかる場合があります。citeturn155430view0

### 2. gBizINFO

gBizINFOはREST APIで法人情報を取得でき、法人基本情報、届出・認定、表彰、財務、特許、調達、補助金、職場情報を提供しています。citeturn965165view0

また、法人基本情報や法人活動情報をCSV、PDF、JSON形式でダウンロードできます。citeturn738252view5

ただし、gBizINFOのAPI利用には事前申請とAPIトークンが必要です。citeturn965165view0

## P1：拡張データソース

### 3. EDINET

上場企業や有価証券報告書提出企業については、EDINET APIを使います。EDINET APIの利用には登録とAPIキー発行が必要です。citeturn970017view0

MVPでは全企業に使うのではなく、**上場企業・有報提出企業だけ**を対象にします。

### 4. e-Stat

地域統計や業種統計を企業ページに補助情報として載せる場合、e-Stat APIが候補です。e-Stat APIはユーザー登録とアプリケーションID取得が必要です。citeturn970017view2

e-Stat FAQでは、APIリクエスト使用回数について「現在のところ、ございません」とされています。citeturn970017view3

### 5. 企業公式サイト

これはMVPでは後回しです。  
公式サイトの巡回はコスト・法務・robots.txt・重複排除・本文抽出・誤検知が絡むため、最初から入れると重くなります。

## 全体アーキテクチャ

```txt
[国税庁 全件データ / 差分API]
[ gBizINFO API / Download ]
[ EDINET API ]
[ e-Stat API ]
        ↓
[Ingestion Agent]
GitHub Actions / Cloudflare Cron
        ↓
[Raw Data Lake]
Cloudflare R2
        ↓
[Normalizer / Diff Engine]
Cloudflare Workers + Queues
        ↓
[Search / Index]
Cloudflare D1
        ↓
[Company JSON]
Cloudflare R2
        ↓
[Page Renderer]
Cloudflare Workers
        ↓
[HTML / JSON / Sitemap]

```

## 採用サービス

| 役割 | 採用 | 理由 |
|---|---|---|
| ページ配信 | Cloudflare Workers Paid | 企業数制限ではなく、リクエスト・CPU課金で扱える |
| データ本体 | Cloudflare R2 | JSON、Rawデータ、スナップショット保存に向く |
| 検索・索引 | Cloudflare D1 | 法人番号、社名、住所、更新状態の検索用 |
| 非同期更新 | Cloudflare Queues | 差分更新ジョブを安全に分散処理 |
| 定期実行 | Cloudflare Cron + GitHub Actions | Cronは起動、GitHub Actionsは重いETL |
| AI要約 | Workers AI or 外部LLM | 変更企業だけ選択的に実行 |
| AIコスト制御 | Cloudflare AI Gateway | キャッシュ、レート制御、分析に使える |

Workers Paidは月額$5の最低料金で、10 million requests/month、30 million CPU milliseconds/monthが含まれ、追加リクエストは$0.30/million、追加CPUは$0.02/million CPU millisecondsです。citeturn738252view0

R2は10GB-month、Class A 1 million requests/month、Class B 10 million requests/monthまで無料で、標準ストレージは超過分$0.015/GB-monthです。citeturn738252view1

D1はWorkers Paidで最大10GB/database、アカウント合計1TBまで対応し、Rows readは月25 billionまで、Rows writtenは月50 millionまで含まれます。citeturn738252view3turn229501view0

QueuesはWorkers Paidで1 million operations/monthが含まれ、超過は$0.40/million operationsです。通常は1メッセージの配信にwrite/read/deleteの3 operationsがかかります。citeturn248078view0

D1には全文データを詰め込みません。

社名や所在地をURLに入れると、社名変更・移転時にURLが壊れます。  
SEO用の見た目URLを作る場合も、canonicalは法人番号URLに寄せます。

## 企業ページの構成

```txt
H1：株式会社サンプルの企業情報

1. 基本情報
   - 法人番号
   - 商号
   - 所在地
   - 法人状態
   - 最終更新日

2. 最近の変更
   - 住所変更
   - 社名変更
   - 閉鎖
   - 新規指定

3. AI要約
   - 最近何が変わったか
   - 注意すべき公的イベント

4. 公的活動情報
   - 補助金
   - 調達
   - 特許
   - 届出・認定
   - 表彰
   - 財務
   - 職場情報

5. データソース
   - 国税庁
   - gBizINFO
   - EDINET
   - e-Stat

6. 更新履歴
   - いつ
   - どのソースから
   - 何が変わったか
```

## SEO上の注意

ここはかなり重要です。  
全法人ページを作るだけだと、Googleから「大量生成された低価値ページ」と見られるリスクがあります。Googleは、検索順位操作を主目的とした大量・低独自性ページをscaled content abuseとして扱います。citeturn888073search0

したがって、MVPでは以下のルールを入れます。

```txt
情報が薄い企業ページ：
  noindex または低優先度 sitemap

更新履歴がある企業：
  index対象

gBizINFO / EDINET / 補助金 / 調達 / 特許などがある企業：
  優先index

AI要約だけの水増し：
  禁止

ソース・更新日時・変更理由：
  必ず表示
```

SEO目的でページを量産するのではなく、**「変更履歴とソース付き企業ナレッジ」として価値を作る**べきです。

# 8. 更新パイプライン設計

## 初回投入

```txt
1. 国税庁 全件データを都道府県単位で取得
2. R2 raw/nta/full/ に保存
3. ストリーミングパース
4. companiesテーブルへupsert
5. company/{法人番号}.json をR2へ保存
6. sitemap shard生成
7. 検索インデックス生成
8. update_runsに結果保存
```

国税庁の全件ダウンロードは全国・都道府県・国外単位で提供されており、たとえばXML形式・Unicodeの全国ファイルは2026年6月30日更新時点でzip 360MBです。citeturn848401view1

## 毎日更新

```txt
Cloudflare Cron / GitHub Actions
        ↓
NTA差分API取得
        ↓
Raw差分をR2保存
        ↓
Diff Engine
        ↓
変更法人番号をQueueへ投入
        ↓
Queue Consumer
        ↓
R2 company JSON更新
        ↓
D1 index更新
        ↓
必要ならAI要約
        ↓
キャッシュ削除 / sitemap更新
```

## 差分更新の処理ルール

```txt
event_type:
  - created
  - name_changed
  - address_changed
  - status_changed
  - closed
  - gbiz_activity_added
  - edinet_filing_added
  - subsidy_added
  - procurement_added
  - patent_added
  - certification_added
```

重要なのは、**最新状態だけでなくイベントとして保存すること**です。  
企業情報サイトは最新状態だけを見せがちですが、ナレッジベースの価値は「いつ何が変わったか」です。

## 障害対策

毎日更新では、単日差分だけを取ると失敗時に穴が空きます。  
国税庁APIは期間指定が最大50日なので、毎回以下のように重複取得します。citeturn155430view0

```txt
通常：
  過去3日分を毎日取得

週次：
  過去14日分を再照合

月次：
  過去45日分を再照合

四半期：
  全件データで整合性チェック
```

同じイベントが複数回入らないように、

```txt
source + corporate_number + event_type + occurred_at + payload_hash
```

を一意キーにします。

# 9. AIエージェント仕様

## ここで言う「AIエージェント」の正体

MVPでは、AIエージェントを「自律的にWebを歩き回るLLM」にしないほうがいいです。  
それはコストも誤検知も大きい。

最初は以下の5つの小さなエージェントに分けます。

```txt
1. Fetch Agent
   データソースから取得する

2. Normalize Agent
   形式を統一する

3. Diff Agent
   前回との差分を検出する

4. Enrichment Agent
   gBizINFO / EDINET等を追加取得する

5. Summary Agent
   重要変更だけAI要約する
```

LLMを使うのは5番だけです。  
1〜4番は普通のPython/TypeScript処理で十分です。

## AI要約の対象

AI要約は全件ではなく、以下に絞ります。

```txt
AI要約する：
  - 社名変更
  - 所在地変更
  - 閉鎖
  - EDINET重要書類提出
  - 新しい補助金・調達・特許
  - アクセスが多い企業
  - ユーザーがウォッチしている企業

AI要約しない：
  - 変化なし
  - 情報が基本3情報だけ
  - ソースが不確かな情報
  - 重複イベント
```

## AI出力ルール

AIには自由作文させません。  
必ずJSONで返させます。

```json
{
  "summary": "2026年7月3日に本店所在地が変更されました。",
  "change_type": "address_changed",
  "importance": "low",
  "confidence": 0.98,
  "source_event_ids": ["evt_123"],
  "do_not_infer": true
}
```

禁止事項です。

```txt
- 売上が伸びている等の推測
- 倒産危機などの断定
- 反社・信用不安など高リスク表現
- ソースにない事業内容の生成
- AIが勝手に企業評価を作ること
```

AIの役割は、**事実の説明**であって、**根拠のない評価**ではありません。

# 10. 無料または低コストの更新エージェント

## 第一候補：GitHub Actions

public repositoryの標準GitHub-hosted runnersは無料で使えます。citeturn738252view6

使い方はこうです。

```txt
GitHub Actions:
  - 初回データ投入
  - 毎日バッチ
  - gBizINFO bulk download
  - EDINET daily check
  - 週次・月次の再照合
```

ただし、public repoにするとコードは公開されます。APIキーはGitHub Secretsに置けますが、MVP初期は以下のように分けるのが安全です。

```txt
public repo:
  ETLコード、スキーマ、テスト

private secret:
  Cloudflare token
  gBizINFO token
  EDINET API key
  e-Stat app ID
```

## 第二候補：Cloudflare Cron Triggers

Cron TriggersはWorkerをスケジュール実行できます。定期メンテナンスや外部API取得のような用途に向いています。citeturn248078view1

ただし、CronやQueue Consumerの1回の実行は最大15分なので、全件処理を1回のCronで終わらせる設計は避けます。citeturn248078view2

正しい使い方はこれです。

```txt
Cron:
  ジョブ開始だけ

Queues:
  企業単位・都道府県単位に分割処理
```

Googleのサイトマップは1ファイルあたり50,000 URLまたは50MB uncompressedが上限です。大量ページではサイトマップを分割し、sitemap indexを使います。citeturn672826search0

設計はこうします。

```txt
/sitemap-index.xml

/sitemaps/company-active-000001.xml
/sitemaps/company-active-000002.xml
/sitemaps/company-updated-2026-07.xml
/sitemaps/company-enriched-000001.xml
```

優先度はこうです。

```txt
最優先：
  最近変更があった企業

```

全ページを同じ優先度で検索エンジンに投げるのは雑です。  
価値のあるページからインデックスさせるべきです。

# 12. コスト試算

## MVP低アクセス時

| 項目 | 想定 | 月額目安 |
|---|---:|---:|
| Workers Paid | 基本料金 | $5 |
| R2 storage | 50GB保存なら無料10GB超過分40GB | 約$0.60 |
| D1 | 5GB以内なら含まれる | $0 |
| Queues | 変更10万件/月なら概ね含まれる | $0 |
| AI | 変更企業だけ・無料枠中心 | $0〜数ドル |
| 合計 | 低アクセスMVP | **約$5〜$10/月** |

R2は標準ストレージが$0.015/GB-monthで、10GB-monthまでは無料です。citeturn738252view1

初回に企業ごと1オブジェクトで500万件PUTすると、R2のClass A操作が多くなります。Class Aは1 million/monthまで無料、超過は$4.50/millionです。citeturn738252view1

したがって初回投入だけは、

```txt
企業ごと1オブジェクト：
  更新しやすいがPUT数が多い

都道府県・法人番号prefix単位でshard：
  PUT数は減るが部分更新がやや面倒
```

のトレードオフがあります。

MVPでは企業ごと1 JSONでよいです。  
一時的な初回PUTコストより、実装の単純さを優先すべきです。

# 16. 率直な戦略判断

このサービスの勝ち筋は、**全法人を載せることではありません**。  
全法人を載せるだけなら誰でもできます。

勝ち筋はここです。

```txt
1. 変更検知が速い
2. 更新理由がわかる
3. 出典が明確
4. 企業の活動履歴が時系列で見える
5. AIが事実ベースで要点を説明する
6. 重要企業だけ深くなる
```

逆に、失敗するパターンはこれです。

```txt
- SEO狙いで薄い企業ページを大量生成
- AIで根拠のない説明を付ける
- 全企業を最初から深掘りしようとする
- 更新パイプラインより見た目を優先する
- データソースの利用条件を軽視する
```

最初に作るべきMVPは、派手なAIではありません。  
**壊れない差分更新パイプライン**です。

# 17. 最初の実装優先順位

最優先はこの順番です。

```txt
1. 国税庁全件データの初回import
2. R2 company JSON保存
3. D1 companies index作成
4. /company/{法人番号} 表示
5. /search 実装
6. 国税庁差分更新

```

この順番を守るべきです。
