## 1. 「検証可能な主張」とは何か

Webページを保存単位にしない、という発想です。

例えば、ある記事にこう書いてあったとします。

> NVIDIAは2026年に新しいGPUを発表し、前世代より推論性能が3倍になり、主要クラウド各社が採用を発表した。

これを1レコードにしてはいけません。

最低でも、

```text
Claim A:
NVIDIAは2026年にGPU Xを発表した。

Claim B:
GPU Xの推論性能は前世代の3倍である。

Claim C:
AWSはGPU Xを採用すると発表した。

Claim D:
Google CloudはGPU Xを採用すると発表した。
```

まで分解する。

これがAtomic Claimです。

この方向性は研究的にもかなり強いです。2024年のFEVER論文でも、chunkをatomic statementsへ分解して検索するとchunk検索よりRecallが向上したと報告されています。citeturn0search2

つまり、

**Page → Chunk**

より、

**Page → Claim**

の方がLLM検索基盤として合理的な可能性があります。

# 2. ただし「文章」だけ保存するのも違います

私は最終的には1つのClaimを、単なる文章ではなく構造化します。

例えば、

```json
{
  "claim_id": "clm_8f91...",
  "subject": "NVIDIA B200",
  "predicate": "has_memory",
  "object": {
    "value": 192,
    "unit": "GB"
  },

  "canonical_claim":
    "NVIDIA B200 has 192 GB of HBM3e memory.",

  "valid_from": "2024-03-18",
  "valid_to": null,

  "observed_at": "2026-08-26",

  "confidence": 0.97,

  "evidence": [
    {
      "source": "NVIDIA",
      "type": "primary",
      "support": "entails"
    }
  ]
}
```

この構造には重要な意味があります。

LLMに毎回、

「このページを読んでB200のメモリ容量を探してください」

とやらせなくていい。

直接、

```text
NVIDIA B200
has_memory
192 GB
confidence=.97
```

を渡せます。

これが「WebをLLM用にコンパイルする」という考え方です。

# 3. 「確度スコア」は単純な多数決にしない

前回、

> 何社のソースで裏取りされたか

と書きましたが、これは不十分です。

例えば、

```text
ブログ100サイト
「B200は192GB」
```

と、

```text
NVIDIA公式仕様書1件
「B200は192GB」
```

なら、後者の方が強い。

したがってConfidenceは最低でも、

**Source Authority × Independence × Evidence Strength × Freshness × Agreement**

で計算するべきです。

たとえば、

```text
Primary Source         0.98
Government             0.97
Academic paper         0.95
Major news             0.85
Specialist publication 0.80
Corporate blog         0.70
General website        0.50
Anonymous post         0.25
```

くらいのSource Reliabilityを持たせる。

さらに重要なのが**独立性**です。

100サイトが同じReuters記事を転載していたら、

> 100 evidence

ではなく、

> 実質1 evidence

です。

ここはかなり重要です。

# 4. EvidenceをClaimから分離する

私はデータモデルを、

**Claim**
**Evidence**
**Source**

の3層にします。

例えば、

```text
CLAIM
│
├── Evidence A
│      └── NVIDIA
│
├── Evidence B
│      └── Reuters
│
├── Evidence C
│      └── AWS
│
└── Evidence D
       └── TechCrunch
```

そしてEvidenceごとに、

```text
SUPPORTS
CONTRADICTS
PARTIALLY_SUPPORTS
OUTDATED
UNCERTAIN
```

を持たせる。

すると、

> 「このClaimは正しいです」

ではなく、

> 「一次情報2件、独立二次情報3件が支持し、反証1件が存在する」

という状態をLLMへ返せます。

このclaim-level verification自体も現在かなり研究されています。例えば2026年のMedRAGCheckerは、回答をatomic claimsへ分解して、それぞれが取得証拠によって支持・矛盾されているかを判定しています。citeturn0academia12

# 5. Temporal Validityは「有効期限」より重要

ここは特に重要です。

私は前回「有効期限」と簡略化しましたが、本当は違います。

例えば、

> Sam Altman is CEO of OpenAI.

というClaim。

食品の賞味期限のように、

```text
2027-01-01まで有効
```

とは決められません。

明日変わる可能性があります。

そこで少なくとも、

```text
valid_from
valid_to
observed_at
last_verified_at
expected_mutability
```

を持たせます。

例えば、

```json
{
  "claim": "X is CEO of Company Y",

  "valid_from": "2025-04-01",
  "valid_to": null,

  "first_observed_at": "2025-04-01",
  "last_verified_at": "2026-08-26",

  "mutability": "high",

  "recommended_recheck":
      "24 hours"
}
```

となります。

ここで重要なのは、

**「事実が成立している時間」と「我々がその事実を確認した時間」は違う**

ということです。

これはまさに2026年のATOMでもdual-time modelingとして扱われています。citeturn0search0

# 7. そして「矛盾」を消さない

ここは普通のKnowledge Graphとかなり違うところです。

例えば、

```text
Claim A
Coffee reduces disease X risk.

Claim B
Coffee has no statistically significant
effect on disease X.

Claim C
Coffee increases disease X risk
in subgroup Y.
```

普通のDBなら「どれが正しいの？」となります。

しかしLLMにはむしろ、

```text
Consensus cluster
Contradiction cluster
Minority claim
Conditional claim
```

として全部渡した方がいい。

つまり、

```text
                    Claim A
                   /       \
            supports       contradicts
               /               \
         Evidence1           Claim B
                                |
                           qualified_by
                                |
                             Claim C
```

という構造です。

LLMはこれを使って、

> 「研究全体ではAが優勢ですが、Y群についてはCという結果もあります」

と回答できます。

これは単なるKnowledge Graphより、**Evidence Graph**に近いです。

# 8. さらに重要なのが「Claimの変化しやすさ」

世界の知識は更新頻度が全部違います。

例えば、

| Claim | 変化速度 |
|---|---:|
| 水の化学式はH₂O | ほぼ不変 |
| 富士山の標高 | 極低 |
| 会社CEO | 中 |
| 製品価格 | 高 |
| 株価 | 超高 |
| 天気 | 超高 |
| スポーツスコア | リアルタイム |

全部を同じ周期でクロールするのは無駄です。

そこで、

```text
Knowledge volatility
```

を推定します。

するとCrawler Schedulerが、

```text
H₂O               → 再取得不要
CEO               → 1日〜1週間
製品仕様           → 1週間
価格               → 数時間
ニュース           → 数分
```

のように自動調整できます。

**低価格スクレイピング能力との相性が非常に良い部分です。**

「Web全体を定期クロール」ではなく、

> **変わる可能性の高いClaimだけ再検証する。**

これならインターネット全体を巨大コピーする必要がありません。

Temporal RAGの研究でも、知識を静的に扱う問題が指摘され、更新されたtemporal factsだけ既存グラフへincremental mergeする方向が研究されています。citeturn0academia13turn0search7
