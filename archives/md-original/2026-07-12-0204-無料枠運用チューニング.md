````
## Durable Objectの役割

Durable Objectには、次のような状態を保存します。

```json
{
  "cursor": 4,
  "lastRunAt": "2026-07-12T06:17:00.000Z",
  "rotationCount": 12
}
```

主に必要なのは `cursor` です。

```text
cursor = 次回処理を開始する配列位置
```

たとえば検索条件が10件、バッチサイズが2件なら、

```text
0 → 2 → 4 → 6 → 8 → 0
```

と進みます。

計算式は次です。

```js
nextCursor = (currentCursor + batchSize) % queries.length;
```

`%` は余りを求める演算子なので、配列の末尾まで進むと0に戻ります。

## Worker側の処理イメージ

Cron実行時の処理は、概ね次のようになります。

```js
async scheduled(event, env, ctx) {
  ctx.waitUntil(runScheduledRotation(env));
}
```

ローテーション本体です。

```js
async function runScheduledRotation(env) {
  const queries = JSON.parse(env.SCHEDULED_QUERIES_JSON || "[]");
  const batchSize = Number(env.SCHEDULED_QUERY_BATCH_SIZE || "1");

  if (queries.length === 0) {
    throw new Error("SCHEDULED_QUERIES_JSON is empty");
  }

  const id = env.RUN_STATE.idFromName("scheduled-query-rotation");
  const state = env.RUN_STATE.get(id);

  const response = await state.fetch(
    "https://rotation.internal/next",
    {
      method: "POST",
      body: JSON.stringify({
        total: queries.length,
        batchSize
      })
    }
  );

  const { startIndex, indexes } = await response.json();

  for (const index of indexes) {
    const query = queries[index];

    await env.CRAWL_QUEUE.send({
      type: "search",
      query: query.q,
      location: query.l,
      maxPages: Number(query.maxPages || env.RUN_MAX_PAGES_PER_QUERY),
      scheduled: true,
      rotationIndex: index
    });
  }

  return {
    startIndex,
    submitted: indexes.length
  };
}
```

Durable Object側では、cursorを原子的に更新します。

```js
export class RotationState {
  constructor(state, env) {
    this.state = state;
    this.env = env;
  }

  async fetch(request) {
    const { total, batchSize } = await request.json();

    if (!Number.isInteger(total) || total <= 0) {
      return Response.json(
        { error: "Invalid total" },
        { status: 400 }
      );
    }

    const safeBatchSize = Math.max(
      1,
      Math.min(Number(batchSize) || 1, total)
    );

    const cursor =
      Number(await this.state.storage.get("cursor")) || 0;

    const indexes = [];

    for (let i = 0; i < safeBatchSize; i++) {
      indexes.push((cursor + i) % total);
    }

    const nextCursor = (cursor + safeBatchSize) % total;

    await this.state.storage.put({
      cursor: nextCursor,
      lastRunAt: new Date().toISOString()
    });

    return Response.json({
      startIndex: cursor,
      nextCursor,
      indexes
    });
  }
}
```

## Durable Objectを使う理由

単純な実装なら、現在時刻から配列位置を計算できます。

```js
const slot = Math.floor(Date.now() / (6 * 60 * 60 * 1000));
const startIndex = (slot * batchSize) % queries.length;
```

しかし、この方法には問題があります。

### Cronが失敗した場合

2回目のCronが失敗しても、次回は3回目の位置へ進みます。

```text
1回目: 条件0〜1 成功
2回目: 条件2〜3 失敗
3回目: 条件4〜5 実行
```

条件2〜3が飛ばされます。

### 手動実行が混ざった場合

手動でCron相当の処理を実行しても、時刻ベースでは状態が進みません。

同じ条件を重複投入する可能性があります。

### 複数Cronが重なった場合

実行遅延や再試行で同時実行されると、同じ条件セットが投入される可能性があります。

Durable Objectなら、同じオブジェクトへの処理が直列化されるため、cursorを安全に進められます。

```text

```text

## さらに重要な設計上の問題

単に職種と都道府県をローテーションするだけでは、「全企業の採用データ」は取得できません。

Indeedの検索結果には件数上限、ランキング、重複、スポンサー求人、検索結果の切り詰めがあり得ます。たとえば、

```text
営業 / 東京都
```

だけで大量求人が存在する場合、50ページ取得しても後半企業まで到達しません。

本当に網羅性を上げるなら、検索条件を細分化します。

```text
職種 × 都道府県 × 市区町村 × 掲載日 × 雇用形態
```

例:

```json
{
  "q": "営業",
  "l": "新宿区",
  "fromAge": 1,
  "jobType": "fulltime"
}
```

ただし条件を増やすほど、同じ求人が複数検索に出るため、`jobKey`、求人URL、企業名、勤務地などを使った重複排除が必須です。

結論として、**ローテーション自体は簡単ですが、収集漏れを減らす検索分割と、重複排除の方が本質的に難しい部分**です。
````
