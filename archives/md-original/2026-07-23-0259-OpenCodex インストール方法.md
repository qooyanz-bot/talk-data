この部分は **OpenCodex (ocx)** が **Codex CLIをどのように乗っ取る（フックする）か** という話です。

結論から言うと、**あなたの環境なら `ocx service install` の方が安全でおすすめ**です。

---

## まず OpenCodex の仕組み

通常は

```
あなた
   │
codex
   │
OpenAI API
```

ですが、OpenCodexを入れると

```
あなた
   │
codex
   │
OpenCodex Proxy (localhost:10100)
   │
OpenAI
Claude
Gemini
Ollama
...
```

このように間にプロキシが入ります。

つまり

```
codex
```

と打っても実際には

```
OpenCodex
```

を経由するようになります。

---

# 方法① shim

これは

```
codex
```

というコマンドを

```
OpenCodex
   ↓
本物のcodex.exe
```

へ置き換える方法です。

イメージすると

```
codex.exe
```

の前に

```
codex.cmd
```

という薄いラッパーを置きます。

```
codex.cmd

↓

ocxが起動してる？

↓

YES
↓

proxyへ送る

↓

本物のcodex.exe
```

つまり

```
codex
```

というコマンド自体を書き換えるイメージです。

---

## なぜエラーになったの？

あなたの環境では

```
PATH

↓

C:\Program Files...

↓

codex.exe
```

が既に存在しています。

OpenCodexは

```
codex.exe
```

を勝手に

```
codex.exe.old
```

などへ変更しません。

理由は

- OpenAI公式を壊したくない
- アンインストール時に困る
- 更新時に競合する

からです。

なので

```
shim install
```

すると

> codex.exeがあるので安全のため拒否します

となります。

これは正常動作です。

---

# 方法② service

こちらは全く違います。

```
ocx service install
```

すると

Windowsサービスとして

```
OpenCodex Proxy
```

を常駐させます。

つまり

```
PC起動

↓

OpenCodex起動

↓

10100番ポート待機

↓

Codexから接続
```

になります。

メリット

- shim不要
- PATHを書き換えない
- codex.exeを触らない
- 安定

# あなたならどちら？

今の環境を見ると

- ChatGPT Work
- Codex Desktop
- EnterpriseOS開発
- 長時間起動
- Windows

なので

**shimは不要**です。

むしろ

```
ocx service install
```

だけで十分です。

理由

- PATHを壊さない
- OpenAI公式アップデートに強い
- 元へ戻しやすい
- トラブルが少ない

# さらにおすすめの構成

あなたはEnterpriseOSで複数AIを活用した開発をしているので、OpenCodexは次のように使うと効果的です。

```
VSCode

        │
        ▼

   codex CLI
        │
        ▼

 OpenCodex Proxy
        │
 ┌──────┼─────────┐
 │      │         │
 ▼      ▼         ▼
OpenAI Claude Gemini
        │
        ▼
 EnterpriseOS
```

この構成なら、同じ `codex` コマンドを使いながら、用途に応じてバックエンドのAIモデルを切り替えられる可能性があります（OpenCodexの対応プロバイダー設定に依存します）。

---

**EnterpriseOSのような大規模プロジェクトを前提にするなら、OpenCodexを「複数LLMを束ねるローカルAIルーター」として運用する設計が最もメリットがあります。** これにより、Codexの操作感を維持したまま、OpenAI・Claude・Geminiなどを統一的に利用できるようになります。
