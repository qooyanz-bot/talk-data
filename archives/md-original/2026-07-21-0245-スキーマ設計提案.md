この「**スキーマ**」は、単なるテーブル設計ではありません。

あなたが作ろうとしているのは**食べログを継続的に同期するクローラー基盤**なので、「取得したデータ」と「取得状況」を分けて管理する必要があります。

私は以下のような構成をおすすめします。

---

# 全体構成

```text
            URL Discovery Bot
                   │
                   ▼
        restaurant_urls
                   │
        ┌──────────┴──────────┐
        │                     │
 Daily Checker          Monthly Updater
        │                     │
        ▼                     ▼
 restaurant_pages      restaurant_detail_items
        │
        ▼
 change_history
```

つまり役割毎にテーブルを分けます。

---

# ① restaurant_urls

これは

**「存在する店舗URL一覧」**

です。

例えば

|id|restaurant_id|url|
|----|------------|----------------|
|1|13300481|https://tabelog.com/...|
|2|13217462|https://tabelog.com/...|

だけではありません。

管理情報も持ちます。

```
restaurant_id
url
prefecture
area
status
first_found_at
last_seen_at
last_checked_at
last_detail_updated_at
next_update_at
crawl_priority
```

例えば

```
status

ACTIVE
CLOSED
MOVED
DELETED
```

など。

---

# ② restaurant_pages

これは

**最新の店舗情報**

です。

```
restaurant_id

title

rating

review_count

save_count

page_title

json全文

updated_at
```

ここには

「最新状態」

だけ入ります。

---

# ③ restaurant_detail_items

ここが今回のBotの中心です。

例えば

```
restaurant_id

label

value

order
```

データ例

```
店名
鮨 一幸

営業時間
17:30〜22:30

席数
8席

料理
魚料理にこだわる
```

重要なのは

**label固定ではない**

こと。

だから

```
VARCHAR
```

で持つ。

これなら

新しい項目

```
ペット可

ソムリエ

ワイン持込

外国語対応

```

全部保存できます。

---

# ④ change_history

ここがかなり重要です。

例えば

昨日

```
営業時間

11:00〜22:00
```

今日

```
11:00〜23:00
```

になったら

```
restaurant_id

field

old

new

changed_at
```

へ保存。

こうすると

「営業時間変更」

「閉店」

「価格改定」

全部履歴になります。

---

# ⑤ discovery_log

URL発見用です。

例えば

```
東京都

銀座

銀座駅

寿司

```

などを巡回して

```
このURLを発見した
```

を保存します。

```
source_url

restaurant_url

discovered_at
```

---

# ⑥ crawl_queue

これが一番重要。

全部を毎日取得すると

87万店舗

あります。

そこで

```
restaurant_id

job_type

priority

retry

scheduled_at

started_at

finished_at
```

を持ちます。

例えば

```
DETAIL

MONTHLY

DISCOVERY

CHECK
```

など。

---

# ジョブ構成

## Discovery

毎日

```
都道府県

↓

エリア

↓

駅

↓

一覧ページ

↓

店舗URL取得
```

新URLなら

restaurant_urlsへ追加。

---

## Daily Check

毎日

restaurant_urlsを見て

```
HTTP

404

閉店表示

移転表示
```

確認。

---

## Monthly Update

```
last_detail_updated

>30日
```

なら

詳細ページ取得。

---

## Change Detection

取得後

前回JSONと比較。

違ったら

change_history

へ追加。

---

# EnterpriseOS向けなら更に追加したい

あなたの構想なら、ここで終わらせるのはもったいないです。

以下のテーブルも追加します。

```
restaurant_photos

restaurant_business_hours

restaurant_socials

restaurant_tags
```

例えば

Instagram

公式HP

GoogleMap

予約サイト

など全部分離できます。

# 将来的なEnterpriseOS構成

```text
Discovery Bot
      │
      ▼
restaurant_urls
      │
      ▼
 Crawl Queue
      │
      ├──────────────┐
      ▼              ▼
 Detail Bot      Status Bot
      │              │
      └──────┬───────┘
             ▼
      PostgreSQL
             │
 ┌───────────┼────────────┐
 ▼           ▼            ▼
店舗情報   履歴DB     URL管理
             │
             ▼
    AI分析・営業シグナル
```

この構成にしておくと、単なる「スクレイピングBot」ではなく、**EnterpriseOSの飲食店インテリジェンス基盤**として拡張できます。例えば、営業時間変更・受賞歴追加・新規開店・閉店・SNS追加・予約方法変更などをシグナルとして蓄積し、差分だけをAIに解析させるアーキテクチャに発展させることができます。memcite
