````
# 1. 中央DB公開VIEWとは何か

今ある577万社のテーブルは

```
company_directory.company2_companies
```

です。

ここには

- 生データ(raw)
- JSON
- 監査情報
- インポート情報
- 内部ID

など全部入っています。

これをそのまま公開すると危険です。

そこで

```
company_public_api.companies
```

という

**公開専用のVIEW**

を作っています。

例えば

```sql
SELECT

corporate_number,
name,
address,
prefecture_city,
source_url,
excerpt

FROM company_directory.company2_companies
```

だけ公開します。

つまり

```
577万社
↓

公開してよい列だけ

↓

company_public_api.companies
```

になります。

これが

```
公開API
```

の役目です。

---

# 2. Hyperdriveとは何か

Cloudflare Workerは

普通は

```
PostgreSQL
```

へ直接接続できません。

そのためCloudflareが用意している

**Hyperdrive**

を使います。

イメージは

```
Worker

↓

Hyperdrive

↓

PostgreSQL
```

です。

Hyperdriveは

- 接続プール
- KeepAlive
- キャッシュ
- TLS
- タイムアウト

全部やってくれます。

---

Workerのコードには

例えば

```ts

```

というBindingを書きます。

Cloudflare管理画面で

```

↓

すると

コードの

```ts

本当に

```

この設定だけ無い状態です。

だから

```

```

なので

中央DBへ行けません。

# 6. D1は不要になる？

ここは設計判断です。

実は

**全部Hyperdriveで読む必要はありません。**

EnterpriseOSなら

こちらの構成が適しています。

```
検索一覧

↓

D1

（高速）
```

```
企業詳細

↓

Hyperdrive

（最新）
```

つまり

```
一覧ページ

↓

D1
```

```
企業詳細

↓

中央DB
```

です。

このハイブリッド構成が

Cloudflareでも一般的です。

# 7. 私ならさらにこう設計する

EnterpriseOSは577万社を扱うため、D1を単なるキャッシュではなく役割分担させます。

```text
                PostgreSQL
                （唯一の原本）
                      │
         ┌────────────┴────────────┐
         │                         │
Hyperdrive                  同期ジョブ
         │                         │
         ▼                         ▼
企業詳細ページ                D1（検索用）
企業プロフィール            一覧・検索・SEO
```

役割は次のように分けます。

- **PostgreSQL**：577万社の原本。更新・AI解析・営業シグナル・履歴などすべて保持。
- **D1**：検索・一覧・ランキング・SEO用の軽量データ。
- **Hyperdrive**：企業詳細やリアルタイム情報取得。

こうすると、

- 一覧ページは非常に高速
- 詳細ページは常に最新
- PostgreSQLへの負荷を最小化
- D1の容量制限も回避

というバランスの良い構成になります。

EnterpriseOSのような「企業ナレッジベース＋AI営業プラットフォーム」を目指すなら、このアーキテクチャが最もスケールしやすい設計です。
````
