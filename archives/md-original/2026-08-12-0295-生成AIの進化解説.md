````
生成AIの進化を一言で表すと、

**「何を答えるかを指示するAI」→「仕事のやり方を覚えたAI」→「仕事を実行できるAI」→「結果を見ながら自律的に仕事を完遂するAI」**

への進化です。

現在のAIエージェント開発を理解するうえでは、

**Prompt → Skill → Harness → Loop**

という4層で考えると非常に整理しやすいです。OpenAIも2026年にはCodexやAgents SDKについて、モデルそのものだけでなく、モデル・ツール・状態・承認・実行環境を取り囲む **Harness** と、その内部で回る **Agent Loop** を明確に分けて説明しています。citeturn336827search0turn336827search2turn336827search21

# まず全体像

イメージとしてはこうです。

```text
第1世代
Prompt
「これをやって」

        ↓

第2世代
Skill
「この仕事は、この手順でやって」

        ↓

第3世代
Harness
「必要な道具・記憶・権限・環境を使って仕事して」

        ↓

第4世代
Loop
「実行 → 確認 → 修正 → 再実行を繰り返して、
 完了条件を満たすまで進めて」
```

別の表現をすると、

```text
Prompt  = 指示
Skill   = 作業手順
Harness = 作業環境
Loop    = 自律実行
```

です。

ここを混同するとAIエージェントが非常に分かりにくくなります。

# 1. Prompt ― 「AIに指示を書く」時代

最初の生成AIは基本的に、

```text
人間
 ↓
Prompt
 ↓
LLM
 ↓
回答
```

という構造でした。

例えば、

```text
日本のAI市場について調査してください。
以下の観点でまとめてください。

・市場規模
・主要企業
・競合
・成長率
・今後5年間の予測
```

というものです。

ここでは**仕事の知識や手順そのものがPromptの中に入っています。**

LLMは、

> 「今回だけ、この指示に従ってください」

と言われている状態です。

### Promptの本質

Promptとは、

**その1回の推論に対して、モデルへ渡す指示・背景・制約**

です。

例えば、

```text
Role:
あなたは戦略コンサルタントです。

Goal:
AI検索市場を分析してください。

Constraints:
一次情報を優先してください。

Output:
市場規模、競合、参入障壁、機会の順番でまとめてください。
```

などです。

これは非常に便利ですが、大きな弱点があります。

毎回、

```text
この順番で調査して
このサイトを見て
この形式で出力して
このチェックをして
間違っていたら修正して
```

と書かなければなりません。

つまり、

**Prompt Engineeringは「AIへの指示書作成技術」**

だったわけです。

---

# 2. Skill ― 「仕事のやり方を部品化する」時代

次に出てきたのがSkillです。

これは非常に重要な変化です。

AnthropicはAgent Skillsを、

**instructions、metadata、scripts、templates、resourcesなどをまとめた再利用可能な能力**

として提供しています。citeturn336827search3turn336827search7

例えば、

```text
/skills
    market-research/
        SKILL.md
        sources.md
        templates/
        scripts/

    prd-generator/
        SKILL.md
        template.md

    competitor-analysis/
        SKILL.md
        scoring.py
```

とします。

すると人間は毎回、

```text
まず顧客課題を整理して
次に競合を調査して
機能をMust/Should/Couldで分類して
PRDテンプレートに入れて...
```

と説明しなくてよくなります。

単に、

```text
この案件のPRDを作って
```

と言えば、

AI側が適切なSkillを選択します。

---

## PromptとSkillの決定的な違い

Promptは、

```text
今回の仕事の指示
```

です。

Skillは、

```text
この種類の仕事なら
こうやって進める
```

という**再利用可能な業務ノウハウ**です。

つまり、

```text
Prompt
= 「これをやって」

Skill
= 「この仕事のやり方」
```

です。

例えば営業調査Skillなら、

```text
営業候補企業を調査するときは

1. 企業概要確認
2. 製品確認
3. 顧客確認
4. 技術スタック確認
5. 課題仮説
6. 自社との適合性評価
7. 営業アプローチ作成
```

という手順をSkillとして保存しておけます。

この段階から、

**AIの能力をPromptではなく「ファイル」として管理する**

という思想が出てきます。

AnthropicもSkillsをファイル・フォルダを用いて専門能力を持たせる仕組みとして説明しており、OpenAI側でもSkillを評価・改善する方法が扱われています。citeturn336827search7turn336827search19

# 3. Harness ― AIに「仕事場」を与える

Skillだけでは、まだ問題があります。

AIが、

> 「GitHubを調べるべきだ」

と理解したとしても、

GitHubにアクセスできなければ何もできません。

そこで出てくるのが、

# Harness

です。

Harnessは日本語に直訳すると「馬具」ですが、AIでは、

**LLMを実際に働かせるための制御・実行基盤**

と考えるのが一番分かりやすいです。

OpenAIは現在、Harnessをモデルの周囲にある **control plane** として説明し、agent loop、model calls、tool routing、handoffs、approvals、tracing、recovery、run stateなどを管理するものとしています。citeturn336827search21

例えばCodexを単純化すると、

```text
                    ┌─────────────┐
                    │     LLM     │
                    └──────┬──────┘
                           │

       ▼           ▼       ▼       ▼           ▼
     Shell       Files   GitHub   Browser      MCP
```

になります。

OpenAIのCodexの説明でも、Harnessがモデルとツールの間を取り持ち、shell/file toolsやMCP、SkillsなどをAgent Loopへ接続しています。citeturn336827search0turn336827search27

つまりLLM単体は、

```text
「GitHubを確認したほうがいい」
```

と考えるだけ。

Harnessがあると、

```text
GitHubを開く
↓
Repoを検索
↓
READMEを読む
↓
コードを書く
↓
テスト
↓
commit
```

までできる。

ここが革命的な違いです。

# SkillとHarnessの違い

ここは特に重要です。

```text
Skill
= どう仕事するか

Harness
= 仕事するための環境
```

料理で考えると簡単です。

### Prompt

```text
カレーを作って
```

### Skill

```text

2. 炒める
3. 肉を入れる
4. 水を入れる
5. 煮る
6. ルーを入れる
```

### Harness

```text

包丁
鍋
コンロ
冷蔵庫
タイマー
```

です。

ところが、まだ一つ足りません。

誰かが、

```text

↓
炒める
↓
味見
↓
薄ければ修正
↓
再び味見
```

と動かさなければならない。

そこでLoopが出てきます。

現在最も重要なのが、

↓

↓

# さらに重要なのが「Evaluator Loop」

現在の高度なAIシステムでは、

単純な、

```text
実行
→
再実行
```

だけではありません。

例えば、

```text
Generator
    ↓
成果物
    ↓
Evaluator
    ↓
品質スコア
    ↓
不足点
    ↓
Generator
    ↓
改善
```

という構造があります。

Anthropicも長時間アプリ開発においてgenerator-evaluator loopを利用したHarness設計を紹介しています。citeturn336827search5

例えばWebサイトなら、

```text
AI Developer
    │
    ▼
WEB作成
    │
    ▼
AI Reviewer
    │
    ├─ Design 72点
    ├─ Accessibility 85点
    ├─ Performance 91点
    └─ SEO 65点
    │
    ▼
Developerへ修正要求
    │
    ▼
再実装
```

という構造にできます。

これが非常に強い。

# 「Loop」の本当の意味

Loopの価値は、

**AIを何度も呼び出すこと**

ではありません。

本質は、

# 「環境からフィードバックを受け取れる」

ことです。

従来：

```text
AI
↓
予想
↓
回答
```

Agent：

```text
AI
↓
実行
↓
現実
↓
結果
↓
AI
↓
修正
```

例えば、

```text
コードが正しいと思う
```

ではなく、

```text
コードを書く
↓
Compilerを実行
↓
エラーを見る
↓
修正する
```

になります。

これによって、

**推論だけだったAIに「試行錯誤」が加わる**

わけです。

になります。

# そして2026年に重要になっている「Harness Engineering」

ここが現在のAI開発で特に重要です。

以前は、

# Prompt Engineering

でした。

現在はかなり、

# Harness Engineering

へ移っています。

OpenAI自身も2026年に「Harness engineering」という言葉を使い、Agentがコードレビュー、Git操作、テスト、修正など既存の開発ツールを直接利用する設計について説明しています。citeturn336827search4

＋

どんなContextを渡すか

＋

＋

＋

どこでHuman Approvalを挟むか
```

へ移っています。

# AI進化を世代で整理すると

かなり乱暴に整理するとこうです。

| 世代 | 中心 | 人間の指示 |
|---|---|---|
| Gen 1 | Prompt | 「こう答えて」 |
| Gen 2 | RAG / Tools | 「これを調べて」 |
| Gen 3 | Skills | 「この仕事をして」 |
| Gen 4 | Harness | 「この環境で仕事して」 |
| Gen 5 | Agent Loop | 「目的を達成して」 |
| Gen 6 | Multi-Agent | 「チームで達成して」 |
| Gen 7 | Improvement Loop | 「仕事の仕方自体を改善して」 |

もちろんこれは正式な業界規格ではなく、**技術的な進化を理解するための整理**です。しかしOpenAIとAnthropicの2025〜2026年の設計思想を見ると、Skill、Harness、Agent Loop、Evalsという方向へ進んでいることはかなり明確です。citeturn336827search2turn336827search5turn336827search8turn336827search16

# 最も重要なポイント

この進化の本質は、

**LLMのIQが上がったことだけではありません。**

むしろ、

```text
LLM
「考える」

        ↓

LLM + Skill
「やり方を知っている」

        ↓

LLM + Harness
「実行できる」

        ↓

LLM + Harness + Loop
「失敗を見てやり直せる」

        ↓

LLM + Evaluator Loop
「品質を確認しながら改善できる」

        ↓

Improvement Loop
「自分の仕事の仕方そのものを改善する」
```

という変化です。

したがって今後のAIシステム開発では、**「どのLLMが一番賢いか」だけを見ると本質を外す可能性があります。**

重要なのはむしろ、

> **Model × Skill × Context × Tools × Harness × Loop × Eval**

という「システム全体の設計」です。

そしてこれは、検索・RAG系のシステムにもそのまま当てはまります。たとえば検索AIなら、「検索Prompt」だけを改善する段階から、**検索Skill → 検索Harness → Search/Evaluate/Re-search Loop**へ進めることで、単なる検索APIではなく「検索を自律最適化するAgent基盤」に変わります。これは現在のAgent技術の流れとも非常に相性がいい設計です。citeturn336827search24turn336827search30turn336827search31

**次に理解すると一気につながるのは、「Prompt / Skill / MCP / Tool / Harness / Agent / Sub-Agent / Memory / Context Engineering / Eval」がそれぞれ何を担当するのかという“AIエージェント全体アーキテクチャ”です。** これを1枚の構成図にすると、Codex・Claude Code・OpenClaw系が何をしているのかまでかなり明瞭になります。
````

## assistant / 2026-08-12T16:09:52.0000000Z

```
この4段階は、単なる「AIが賢くなった歴史」ではなく、**人間が毎回細かく指示する方式から、AIが仕事の進め方そのものを持つ方式への進化**として捉えると理解しやすいです。現在の最前線では、モデル単体よりも「スキル・ツール・状態管理・評価・再試行をどう組むか」というハーネス設計が性能差を作り始めています。
```
