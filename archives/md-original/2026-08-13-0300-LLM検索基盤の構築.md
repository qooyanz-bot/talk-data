```
検索意図（インテント）と対話データの強化Q&A構造の学習: Googleの「強調スニペット」や「関連する質問（People Also Ask）」は、人間が尋ねる質問とそれに対する最適な回答がセットになっています。指示追従能力の向上: このデータを学習させることで、ユーザーの意図を正確に汲み取る能力（Instruction Tuning）を飛躍的に高められます。
```

````
# DataQorixDB
## ローカル言語別「LLM検索向けGoogle」を超低コストで構築するWebデータ基盤

### 1. DataQorixDBとは

**DataQorixDBは、DataQorixの独自データ資産を構築するための大規模Webデータ収集・蒸留・検索基盤です。**

目的は単なるWebクローリングではありません。

Web上に存在する膨大な情報を、

**収集 → 抽出 → Markdown化 → 言語判定 → 正規化 → 重複排除 → 品質判定 → 蒸留 → 圧縮 → インデックス化 → 継続更新**

することで、LLMがそのまま検索・RAG・学習に利用できるデータへ変換します。

最初のVer.0.1では**日本語に特化**し、その後、中国語、韓国語、ドイツ語、フランス語、スペイン語などへ同じ仕組みを展開します。

最終的な構想は、

> **各ローカル言語ごとに「LLM検索向けGoogle」を構築できる共通基盤**

を作ることです。

# 2. 従来型Googleとの根本的な違い

通常の検索エンジンは、人間がWebページを閲覧することを前提としているため、

- HTML
- 画像
- JavaScript
- CSS
- 広告
- ナビゲーション
- レイアウト情報
- ページ構造
- 大量の検索用インデックス

などを保持する必要があります。

一方、DataQorixDBが対象とするのは**人間向けWebページではなく、LLMが回答生成に必要とする「知識」そのもの**です。

したがって、

**Webページ**
↓
本文抽出
↓
Markdown
↓
意味のある部分のみ抽出
↓
重複除去
↓
LLM検索用Chunk
↓
メタデータ付与

という「Web蒸留」を行います。

つまり、

**Googleが「Webページを探す検索エンジン」なら、DataQorixDBは「LLMが答えるための知識を探す検索基盤」**

という位置付けになります。

# 3. なぜ超低コスト化できるのか

構想上、日本語Webの主要ページを数十億ページ規模と仮定すると、生Webページをそのまま保存する場合は非常に巨大なストレージが必要になります。

しかしDataQorixDBでは、検索に不要なデータを保存しません。

例えば、

**元Web：約1〜2MB/ページ**
↓
本文：約100KB
↓
LLM向け蒸留：約30〜50KB
↓
重複排除・低品質除去
↓
圧縮・Chunk最適化

という形で縮小できます。

構想上の試算では、

**約150TB**
→ 重複排除
→ **60〜75TB**
→ 低価値データ除去
→ **45〜50TB**
→ Zstd等による圧縮
→ **15〜25TB程度**

まで減らせる可能性があります。

重要なのは「Web全体を保存する」のではなく、

> **LLMが回答するために必要な情報だけ保存する**

という発想です。

# 8. サイト単位のLLM自動スクレイピング

DataQorixDBでは単純なCSS Selectorベースのスクレイピングだけではなく、

**サイト全体をLLMが理解し、自動的に収集方法を決定する仕組み**

を目指します。

まずオープンソースライブラリによってHTMLをMarkdownへ変換します。

```text
HTML
 ↓
DOM Cleaning
 ↓
Main Content Extraction
 ↓
Markdown
 ↓
LLM
```

LLMにはHTML全体ではなくMarkdownを渡すことで、

- Token削減
- 広告削減
- DOMノイズ削減
- JavaScript削減
- 意味理解精度向上

を実現します。

LLMは、

- どこが記事本文か
- ページ送りはどこか
- 詳細ページへのリンクはどこか
- どの項目を抽出するか
- 次ページをどう辿るか
- 同一テンプレートか
- 更新されたページか

などを判断します。

重要なのは**全ページをLLMに処理させないこと**です。

最初の数ページだけLLMに構造解析させ、

> **LLMがスクレイピングルールを生成 → 通常コードが大量実行**

という構成にすることで、LLM APIコストを大幅に削減できます。

これはDataQorixDBの超低コスト化において非常に重要です。

 ↓

 ↓

 ↓

```

# 16. DataQorixDBが解決する問題

現在のLLM検索には大きく4つの問題があります。

**① ローカル言語データ不足**

英語圏に比べ、日本語を含むローカル言語の高品質データ基盤が弱い。

**② Freshness**

基盤モデルの学習時点以降の情報を回答できない。

**③ Search Grounding**

LLM自身の知識だけでは出典付きの正確な回答が困難。

**④ Proprietary Data**

AIサービス企業が競争優位を作るには、モデルだけではなく独自データが必要。

DataQorixDBはこの4つを一つの基盤で解決します。

**② 自動的に取得できる**

**③ LLM向けに自動蒸留できる**
````

````
# 1. FineWebとは何か

FineWebはurlHugging Facehttps://huggingface.co/の研究チームなどが構築した、**高品質なLLM事前学習用Webデータセット**です。

論文名そのものが、

> **The FineWeb Datasets: Decanting the Web for the Finest Text Data at Scale**

です。「Webをデカントして良質なテキストだけ取り出す」という発想です。citeturn0academia3

### 元データはCommon Crawl

世界中のWebを大量収集しているCommon Crawlを使います。

ただし、

```text
Common Crawl
↓
そのままLLMへ
```

ではありません。

Webには大量の、

```text
広告
メニュー
スパム
SEO文章
重複記事
Cookie表示
低品質文章
機械生成ページ
```

があります。

そこでFineWebは、

```text
Common Crawl
     ↓
テキスト抽出
     ↓
URLフィルタ
     ↓
言語判定
     ↓
品質フィルタ
     ↓
重複排除
     ↓
FineWeb
```

という「精製工場」を通します。

最終的にFineWebは**15兆token**規模になりました。96個のCommon Crawl snapshotを処理しています。citeturn0academia3

## FineWebで特に重要なのがDedup

例えばWeb上に、

```text

「OpenAIが新モデルを発表した」

「OpenAIが新モデルを発表した」

ブログC
「OpenAIが新モデルを発表した」

まとめサイトD
「OpenAIが新モデルを発表した」
```

と同じ情報が100回存在するとします。

全部LLMに食わせる必要はありません。

そこで、

```text
100 copies
      ↓
 Deduplication
      ↓
代表データ
```

とします。

これが**重複排除（Deduplication）**です。

DataQorixDBで150TBを劇的に小さくできる最大の理由の一つもこれです。

        ↓

# 8. Multilingual Model-Based Filteringとは

ここが今回の**150MB → 10MB前後**という議論で一番面白いところです。

論文は、

**Enhancing Multilingual LLM Pretraining with Model-Based Data Selection**

です。citeturn0academia2

普通のFilteringは、

```text
文字数 < 100 → 削除

日本語率 < 80% → 削除

記号率 > 40% → 削除
```

という**人間が作ったルール**です。

これをRule-Based Filteringと呼びます。

Model-Based Filteringでは、

# 「この文章はLLMの知識として価値があるか？」

をモデルに判断させます。

---

# 9. 例えば

### ページA

> 東京は日本の首都です。東京都の行政区域は23特別区、多摩地域、島嶼部から構成され……

### ページB

> 東京最高！！！  
> 詳細はこちら！！！  
> 今なら登録無料！！！  
> CLICK HERE！！！

RuleだけでもBをある程度除去できます。

ところが現実にはもっと微妙です。

### ページC

> 本日は当サイトをご覧いただきありがとうございます。今回は東京について詳しく説明していきたいと思います。それでは早速……

文法は正常です。

日本語です。

Spamでもありません。

でも**知識密度が低い。**

そこでAIモデルが、

```text
Knowledge-rich: 0.08
Structured:     0.21
Useful:         0.13

→ DELETE
```

と判断します。

一方、

```text
Knowledge-rich: 0.94
Structured:     0.91
Useful:         0.96

→ KEEP
```

なら残す。

これがModel-Based Filteringです。

> **100GBのデータ全部より、選び抜いた15GBの方が同等以上の価値を持つ場合がある**

ということです。
````

````
私はページでもChunkでもなく、

をDataQorixDBの最小論理単位にするのがよいと思います。

です。

**1 Knowledge Unit = 1ページ**

ではないことです。

1ページから、

```text

ここで初めてWebの重複が猛烈に消えます。
````

````
# 10. GraphRAGをそのまま使う必要はない

Microsoft GraphRAGは、ソース文書からEntity Knowledge Graphを構築し、さらにEntity communityとcommunity summaryを作って検索する設計です。巨大な非構造テキストを構造化する方法として非常に参考になります。 citeturn994001search1
````

````
## Knowledge Unit中心の5層アーキテクチャ

DataQorixDBは純粋なKnowledge Graphだけにはせず、**Knowledge Unitを中心としたHybrid Semantic Index**を採用します。

| Layer | 役割 |
|---|---|
| **Source Archive** | URL・取得日時・Hash・ライセンス・Provenance |
| **Canonical Evidence** | 重複排除された引用可能な原文Chunk |
| **Knowledge Units** | Fact・Claim・Eventなど検索可能な最小知識単位 |
| **Knowledge Graph** | Entity・Relation・時間・場所など知識間の関係 |
| **Retrieval Index** | BM25・Vector・Graph・Freshness・Authority |

これにより、Knowledge Graphの構造検索、Vectorの意味検索、BM25の高精度全文検索を組み合わせながら、回答時には原典Evidenceまで遡ってCitationを提示できます。
````

````
### 実装上は4 Agentに分けると綺麗です

**Query Planner**  
現在のGraph/KUから不足している知識を質問へ変換。

**Search Agent**  
複数Search Providerへqueryを投げてURL集合を取得。

**Evidence Agent**  
URLをDataQorix Crawlerで取得、Markdown化、Claim/KU抽出。

**Discovery Agent**  
既存KUと比較し、新規情報量を計算。次QueryをQueueに追加。

つまり、

```text
Planner
   ↓
Search
   ↓
Evidence
   ↓
Dedup
   ↓
Discovery
   └────→ Planner
```

です。

### 無限ループ防止は必須

終了条件を複数用意します。

- Query単位の新規KU率が閾値未満
- Entity単位のcoverageが閾値以上
- 同一Sourceばかり出てくる
- Semantic Query重複率が高い
- 最大depth到達
- 最大cost到達
- Freshness要求を満たした
- Evidence confidenceが十分

例えば、

```text
Entity coverage ≥ 95%
AND
new_KU_per_100_queries < 5
AND
citation_confidence ≥ 0.95
```

なら探索終了です。
````

````
Python側は`asyncio`で各タブを非同期処理します。概念的には、

```python
async def worker(page, query):
    await page.goto(...)
    await submit_query(page, query)
    await wait_for_ai_response_complete(page)
    return await extract_response(page)

pages = [await context.new_page() for _ in range(5)]

results = await asyncio.gather(
    *[
        worker(page, query)
        for page, query in zip(pages, queries)
    ]
)
```

```text
Query Queue

に増やせます。
````
