## そして一番重要なのが「1,000プロフィール ≠ 1,000ブラウザ同時起動」です

例えばPCが20ブラウザまで安定すると仮定します。

1,000プロフィールを50グループに分ければいい。

```text
保存Profile
1〜1000
       │
       ▼
Scheduler
       │
       ├─ 001〜020 → 起動 → 検索 → 終了
       │
       ├─ 021〜040 → 起動 → 検索 → 終了
       │
       ├─ 041〜060 → 起動 → 検索 → 終了
       │
       └─ …
```

BitBrowser公式も「複数ブラウザを開く場合はPC性能に応じてBatch Open Intervalを設定する」と説明しています。つまり**プロファイル保有数と同時実行数は完全に別概念**です。citeturn0search4

しかも2025年8月から公式にHeadless modeがサポートされています。citeturn0search2

## したがって、いきなりSerper併用とは判断しません

ここは前回の私の回答を修正します。

**Serperで残り1,400万件を買う判断は早すぎます。**

先に100プロファイルのパイロットで、次の5数字だけ実測すべきです。

| KPI | 実測するもの |
|---|---|
| QPS | 1ブラウザで1時間何検索できるか |
| RAM/Profile | Headless 1本あたり実RAM |
| CPU/Profile | 同時10/20/30本でCPUがどうなるか |
| Session capacity | 1回起動で何検索まで安定するか |
| Error/challenge rate | 通常結果以外になる割合 |

例えば実測結果が仮に、

**30同時 × 1検索/20秒**

まで安定したとします。

これは90検索/分、5,400検索/時です。

24時間なら約13万検索/日。

30日なら、

**約389万検索/月/PC**

です。

さらに1検索10秒まで行けば、

**約778万検索/月/PC**

です。

そうなると、1,500万件/月は「巨大VPSクラスタ」の話ではなく、**PC数台または高RAMマシン数台の問題**まで落ちてきます。

ただし、これは能力計算であって、対象サービスのレート制限や利用条件を回避するための運用設計とは分けて考えるべきです。
