結論から言うと、最初から1万件のDeepResearchを集める必要はありません。

最も現実的なのは、特定業界に絞って「1,000個のユニーク検索意図・約4,300回のDeepResearch実行・3万〜8万件の重複排除済みKnowledge Unit」を作ることです。これなら、単なるレポート集ではなく、販売可能な「Intent-conditioned Temporal Evidence Graph」になります。

Defined.aiもデータセットの固定最低件数は設けておらず、件数より品質・希少性・権利・利用目的を重視しています。[Defined.ai Partnership Programs](https://defined.ai/partnership-programs)

## 推奨するデータ量

| 段階 | ユニーク検索意図 | DeepResearch実行数 | Knowledge Unit目安 | 用途 |
|---|---:|---:|---:|---|
| 営業サンプル | 100 | 150〜250 | 3,000〜8,000 | 販売代行会社への審査・顧客ヒアリング |
| 有償PoC | 500 | 800〜1,500 | 15,000〜40,000 | 特定企業向け試験販売 |
| 最初の標準商品 | 1,000 | 約4,300 | 30,000〜80,000 | データセット・年間ライセンス販売 |
| 本格版 | 3,000〜5,000 | 15,000回以上 | 10万〜30万 | API・月次更新・独占契約 |

約4,300回の内訳は、3カ月間で以下を想定します。

- 高変動200意図：毎週再調査 × 12週＝2,400回
- 中変動300意図：毎月再調査 × 3回＝900回
- 低変動500意図：開始時と終了時＝1,000回

重要なのは、4,300種類の話題を集めることではなく、1,000個の同一意図を時間を変えて再調査することです。これで「いつ情報が変わったか」「古い回答がいつ無効になったか」という、通常のデータセットにない価値が生まれます。

### Japanese AI Product & API Temporal Knowledge Graph

対象例：

- LLM、埋め込み、画像・音声モデル
- 検索API、RAG、スクレイピングAPI
- 価格、コンテキスト長、対応言語、提供地域
- 商用利用条件、API制限、廃止予定
- モデル更新、ベンチマーク、対応ツール
- 各製品の代替・競合・依存関係

この領域は変化が激しいため、時間的信頼度と更新履歴を付ける意味が大きく、AIエージェント会社、モデルルーター、AI SaaS、GPUクラウドに販売先があります。個人情報もほとんど扱わずに済みます。

1,000件を10業界へ薄く分散するより、AI/API分野だけで1,000意図を作る方が売れます。

## DeepResearch一件から生成するデータ

単純なレポート本文は商品価値が低いため、1実行を次の構造に分解します。

### 1. インテント・トポロジー

- Domain：AI Infrastructure
- Goal：最適な検索APIを選びたい
- Subgoal：価格比較／日本語性能／鮮度／利用規約
- Constraints：日本、商用、月10万検索、低遅延
- Query variants：同じ意図の自然な質問表現
- Expected evidence：公式価格表、API仕様、利用規約
- Stopping criteria：必要項目がすべて埋まった状態
- Freshness requirement：7日、30日、90日など

関係は以下を持たせます。

- `parent_of`
- `narrows`
- `requires`
- `contrasts_with`
- `alternative_to`
- `follow_up_to`

### 2. Claim中心のKnowledge Graph

単純な「企業→提供する→API」だけでは不十分です。Claimを独立ノードにします。

```text
Claim
 ├ subject: OpenAI Web Search
 ├ predicate: price_per_1000_calls
 ├ object: 金額
 ├ valid_from / valid_to
 ├ observed_at
 ├ supported_by: Source
 ├ contradicted_by: Source
 ├ confidence_components
 └ license_and_usage_status
```

こうすると、同じ事実について旧価格・新価格・矛盾情報を併存させられます。

### 3. Evidence・出典

各Claimに以下を必須化します。

- URL、発行者、ページタイトル
- 取得日時、公開日時
- 一次情報／二次情報
- EvidenceがClaimを支持・否定・更新するか
- コンテンツハッシュ
- 引用位置またはセレクタ
- 利用規約・ライセンス
- 原文再配布可否
- 取得方法と処理履歴

### 4. 時間的信頼度

一つの総合点だけにせず、成分を残します。

- Source authority
- Evidence entailment
- Corroboration count
- Extraction confidence
- Contradiction status
- Volatility class
- Last verified
- Next review
- Valid time
- Observed time

時間減衰は、例えば次で計算できます。

\[
TemporalConfidence
= FactualConfidence \times e^{-\ln(2)\times Age/HalfLife(predicate)}
\]

価格や在庫は半減期を短く、設立年や創業者情報は長くします。時間信頼度はEntity単位ではなく、必ず「述語・Claim単位」で持たせます。

### 5. 学習・評価用の付加データ

販売価格を上げるには、正解だけでなく以下も入れます。

- 採用されたEvidence
- 関連はあるが不採用だったEvidence
- 誤情報・古い情報・重複情報
- 矛盾ペア
- 情報不足で回答すべきでないケース
- Intent分解結果
- 検索先選択ラベル
- 正解回答と引用
- 引用がClaimを本当に支持しているか
- コスト・遅延・取得件数

これはResearch Agent、検索Router、RAG Evaluatorの学習・評価データになります。

## 納品形式

最低でも以下を用意します。

- Parquet：正本
- JSONL：学習・評価用
- JSON-LD／RDF Turtle：Ontology・Graph用
- Neo4j CSV：導入しやすいGraph形式
- Croissant 1.1メタデータ
- Dataset Card
- Data Dictionary
- Quality Report
- Rights Manifest
- Changelog
- 1〜5%の無償サンプル

Croissant 1.1は、レコード単位の来歴、Ontology連携、利用許諾・制限を機械可読で記録でき、今回の設計にかなり適しています。[MLCommons Croissant 1.1](https://mlcommons.org/2026/02/croissant-1-1-standard/)

## 販売審査で目標にする品質

- Claim正確性：95%以上
- CitationがClaimを支持する率：95%以上
- Entity Resolution精度：98%以上
- 出典・取得日時付与率：100%
- Rights Manifest付与率：100%
- Ontology／Schema検証成功率：100%
- 重複率：2%未満
- 10%を人手検証したGold Set
- 評価データはランダム分割ではなく時間分割・Intent分割

特にEntity Resolutionの誤結合は致命的です。別会社・同名製品を誤って同一Entityにすると、Graph全体の信頼性が崩れます。

## 法務上の重要な注意

OpenAIとの関係では、原則としてユーザーがOutputを所有しますが、第三者サービス由来の内容は所有対象外となり得ます。また、ChatGPTの利用規約はOutputの自動・プログラム抽出を禁止しています。数千件を自動製造する場合は、ChatGPT画面の自動操作ではなく、Responses APIのWeb Search／Deep Research構成を使うべきです。[OpenAI Terms of Use](https://openai.com/policies/row-terms-of-use/)、[OpenAI API Web Search](https://developers.openai.com/api/docs/guides/tools-web-search)

また、日本の著作権法第30条の4は「Webから取って加工すれば自由に再販売できる」という包括的な許可ではありません。文化庁も、AI学習用として販売されているデータベースの無許諾複製は、権利者の利益を不当に害する場合になり得ると説明しています。[文化庁「AIと著作権に関するチェックリスト＆ガイダンス」](https://www.bunka.go.jp/seisaku/bunkashingikai/chosakuken/workingteam/r06_02/pdf/94150601_07.pdf)

そのため、

- 原文全文は原則販売しない
- 事実・構造・関係・評価ラベルを中心にする
- 原文を含めるのは再配布可能なソースだけ
- 各Sourceにライセンス状態を持たせる
- 公式資料・オープンライセンスを優先する

という設計が安全です。
