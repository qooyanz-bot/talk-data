この「## 問い合わせフォーム」は、**1500サイトを1つの共通基盤で運用するためのマルチテナント設計**です。

単にフォームを作る話ではなく、

> **どのサイトから送られた問い合わせを、どの事務所へ届けるか**

を安全に判定する仕組みです。

全体の流れは次のようになります。

```text
利用者
   │
   ▼
https://abc-law.jp/contact
   │
   ▼
Cloudflare Pages
(静的サイト)
   │
   ▼
forms.enterpriseos.jp/v1/contact
   │
   ▼
Cloudflare Turnstile
   │
   ▼
Cloudflare D1
   │
   ▼
Cloudflare Queue
   │
   ▼
Resend
   │
   ▼
abc-law.jpの問い合わせ担当
```

---

# なぜ中央APIにするのか

普通の企業サイトなら

```
サイト
↓

PHP

↓

メール
```

で十分です。

しかしEnterpriseOSでは

```
1500サイト
```

を管理します。

もし各サイトが

```
/api/contact
```

を持つと

```
1500個のAPI

1500個のメール設定

1500個のSecrets

1500個の保守
```

になります。

運用が非常に大変です。

そこで

```
問い合わせだけ共通API
```

にします。

```
abc-law.jp
def-law.jp
zzz-law.jp

↓

全部

forms.enterpriseos.jp
```

になります。

---

# なぜHostを見るのか

例えば

```
abc-law.jp
```

から問い合わせが来たら

HTTPには

```
Host: abc-law.jp
```

が入っています。

これを見て

D1から

```
abc-law.jp

↓

tenant_id=123
```

を取得します。

---

# tenant_idとは

EnterpriseOSでは

事務所を全部

```
tenant
```

として管理します。

例えば

```
tenant

123
山田法律事務所

456
佐藤法律事務所

789
鈴木法律事務所
```

になります。

問い合わせは全部

```
tenant_id
```

単位になります。

---

# tenant_domains

例えば

```
abc-law.jp

www.abc-law.jp

abc-law.com
```

全部同じ事務所かもしれません。

だから

```
tenant_domains

abc-law.jp

↓

tenant123

www.abc-law.jp

↓

tenant123
```

になります。

---

# contact_recipients

ここに

```
問い合わせ先
```

があります。

例えば

```
tenant123

↓

[REDACTED_EMAIL]
```

```
tenant456

↓

[REDACTED_EMAIL]
```

です。

つまり

```
送信先メールアドレス

↓

フォームから受け取らない
```

ということです。

これが重要です。

# なぜフォームに送信先を書かせないのか

例えば悪意のある人が

```
recipient=[REDACTED_EMAIL]
```

を送ったら

メールが

```
第三者
```

へ送れてしまいます。

だから

```
ブラウザ

↓

送信先を指定できない
```

ようにします。

送信先は

必ず

```
Host

↓

D1

↓

取得
```

します。

---

# Queueを使う理由

もし

Resendが

```
429
```

を返したら

その場で失敗になります。

Queueを使うと

```
問い合わせ

↓

Queue

↓

後で送信
```

になります。

なので

Resend障害でも

問い合わせは失われません。

---

# Queue Consumer

Queueには

```
メール本文
```

が入り

Consumerが

```
D1

↓

送信先取得

↓

Resend送信
```

します。

ここでも

もう一回

```
tenant
```

を確認します。

二重チェックです。

---

# Reply-To

メールは

```
From

[REDACTED_EMAIL]
```

になります。

しかし

返信すると

```
利用者
```

へ返したいので

```
Reply-To

[REDACTED_EMAIL]
```

にします。

これはメールのベストプラクティスです。

---

# Turnstile

Google reCAPTCHAではなく

Cloudflare純正です。

```
利用者

↓

Turnstile

↓

Token

↓

Server

↓

Cloudflare検証
```

になります。

これで

ボット投稿を防ぎます。

---

# なぜD1へ本文を保存しないのか

あなたは以前

```
1500サイト
```

を運営すると話していました。

問い合わせ本文は

```
個人情報
```

です。

本文までD1へ保存すると

- 個人情報管理
- 削除依頼対応
- バックアップ
- 暗号化
- 保管期間

まで考えなければなりません。

そこで

```
送信できたか
```

だけ保存します。

例えば

```
request_id

tenant_id

status

resend_message_id

created_at
```

だけです。

これなら

個人情報をほとんど保持しません。

# 私ならさらに改善する点

現在の設計でも十分ですが、1500サイト規模を前提にするなら以下を追加するとさらに堅牢になります。

1. **Cloudflare Queuesを必須化**
   - Resendへ直接送らず、必ずQueue経由にする。

2. **冪等性キー（Idempotency Key）をD1で管理**
   - 同じ問い合わせが二重送信されても1通だけ送る。

3. **送信先メールアドレスをキャッシュ**
   - 毎回D1を読むのではなく、Cloudflare KVに数分キャッシュしてD1負荷を下げる。

4. **監査ログ専用テーブルを分離**
   - `email_delivery_events`は送信履歴だけにし、運用ログは別テーブルにする。

5. **Resend以外への切り替えを容易にする**
   - `provider = resend | postmark | ses` のように抽象化し、将来別サービスへ移行しやすくする。

この構成にしておけば、EnterpriseOSのフォーム基盤は**数千〜数万サイト規模まで拡張しやすい設計**になります。
