ここはEnterpriseOSのアーキテクチャで一番重要な部分です。

多くの人は「AIを呼んでページを作る」と考えますが、**本番サービスではAIを呼ぶタイミングを分ける**のが基本です。

## 同期APIとは

同期API（通常のResponses API）は、

```text
リクエスト送信
      ↓
AIが考える
      ↓
回答が返るまで待つ
      ↓
次の処理へ進む
```

という方式です。

例えば管理画面で顧客が

> 「会社紹介をもっと親しみやすくしてください」

とボタンを押した瞬間、

```text
ブラウザ
      ↓
EnterpriseOS
      ↓
GPT-5.6 Sol
      ↓
約5〜30秒
      ↓
新しい文章
```

となります。

ユーザーは待っています。

だから同期APIになります。

---

## Batch APIとは

Batch APIは全く違います。

```text
15,741社分のJSON
      ↓
まとめてアップロード
      ↓
OpenAIが順番に処理
      ↓
数時間〜24時間以内
      ↓
全部まとめて返ってくる
```

つまり

```text
今すぐ結果は不要
```

という処理専用です。

## 私ならさらにこう設計します

EnterpriseOSでは、

AIを直接HTMLに触らせません。

必ず

```text
GPT

↓

site-spec.json

↓

Schema検証

↓

Astro

↓

HTML生成
```

にします。

つまりAIは

```
{
  title:"",
  hero:"",
  summary:"",
  business:[]
}
```

だけ作ります。

HTMLは100%プログラムです。

この設計だと、

- AIの出力が毎回違ってもページが壊れない
- デザイン変更はテンプレートを1回修正するだけで全ページに反映できる
- 生成速度が速く、トークン消費も減る
- 品質チェックや差分更新も自動化しやすい

---

## EnterpriseOS向けの推奨パイプライン

私は最終的に、以下のような5層構成にします。

```text
① Data Layer
新設法人DB・国税庁・法人番号・企業情報

        ↓

② AI Layer
Batch API（夜間一括生成）
同期API（顧客編集）
管理AI（保守・再生成）

        ↓

③ Validation Layer
JSON Schema
証拠チェック
禁止表現チェック
重複チェック

        ↓

④ Rendering Layer
Astro
静的HTML
OG画像
サイトマップ

        ↓

⑤ Delivery Layer
Cloudflare Pages
Cloudflare R2
Cloudflare CDN
```

この構成なら、**AIは「文章を生成する役割」に専念し、Webサイトそのものは決定論的なプログラムで生成**できます。結果として、コスト・速度・保守性・品質のバランスが非常に良くなります。
