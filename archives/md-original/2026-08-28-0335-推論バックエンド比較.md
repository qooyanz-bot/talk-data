重要なのは、今の構成を次の3層に分けて考えることです。

```text
[Hugging Face 公開デモ]

```

つまり、**`RUNTIME_API_URL` はモデルそのもののURLではなく、原則として真ん中のPrivate RuntimeのURL**にするのが適切です。

## 1. 自前モデル／既存モデル

これは、Qwen、Llama、Mistral、gpt-ossなどのモデルを**自分のGPUで動かす方式**です。

たとえば、

```text
HF ZeroGPU
   ↓
Private Runtime
   ↓
vLLM
   ↓
Qwen / Llama / gpt-oss
```

という構造です。

Hugging Face Inference Endpointsは現在、vLLM、TGI、SGLang、llama.cppなどの推論エンジンをサポートしており、モデルを専用インフラへ配置してAPI化できます。citeturn0search2turn0search8

したがって、

```text
LLMs-Research Algorithm
       ↓
Qwen
```

のような実験ができます。

## 2. OpenAI互換API

これは少し意味が違います。

OpenAI互換APIというのは、APIの呼び出し形式をOpenAI形式に統一してしまう方式です。

例えばPrivate Runtimeから、

```text
POST /v1/chat/completions
```

のような共通形式で呼べるようにします。

するとバックエンドを、

```text
Qwen
DeepSeek
Llama
Mistral
gpt-oss
その他
```

へ変更しても、LLMs-Research側をほとんど変更しなくて済みます。

これは今回かなり重要です。

たとえば、

```text
                 ┌→ Qwen
HF → Runtime → Router → DeepSeek
                 ├→ Llama
                 └→ その他
```

という構造にできます。

そして研究アルゴリズム側は、

```python
executor.run(task)
```

程度の抽象化だけ持つ。

**モデル固有APIを研究コードから切り離せる**わけです。

---

## 3. Anthropic等の外部API

これは自分でGPUを持たず、

```text
Private Runtime
      ↓
Anthropic API
```

のように外部モデルをExecutorとして使う方式です。

同様に、

```text
OpenAI
Anthropic
Gemini
DeepSeek API
Mistral API
```

なども利用できます。

この方式の最大のメリットは、

**GPUを準備する前にLLMs-Researchのアルゴリズム開発を進められる**

ことです。

つまり現在の未実装部分を、

```text
run_private_runtime()
        ↓
Architecture / Router
        ↓
External Model API
```

として先に完成させられます。

GPU調達を待つ必要がありません。

ただし、これは**公式benchmarkには少し不向き**です。

外部APIモデルは提供者側でモデル更新・推論基盤変更などがあり得るため、完全な再現性を保証しにくいからです。

したがって、

```text
開発・動作確認
    ↓
外部API

正式benchmark
    ↓
固定GPU + 固定モデル
```

という分離が合理的です。

# ではLLMs-Researchでは何を選ぶべきか

私は**1つを選ばない設計**を推します。

ここがかなり重要です。

```text
                    HF ZeroGPU
                        │
                        ▼
               Public Demo Client
                        │
                RUNTIME_API_URL
                        │
                        ▼
              ┌─────────────────┐
              │ Private Runtime │
              │                 │
              │ LLMs-Research   │
              │ Architecture    │
              │ Router          │
              │ Executor        │
              └────────┬────────┘
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
      External      OpenAI       Fixed GPU
       APIs       compatible       Model
          │                         │
     開発・実験                 benchmark
```

つまりPrivate Runtimeに**Provider Adapter Layer**を作ります。

例えば、

```text
providers/

openai_compatible.py
anthropic.py
huggingface.py
local_vllm.py
mock.py
```

とします。

そうすると研究アルゴリズムは、

```text
Anthropicを使っている
Qwenを使っている
Llamaを使っている
```

ことを意識しません。

# さらに重要なポイント

今回研究しているものが本当に

**「モデル自体を巨大化するのではなく、必要なExecutorを選択・分解・合成することで能力を上げるArchitecture」**

なのであれば、むしろ**複数バックエンド対応は研究上の武器**になります。

例えば、

```text
Task
 ↓
Planner
 ↓
Executor selection
 ├─ Search
 ├─ DB
 ├─ Arithmetic
 ├─ Code
 └─ LLM
       ↓
    Provider Adapter
       ↓
 Qwen / Llama / Claude / etc.
```

にできます。

そうすると、

> 「特定モデルだから成功したのでは？」

という反論に対して、

```text
Qwenでも改善
Llamaでも改善
別モデルでも改善
```

を示せます。

これは論文としてかなり重要です。

# 固定GPUは何のために必要なのか

ここも混同しやすいところです。

固定GPUは**公開サービスを動かすためではありません。**

目的は、

**科学的な比較実験**

です。

例えば、

```text
GPU      = A100 80GB
Model    = Qwen-X
Revision = abc123
CUDA     = 固定
vLLM     = 固定
Seed     = 42
Dataset  = SHA256固定
```

として、

```text
Baseline
vs
LLMs-Research Architecture
```

を1000問実行します。

結果、

```text
Baseline      61.2%
Architecture  78.4%
```

となった場合、

**+17.2pt**

を研究成果として主張できる。

だから現在作った

`fixed-gpu.template.yaml`

が重要になります。

Hugging FaceのDedicated Inference EndpointでもGPU種類・台数等を指定でき、デプロイ後には固有のHTTPS endpoint URLが発行されます。citeturn0search3turn0search5

またDedicated Endpointは稼働compute時間ベースの課金なので、benchmark時だけ起動して、それ以外はpause/scale-to-zeroする運用も可能です。citeturn0search5turn0search6
