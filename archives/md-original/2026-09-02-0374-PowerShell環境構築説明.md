## 1. なぜ `pip` が無かったのか

最初に、

```powershell
pip install daytona
```

を実行して、

```text
pip : 用語 'pip' は認識されません
```

となりました。

これは単純に、

```text
Pythonなし
↓
pipなし
↓
pip installできない
```

という状態です。

普通ならPythonをWindowsへインストールします。

ただし漫画喫茶PCでは、

**再起動すると環境が消える**

という特殊事情があります。

そこでPythonそのものを先に入れるのではなく、`uv` を使います。

## 2. `uv` は何をしているのか

このコマンドです。

```powershell
irm https://astral.sh/uv/install.ps1 | iex
```

`irm` はPowerShellの `Invoke-RestMethod` の別名です。

大雑把には、

```text
インターネット
↓
uv公式インストールスクリプト取得
↓
PowerShellで実行
↓
uv.exe配置
```

を1行で行っています。

これはAstral公式が案内しているWindowsでの導入方式です。uv自体は**Pythonがなくても導入できます**。citeturn0search1turn0search8

公式：

urluv公式ドキュメントhttps://docs.astral.sh/uv/

そして、

```powershell
$env:Path = "$env:USERPROFILE\.local\bin;$env:Path"
```

は、Windowsに

> 今からこのPowerShellでは `uv.exe` がここにあるから使っていいよ

と教えています。

重要なのは、この変更は**現在のPowerShellセッションだけで成立させられる**ことです。

漫画喫茶ではむしろ都合がいいです。

## 4. Daytona Python SDKは何のため？

次の部分です。

```powershell
uv venv .venv --python 3.12
```

これは、このフォルダに

```text
.venv/
```

という**専用Python環境**を作ります。

さらに、

```powershell
.\.venv\Scripts\Activate.ps1
```

で、そのPython環境へ入ります。

そして、

```powershell
uv pip install daytona
```

でDaytona SDKを入れます。

ここは区別が重要です。

### Harborだけ使う

基本的に、

```text
Harbor
 ↓
Daytona
```

という形でTerminal-Benchを実行できます。

### Daytona SDKも使う

Pythonから直接、

```text
sandbox作成
↓
コマンド実行
↓
ファイル転送
↓
結果取得
↓
sandbox破棄
```

などをプログラムできます。

Cortext9の自動評価基盤を後で作るなら、SDKには価値があります。

**今すぐTerminal-Benchを動かすだけなら、SDKは必須ではありません。**

ここは前の手順より簡略化できます。

## 5. `Set-ExecutionPolicy` は何？

WindowsではPowerShellスクリプトの実行が禁止されている場合があります。

その場合、

```powershell
.\.venv\Scripts\Activate.ps1
```

が拒否されます。

そこで、

```powershell
Set-ExecutionPolicy -Scope Process Bypass
```

とします。

ポイントは、

```text
-Scope Process
```

です。

つまり、

> **今開いているPowerShellだけ許可**

です。

PC全体のセキュリティ設定を書き換えるものではありません。

PowerShellを閉じれば終了します。

漫画喫茶PCにはこちらの方が適しています。

# 8. そしてRTX 4080はどうなる？

ここが今回かなり重要です。

**Daytonaを使っても漫画喫茶のRTX 4080は使いません。**

Daytonaは別のクラウド実行環境だからです。

したがって今回は二本立てにします。

```text
                     Cortext9開発
                          │
             ┌────────────┴────────────┐
             │                         │
       ローカルRTX 4080             Daytona
             │                         │
       PyTorch CUDA                  Harbor
             │                         │
      学習・推論・蒸留          Terminal-Bench
      LoRA/QLoRAなど             Agent評価
             │                         │
             └────────────┬────────────┘
                          ↓
                    Benchmark結果
```

これが5時間のGPU利用時間を考えると合理的です。

**4080をTerminal-Bench環境構築のために遊ばせる必要はありません。**

4080には、

- Cortext9超小型モデル群の学習
- LoRA/QLoRA
- Distillation
- verifier/reranker/router学習
- Address理論系モデルの学習
- checkpoint生成

など、**GPUでなければ時間がかかる処理を優先的に投入する**べきです。

Terminal-BenchのLinuxコンテナ実行はDaytonaへ投げます。

# Cortext9 — 漫画喫茶 RTX 4080 GPU 開発環境 共通指示

現在、この開発は漫画喫茶のWindows PC上で実行しています。

このPCは再起動すると導入した環境・データが初期状態へ戻る可能性があります。そのため、**再起動・WSL導入・Hyper-V有効化・ローカルDocker導入を要求しないでください。**

## 1. 利用可能GPU

GPU:

- NVIDIA GeForce RTX 4080
- Dedicated VRAM: 16 GB
- Shared GPU Memory: 約15.9 GB
- NVIDIA Driver: 導入済み
- WindowsからGPU認識済み

このRTX 4080を、Cortext9の超小型モデル群の以下の処理へ積極的に使用してください。

- 学習
- Fine-tuning
- LoRA / QLoRA
- Distillation
- Embedding生成
- Router / Verifier / Reranker学習
- Address理論採用モデル群の学習
- 大規模batch推論
- benchmark推論
- checkpoint生成
- CPUでは現実的でなかった探索・学習・評価

GPUを使える処理をCPUへ逃がさず、16 GB VRAMの範囲で最大限RTX 4080を利用してください。

ただしOOMを避けるため、mixed precision、gradient accumulation、gradient checkpointing、LoRA/QLoRA等を必要に応じて利用してください。

## 2. Windowsネイティブ環境

WSLは使用しません。

Docker Desktopも使用しません。

WindowsネイティブCUDA対応PyTorchを使用します。

CUDA Toolkit本体をWindowsへシステムインストールすることを前提にしないでください。

PyTorch wheelに含まれるCUDA runtimeと既存NVIDIA Driverを利用する構成を優先してください。

## 3. Python / uv

このPCでは `uv` が利用可能です。

Pythonが必要な場合はシステムPythonへ依存せず、uvで管理してください。

作業ディレクトリ例:

## 6. GPU時間を最優先する

このRTX 4080を利用できる時間には制約があります。

そのため、環境構築・文書作成・GitHub整理・CPUで可能な処理よりも、

**「RTX 4080がある今しか高速にできない処理」**

を最優先してください。

特に、

1. GPU学習
2. GPU fine-tuning
3. GPU distillation
4. 大量GPU推論
5. GPU依存benchmark
6. checkpoint生成

を優先します。

CPUで後から実行できる作業は可能な限り後回しにしてください。

## 7. Cortext9開発原則

Cortext9は単一巨大モデルを作る計画ではありません。

Address理論を採用した超小型モデルを、必要能力まで機能分解して組み合わせるArchitectureです。

したがって、性能不足を単純なパラメータ増加だけで解決しないでください。

まず、

Goal
→ 必要能力分解
→ Address化
→ 専門Tiny Model
→ Router
→ Executor
→ Verifier
→ 再推論/修正
→ Answer

へ分解してください。

ただし、特定Tiny Modelについてパラメータ増加やGPU学習がシステム全体の性能向上に有効だと実験的に判断できる場合、必要なパラメータ数まで増やすことは許可します。

## 8. ベンチマーク原則

ベンチマーク専用hackは禁止です。

例えば数学benchmarkなら、

「AIME専用モデル」

ではなく、

「未知の数学問題を解く汎用数学推論モデル群」

を作ってください。

プログラミングbenchmarkなら、

「Terminal-Bench専用回答器」

ではなく、

「未知の実ソフトウェア開発・Terminal操作・debuggingを行える汎用Coding/Agentモデル群」

を作ってください。

性能値は推測値ではなく、正式benchmarkを実行した測定結果だけを確定値として報告してください。

## 9. Checkpoint保存

漫画喫茶PCは再起動・退出等でローカルデータが失われる可能性があります。

したがって、重要なcheckpoint、adapter、config、tokenizer、学習ログ、benchmark結果、manifest、SHA-256、再現コマンドをローカルだけに残さないでください。

特に長時間GPU学習で得たcheckpointは最優先で永続化してください。

秘密情報、API Key、credentialは絶対にGitHubへ保存しないでください。
