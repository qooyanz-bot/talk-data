このPowerShell部分は、「**ローカルのPostgreSQL(newdb)から企業データを読み出し、Astro用の静的データへ変換して、サイト全体を再生成する**」ための手順です。

```powershell
$env:NEWDB_DATABASE_URL = "postgresql://USER:PASSWORD@HOST:5432/newdb"
pnpm directory:export
pnpm build
```

それぞれ説明します。

---

## ① DATABASE_URLを設定

```powershell
$env:NEWDB_DATABASE_URL = "postgresql://USER:PASSWORD@HOST:5432/newdb"
```

これは

```
newdbへ接続するための情報
```

を環境変数へ設定しています。

例えば

```
postgresql://postgres:password@localhost:5432/newdb
```

なら

|項目|意味|
|----|----|
|postgres|ユーザー名|
|password|パスワード|
|localhost|DBサーバ|
|5432|ポート|
|newdb|データベース名|

という意味です。

この情報をソースコードへ書かず、

```
環境変数
```

から取得するのが一般的です。

---

## ② directory:export

```
pnpm directory:export
```

ここがEnterpriseOSでは一番重要になります。

例えば内部では

```
SELECT *
FROM company2_companies
```

を取得し

```
[
 {
   corporate_number: "...",
   legal_name: "...",
   address: "...",
   ...
 }
]
```

を

```
companies.json
```

へ書き出します。

つまり

```
PostgreSQL
    ↓
JSON
```

への変換です。

Astroは

```
JSON
```

から静的HTMLを生成します。

---

## ③ build

```
pnpm build
```

これは

```
Astro Build
```

です。

例えば

```
companies.json
```

に

```
15741社
```

入っていれば

```
/companies/1234567890123/
/companies/9876543210123/
...
```

というHTMLを全部生成します。

Cloudflareへ置くファイル群になります。

# 私ならさらに一歩進めます

今の

```
directory:export
```

は

```
DB→JSON
```

だけですが、

EnterpriseOSなら

```
DB

↓

Evidence検証

↓

企業情報整形

↓

SEO生成

↓

JSON生成

↓

Astro Build
```

まで一つのコマンドにします。

例えば

```
pnpm directory:build
```

だけで

```
① newdb取得

② URL正規化

③ 電話番号正規化

④ JSON-LD生成

⑤ OG画像生成

⑥ sitemap生成

⑦ robots生成

⑧ HTML生成

⑨ CloudflareへDeploy
```

まで終わるようにします。

---

## EnterpriseOS向けの理想形

私ならコマンドを次のように分割します。

```bash
pnpm directory:sync
```

```
newdb
↓

企業データ同期
```

---

```bash
pnpm directory:validate
```

```
必須項目チェック

SEOチェック

Evidenceチェック

重複チェック
```

---

```bash
pnpm directory:generate
```

```
Astro HTML生成

OG画像生成

JSON-LD生成
```

---

```bash
pnpm directory:publish
```

```
Cloudflare PagesへDeploy
```

---

最後に

```bash
pnpm directory:all
```

を実行すれば、

```
newdb
↓

データ取得

↓

検証

↓

HTML生成

↓

Cloudflareへ公開
```

まで完全自動になります。

EnterpriseOSでは、このように「同期」「検証」「生成」「公開」を分離しておくと、障害発生時の切り分けや将来的な並列処理、増分更新にも対応しやすくなります。
