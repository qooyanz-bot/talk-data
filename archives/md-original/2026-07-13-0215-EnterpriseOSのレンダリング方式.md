SSRは、**アクセスが来た時点でサーバーがデータを読み、完成済みのHTMLを作って返す仕組み**です。

EnterpriseOSでは、法人番号別の企業詳細ページに使う想定です。

## EnterpriseOSでの実際の流れ

ユーザーが次のURLを開いたとします。

```text
https://enterpriseos.jp/companies/1234567890123/
```

サーバー側では、次の順番で処理します。

```text
1. URLから法人番号を取得
2. DBから該当企業を検索
3. 企業情報をReact＋AstryXテンプレートへ埋め込む
4. title、本文、構造化データを含むHTMLを生成
5. ブラウザへ返す
```

生成されるHTMLは概念的には次のようになります。

```html
<!doctype html>
<html lang="ja">
  <head>
    <title>株式会社サンプル｜法人番号1234567890123</title>
    <meta
      name="description"
      content="株式会社サンプルの法人番号、本店所在地、法人番号指定日などの企業情報です。"
    />
  </head>

  <body>
    <main>
      <h1>株式会社サンプル</h1>

      <dl>
        <dt>法人番号</dt>
        <dd>1234567890123</dd>

        <dt>本店所在地</dt>
        <dd>東京都千代田区丸の内1丁目</dd>

        <dt>法人番号指定日</dt>
        <dd>2026年7月10日</dd>
      </dl>
    </main>
  </body>
</html>
```

ブラウザが受け取った時点で、すでに企業名や住所がHTML内に存在します。

## SSRとCSRの違い

CSRは、最初に最低限のHTMLとJavaScriptを返し、その後ブラウザがAPIから企業情報を取得します。

### CSR

```text
ブラウザ
→ 空に近いHTMLを受信
→ JavaScriptを実行
→ APIへ問い合わせ
→ DBから企業情報を取得
→ 画面を描画
```

最初のHTMLは、次のような状態になり得ます。

```html
<div id="app"></div>
<script src="/app.js"></script>
```

企業名や住所は、JavaScript実行後に追加されます。

### SSR

```text
ブラウザ
→ サーバーが完成させたHTMLを受信
→ すぐに企業情報を表示
```

違いを整理すると次のとおりです。

| 比較項目 | SSR | CSR |
|---|---|---|
| HTML生成場所 | サーバー | ブラウザ |
| 初回HTMLに企業情報 | 入っている | 入っていない場合が多い |
| SEO | 強い | 実装次第 |
| JavaScript無効時 | 本文を表示可能 | 表示できない場合がある |
| 初回表示 | 安定しやすい | API取得完了まで待つ |
| サーバー負荷 | 発生する | API部分のみ発生 |
| 管理画面との相性 | 普通 | 良い |
| 公開企業ページとの相性 | 良い | 第一選択ではない |

## なぜ企業DBにSSRが向くのか

### 1. Googleが企業情報を直接読める

Googlebotがページへアクセスすると、最初のHTMLに次の情報が含まれます。

- 企業名
- 法人番号
- 所在地
- 法人番号指定日
- title
- meta description
- canonical URL
- 構造化データ
- パンくず

JavaScriptの実行を待たなくても、ページ内容を取得できます。

ただし、SSRにしただけで順位が上がるわけではありません。SEO上の本質は、HTML生成方式よりも、情報の正確性、ページ固有性、内部リンク、クロール設計、検索意図への適合です。

### 2. SNSや外部サービスが内容を取得しやすい

企業ページをX、Facebook、Slackなどで共有した際、サーバーが返すHTML内にOGPが入っていれば、タイトルや説明、OG画像を取得できます。

```html
<meta property="og:title" content="株式会社サンプル｜EnterpriseOS" />
<meta
  property="og:description"
  content="株式会社サンプルの法人情報を確認できます。"
/>
<meta property="og:image" content="https://.../og/1234567890123.png" />
```

### 3. 初回表示が安定する

CSRでは以下のような問題が起こります。

- JavaScriptの読み込み失敗
- API通信の遅延
- ブラウザ性能による描画遅延
- 一瞬空画面になる
- ローディング表示が長くなる

SSRは最初から本文を返すため、公開情報ページには向いています。

## SSRの問題点

SSRにも欠点があります。

最大の問題は、**アクセスのたびにDBへ問い合わせてHTMLを作ると無駄が多いこと**です。

例えば同じ企業ページへ1日1万アクセスある場合、素朴なSSRでは次の処理を1万回繰り返します。

```text
DB検索
→ Reactレンダリング
→ HTML生成
```

企業情報は頻繁に変わらないため、これは非効率です。

そこでCloudflareキャッシュを組み合わせます。

## SSR＋Cloudflareキャッシュ

実運用では次のようになります。

### 初回アクセス

```text
ユーザー
→ Cloudflare
→ キャッシュなし
→ Worker起動
→ 公開用DBを検索
→ HTML生成
→ キャッシュへ保存
→ ユーザーへ返却
```

### 2回目以降

```text
ユーザー
→ Cloudflareキャッシュ
→ 保存済みHTMLを返却
```

2回目以降は、WorkerやDBを経由しません。

見た目上はSSRですが、キャッシュ命中時の配信は静的ページに近い動きになります。

## キャッシュ時間

例えば次のHTTPヘッダーを設定します。

```http
Cache-Control: public, s-maxage=86400, stale-while-revalidate=604800
```

意味は次のとおりです。

```text
public
共有キャッシュへ保存してよい

s-maxage=86400
Cloudflareでは24時間、新鮮なキャッシュとして扱う

stale-while-revalidate=604800
期限切れ後も最大7日間は古いHTMLを返しながら、
裏側で最新ページを再生成できる
```

ただし、EnterpriseOSでは単純な24時間失効だけより、**企業情報更新時に該当URLを明示的に削除する方式**が適しています。

## 企業情報更新時の動き

法人番号`1234567890123`の所在地が変更されたとします。

```text
1. newdbの企業情報を更新
2. 公開用DBへ反映
3. 対象URLのキャッシュを削除
4. 次回アクセスで最新HTMLをSSR
5. 新しいHTMLを再キャッシュ
```

対象URLだけ処理します。

```text
/companies/1234567890123/
```

都道府県も変わった場合は、関連ページも削除または再生成します。

```text
/companies/1234567890123/
/companies/prefectures/tokyo/
/companies/prefectures/kanagawa/
/companies/assigned/2026-07-10/
```

この依存関係を管理する必要があります。

## newdbへ直接アクセスさせるべきか

私は、公開Workerから`newdb`へ直接接続する構成は推奨しません。

理由は次のとおりです。

- newdbが社内・ローカル環境にある可能性がある
- PostgreSQL接続数が増える
- インターネット経由の接続管理が必要になる
- 公開ページ障害が基幹DBへ波及する
- DBスキーマ変更が公開サイトを壊す
- 秘密情報をCloudflare側へ持たせる必要がある

推奨は、newdbと公開用DBを分けることです。

```text
PostgreSQL newdb
        │
        │ 日次または差分同期
        ▼
公開用データストア
D1 / Hyperdrive経由PostgreSQL / KVなど
        │
        ▼
Cloudflare Worker
        │
        ▼
SSR HTML
```

newdbは原本、公開用DBは配信用の読み取りモデルです。

## React Router側の役割

React Router Framework Modeでは、企業URLに対応するルートを作ります。

概念的には次のような処理です。

```tsx
export async function loader({ params, context }) {
  const corporateNumber = params.corporateNumber;

  const company = await context.companyRepository.findByCorporateNumber(
    corporateNumber
  );

  if (!company) {
    throw new Response("Not Found", { status: 404 });
  }

  return { company };
}
```

React側では取得したデータをAstryXへ渡します。

```tsx
export default function CompanyPage({ loaderData }) {
  const { company } = loaderData;

  return (
    <main>
      <h1>{company.legalName}</h1>
      <p>法人番号：{company.corporateNumber}</p>
      <p>本店所在地：{company.headOfficeAddress}</p>
    </main>
  );
}
```

このReactコードをサーバーで実行し、完成HTMLを返すのがSSRです。

## HTMLとReactの関係

SSRを使っても、必ずしも大量のJavaScriptをブラウザへ送る必要はありません。

公開企業ページが閲覧中心なら、以下の機能だけを静的HTMLとして返せます。

- 企業情報
- パンくず
- 関連企業リンク
- 訂正申請リンク
- 構造化データ
- SEOメタデータ

検索フォームやお気に入りなど、操作が必要な部分だけJavaScriptを有効にします。

```text
企業本文
サーバーHTMLのみ

検索候補
クライアントJavaScriptあり

お気に入り
クライアントJavaScriptあり

グラフ
必要なときだけ遅延読込
```

これが軽量化の重要ポイントです。

## SSRと静的HTML生成のどちらが最適か

EnterpriseOSでは、実際には次の3案があります。

| 方式 | 公開速度 | 更新容易性 | DB負荷 | 実装難度 |
|---|---:|---:|---:|---:|
| 全件SSG | 非常に速い | 低い | なし | 中 |
| SSR＋キャッシュ | 速い | 高い | 初回のみ | 中 |
| 更新時HTML生成＋R2保存 | 非常に速い | 高い | 閲覧時なし | 高 |

MVP段階では、**SSR＋キャッシュが最もバランスがよい**です。

理由は、R2へHTMLを直接保存・配信する独自構成まで最初から作ると、公開ルーティング、HTML生成、キャッシュ無効化、サイトマップ、404処理、アセット管理などを自前で作る範囲が増えるためです。

最初から高度なイベント駆動静的生成へ進むと、売上検証よりインフラ開発に時間を使う危険があります。

## 推奨する段階的導入

### MVP

```text
React Router v8
＋Cloudflare Workers
＋公開用DB
＋SSR
＋24時間キャッシュ
```

まず新設法人ページを公開し、検索流入とWEB販売への転換を検証します。

### 成長段階

```text
更新イベント
＋個別キャッシュ削除
＋都道府県・日付ページの部分更新
```

全キャッシュ失効を避けます。

### 大規模段階

```text
更新時HTML生成
＋R2保存
＋CDN配信
＋検索だけSSR
```

アクセスの多い企業ページや長期間変更されないページを静的化します。

## 結論

EnterpriseOSでいうSSRは、単に「Reactで画面を作ること」ではありません。

```text
法人番号から企業データを取得し、
検索エンジンが直接読める完成HTMLを、
Cloudflare上で生成して返す仕組み
```

です。

そして本当に採用すべき形は、単純なSSRではなく、

```text
SSR
＋公開用DB
＋Cloudflareキャッシュ
＋更新時の個別キャッシュ削除
```

です。

ただし、MVP時点でR2静的HTML生成まで作り込むのは過剰です。まずSSR＋キャッシュで販売検証を開始し、ページ数・アクセス数・更新頻度が実際に問題になった時点でイベント駆動静的生成へ移行するのが合理的です。
