````
この部分は、**「12GB VPSでどこまで安全にスクレイピング基盤を動かせるか」**という運用設計です。

あなたの `scraping-platform` は、

- 約500万社規模の企業DB
- 複数サイトを毎月更新
- Coolify上でDockerコンテナ運用
- PostgreSQL
- Redis
- PgBouncer
- Playwrightブラウザ

という構成なので、**CPU・メモリ・DB接続数を設計しないと簡単にVPSが落ちます。**

---

# 全体構成

```
Contabo VPS 12GB

┌───────────────────────────────┐
│ Coolify                       │
│                               │
│ scheduler                     │
│ HTTP worker                   │
│ browser worker                │
│ writer                        │
│ Redis                         │
│ PgBouncer                     │
│ PostgreSQL                    │
└───────────────────────────────┘
```

この7つが同じVPSで動きます。

---

# scheduler

これは司令塔です。

仕事は

```
今日はIndeedを更新

今日は食べログを更新

今日はGoogleMapを更新
```

などをRedisへ投入するだけ。

CPUはほとんど使いません。

そのため

```
0.25〜0.5CPU

256MB程度
```

十分です。

---

# HTTP worker

HTTPだけ取得するBotです。

例えば

```
求人一覧

会社一覧

企業一覧
```

など、

ブラウザを開かず

```
axios

fetch

got
```

だけで取得できるページを処理します。

かなり軽いです。

```
1〜2CPU

1〜2GB
```

程度。

---

# browser worker

これが一番重いです。

Playwright

Chromium

Firefox

などを起動します。

例えば

```
JavaScriptで生成される企業ページ

GoogleMap

SPAサイト
```

など。

Chromiumは1ページでも

```
200〜500MB
```

使います。

だから

```
2〜4GB
```

割り当てます。

---

# writer

これはDB専用です。

スクレイピングしたデータを

```
INSERT

UPDATE

UPSERT
```

するだけ。

重くありません。

```
512MB〜1GB
```

で十分です。

---

# Redis

Redisは

**ジョブ管理**

です。

例えば

```
100万社
```

取得するとします。

Redisへ

```
会社1

会社2

会社3

...
```

全部積みます。

workerは

```
1件取得

↓

次取得

↓

次取得
```

を繰り返します。

```

をDBへ行います。

Redisを挟くことで

```

↓

↓

```

になるので速いです。

# PgBouncer

ここが非常に重要です。

普通は

```
worker
↓

PostgreSQL
```

です。

100workerなら

100接続。

1000workerなら

1000接続。

PostgreSQLは苦しくなります。

そこで

```
worker

↓

PgBouncer

↓

PostgreSQL
```

にします。

すると

```
100worker

↓

PgBouncer

↓

20接続
```

で済みます。

---

## default_pool_size

例えば

```
20
```

なら

PostgreSQLへの接続は20本。

workerが100いても

20本を共有します。

---

## max_client_conn

これは

```
PgBouncerへ来る接続
```

です。

例えば

```
200
```

なら

200workerまで接続可能。

でもDBは20本だけ。

これが接続プールです。

## あなたの `scraping-platform` におすすめの最終形

企業DBが約500万社規模で、毎月全件更新を目指すのであれば、最終的には以下の構成が拡張性・運用性のバランスが良いです。

```
                Scheduler
                     │
                     ▼
                 Redis Queue
                     │
     ┌───────────────┼───────────────┐
     ▼               ▼               ▼
 HTTP Worker    Browser Worker   Browser Worker
 (20〜40並列)      (2〜4並列)        (2〜4並列)
     └───────────────┼───────────────┘
                     ▼
                 Writer Service
                     ▼
                 PgBouncer
                     ▼
                PostgreSQL
```

この構成なら、ジョブ数が数百万件になっても、**Redisがジョブ管理、PgBouncerが接続管理、PostgreSQLがデータ永続化**という役割分担が明確になります。負荷が増えた場合も、まずHTTP WorkerやBrowser Workerだけを別VPSに増設すればよく、DBサーバーを最後まで安定して保護できます。これは大規模スクレイピング基盤でよく採用されるアーキテクチャです。
````
