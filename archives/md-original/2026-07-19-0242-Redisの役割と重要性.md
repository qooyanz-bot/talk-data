## 何が問題か

Coolify内部のPostgreSQLは、Coolify自身の設定、アプリ情報、デプロイ履歴などを保持する管理DBです。

ここにEnterpriseOSのDBを入れたままだと、以下の問題が起きます。

- Coolifyのアップデートや再構築にEnterpriseOSが巻き込まれる
- EnterpriseOSの高負荷クエリがCoolify管理画面を遅くする
- バックアップと復元の単位を分けられない
- Coolify DBの認証情報をアプリへ渡す必要が生じる
- 誤操作でCoolify本体のテーブルを変更する危険がある
- 将来、EnterpriseOSのDBだけ別サーバーへ移動しにくい

特に500万社規模の企業データを扱うなら、管理DBとの同居は避けるべきです。

## 実際に行う作業

### 1. EnterpriseOS専用PostgreSQLを作る

Coolify管理画面から、EnterpriseOSプロジェクト内に新しいPostgreSQLリソースを作成します。

例：

```text
リソース名：enterpriseos-postgres
Database：enterpriseos
User：enterpriseos_app
Port：5432
```

外部公開は原則として無効にします。EnterpriseOSのAPIやWorkerから、Coolify内部ネットワーク経由で接続します。

### 2. 現在のEnterpriseOS DBをバックアップする

Coolify内部PostgreSQLから、EnterpriseOS DBだけをダンプします。

```bash
docker exec coolify-db pg_dump \
  -U postgres \
  -Fc \
  enterpriseos \
  > /root/enterpriseos.dump
```

ただし、実際のユーザー名とDB名は現在の設定に合わせる必要があります。

SQL形式で保存する場合は次です。

```bash
docker exec coolify-db pg_dump \
  -U postgres \
  enterpriseos \
  > /root/enterpriseos.sql
```

500万社規模なら、プレーンSQLより`-Fc`のカスタム形式を推奨します。復元時に並列化でき、失敗時の扱いも容易です。

### 3. 新しいPostgreSQLへ移行する

新しいPostgreSQLコンテナへダンプファイルをコピーします。

```bash
docker cp /root/enterpriseos.dump enterpriseos-postgres:/tmp/enterpriseos.dump
```

その後、復元します。

```bash
docker exec enterpriseos-postgres pg_restore \
  -U enterpriseos_app \
  -d enterpriseos \
  --clean \
  --if-exists \
  /tmp/enterpriseos.dump
```

コンテナ名はCoolifyが自動生成する場合があるため、実際には`docker ps`で確認が必要です。

### 4. EnterpriseOSの接続先を変更する

EnterpriseOSアプリの環境変数を、新しいDBへ変更します。

```env
DATABASE_URL=postgresql://enterpriseos_app:パスワード@enterpriseos-postgres:5432/enterpriseos
```

ホスト名は、Coolifyが発行する内部接続先を使います。VPSのグローバルIPや`localhost`は使いません。

### 5. 動作確認する

最低限、次を確認します。

- EnterpriseOSが起動する
- 企業検索が動く
- ログインできる
- レコード件数が移行前後で一致する
- インデックスが存在する
- 書き込みテストが成功する
- AI Workerやクローラーが接続できる

件数確認例：

```sql
SELECT COUNT(*) FROM companies;
```

主要テーブルの件数を新旧で比較します。

### 6. 旧DBはすぐに削除しない

移行後も、旧EnterpriseOS DBはしばらく読み取り専用で残します。

推奨は以下です。

```text
移行
↓
新DBで動作確認
↓
EnterpriseOSの書き込み先を新DBへ変更
↓
24〜72時間監視
↓
最終バックアップ
↓
旧DB削除
```

## 重要な注意

Coolify内部DBからEnterpriseOSのDBだけを削除する際、**Coolify本体のDBやテーブルを誤って削除するとCoolify自体が壊れます**。

そのため、次を確認せずに削除してはいけません。

- Coolifyが使用しているDB名
- EnterpriseOSのDB名
- EnterpriseOSが専用DBとして分かれているか
- 同じDB内の別スキーマとして混在していないか
- EnterpriseOSのアプリが現在どの接続文字列を使用しているか

最悪なのは、EnterpriseOSのテーブルがCoolifyと同じデータベース内の`public`スキーマに混在しているケースです。その場合はDB単位の`pg_dump`ではなく、テーブルまたはスキーマ単位で移行する必要があります。

例：

```bash
pg_dump \
  -U postgres \
  -t companies \
  -t users \
  -t contracts \
  coolify \
  > enterpriseos_tables.sql
```

## 結論

**今すぐ壊れる構成ではありませんが、EnterpriseOSを本格運用する前に専用PostgreSQLへ分離するべきです。**

優先順位は次の順です。

1. 現在のEnterpriseOSのDB名・スキーマ・接続先を特定
2. CoolifyでEnterpriseOS専用PostgreSQLを作成
3. バックアップを取得
4. 新DBへ復元
5. EnterpriseOSの`DATABASE_URL`を変更
6. 動作確認後に旧データを削除

500万社DBを扱うなら、Coolify内部DBとの同居を放置するのは技術的負債ではなく、**障害発生時にCoolifyとEnterpriseOSを同時に失う単一障害点**になります。分離が妥当です。
