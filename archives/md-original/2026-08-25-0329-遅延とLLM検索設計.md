````
## 1. まず「LLMが検索するとき何が起きているか」

重要なのは、今のAI検索は必ずしも、

```text
ユーザー質問
 ↓
LLM
 ↓
Googleへ1クエリ
 ↓
検索結果
 ↓
回答
```

ではないことです。

Google自身がAI Modeについて、ユーザー質問を複数のサブトピックへ分解して**複数検索を並列実行する「Query Fan-out」**を使うと説明しています。さらにDeep Searchでは数百回の検索を行う場合があるとしています。citeturn0search0turn0search2

例えば、

> 「Pythonに強くてAI Agent開発実績があり、小規模だけど技術力の高い受託会社を探して」

なら、概念的にはこうなります。

```text
User Intent
│
├─ AI agent development companies
├─ Python AI development agency
├─ LLM agent consulting company
├─ agentic AI development firm
├─ Python LangGraph development company
├─ AI agent case studies
└─ AI development boutique
        ↓
   検索結果を取得
        ↓
   候補企業を抽出
        ↓
   不足情報を発見
        ↓
   追加検索
        ↓
   比較・評価
        ↓
      回答
```

Google自身も、モデルが「計画→検索→得られた情報に応じて計画を調整」というマルチステップ処理を行うと説明しています。citeturn0search6

つまり「キーワード検索が消える」というより、

**Human Query → Machine Search Plan → 多数のMachine Query**

に変わってきています。

ここは今回の構想と非常に相性がいい。

# 2. インターネット越しの場合、どこで時間を使うのか

典型的な外部検索型LLMを単純化すると、

```text
① ユーザー入力
      ↓
② Query planning
      ↓
③ 外部検索API
      ↓
④ Web/APIレスポンス
      ↓
⑤ ページ取得
      ↓
⑥ Parsing / extraction
      ↓
⑦ Ranking / reranking
      ↓
⑧ LLMへContext投入
      ↓
⑨ 推論
      ↓
⑩ Token生成
```

となります。

ここで「ネットワークPing」だけを見るのは危険です。

外部検索では、

**DNS → TLS → API → 検索処理 → HTTP → Web取得 → parsing**

などが積み重なります。

したがって外部検索部分が例えば500msだったとしても、

> Pingが500ms

なのではありません。

ネットワークRTTそのものは数十msで、残りは相手側処理などです。

# 4. ただし「回答時間のほとんどがネットワーク」というわけではない

ここは事業計画上、非常に重要です。

通常のRAGでは**LLM Generationが支配的になるケースが多い**です。2026年のRAGベンチマークでも、retrievalよりgenerationが大きなlatency要因になるという結果があります。citeturn0search8

例えば仮に、

| 処理 | 時間 |
|---|---:|
| Query理解 | 100ms |
| 外部検索 | 500ms |
| ページ取得 | 700ms |
| extraction/rerank | 300ms |
| LLM推論開始 | 500ms |
| Token生成 | 3,000ms |
| 合計 | 5,100ms |

だったとします。

この場合、単純に「ネットワークを内部化」しても5.1秒→0.5秒にはなりません。

例えば、

```text
検索 + Web取得
1,200ms
    ↓
Local Retrieval
20ms
```

なら、

**5.1秒 → 約3.9秒**

程度です。

これでも大きいですが、10倍高速化ではありません。
````

````
# そして学習コストについて、かなり面白いことが起こり得ます

```text
````
