## なぜ30エージェントは失敗したの？

今回の失敗はDBではなく**実行環境の制限**です。

```
spawnAgent ×30
```

を一度に要求しましたが、

```
環境の同時実行数
```

を超えたため拒否されました。

つまり

```
EnterpriseOS

×

DB

×

Google
```

が問題ではなく、

**Codex側の同時サブエージェント実行数の上限**に達したということです。

## あなたのEnterpriseOSなら、さらに良い設計

あなたの構想（577万社を毎日更新する企業インテリジェンス基盤）であれば、30エージェントでも十分ではありません。

更新対象だけを抽出するキューを用意し、

```
Company Queue
        │
        ▼
100 Worker
        │
        ├─ Agent 1
        ├─ Agent 2
        ├─ Agent 3
        ├─ …
        └─ Agent 100
              │
              ▼
公式サイト取得
              │
              ▼
LLM抽出
              │
              ▼
Evidence保存
              │
              ▼
company_enrichment更新
```

という構成にすれば、Cloudflare Queuesやワーカー基盤と組み合わせて大規模にスケールできます。

さらに、毎日577万社を全件クロールするのではなく、

- 公式サイトの更新があった企業
- プレスリリースを出した企業
- 採用ページが更新された企業
- IR情報が更新された企業

だけを優先して再クロールする「差分更新」にすると、計算資源とコストを大幅に削減できます。これは、あなたが目指しているAI営業シグナル基盤とも非常に相性の良いアーキテクチャです。
