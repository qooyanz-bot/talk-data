# なぜD1を1つだけ使うのか？

よくある失敗は

```text
A法律事務所
→ D1を1個

B法律事務所
→ D1を1個

C法律事務所
→ D1を1個
```

これです。

1500社なら

```
1500 D1
```

になります。

これは

- バックアップ
- マイグレーション
- スキーマ変更
- クエリ変更
- 接続管理

全部1500回になります。

完全に運用不能です。

---

逆に

EnterpriseOSは

```
enterpriseos-production
```

という

**1つのD1**

だけ持ちます。

中には

```
tenant_id
```

で

「どこの事務所か」

を識別します。

例えば

```
tenants

id
office_name
```

なら

|tenant_id|office_name|
|---------|-----------|
|1|○○法律事務所|
|2|△△法律事務所|
|3|□□法律事務所|

になります。

# ドメインはどう管理する？

例えば

```
aaa-law.jp
bbb-law.jp
ccc-law.jp
```

があります。

これを

```
tenant_domains
```

へ入れます。

例えば

|hostname|tenant_id|
|---------|---------|
|aaa-law.jp|1|
|bbb-law.jp|2|
|ccc-law.jp|3|

問い合わせが

```
https://aaa-law.jp
```

から来たら

Workerでは

```
Host

aaa-law.jp
```

が取得できます。

そのHostで検索すると

```
tenant_id=1
```

になります。

つまり

```
この問い合わせは
○○法律事務所
```

と分かります。

# メール送信先は？

送信先は

```
contact_recipients
```

にあります。

例えば

|tenant_id|email|
|----------|----------------|
|1|[REDACTED_EMAIL]|
|2|[REDACTED_EMAIL]|
|3|[REDACTED_EMAIL]|

問い合わせは

```
tenant_id=2
```

なので

```
[REDACTED_EMAIL]
```

へ送られます。

ここが非常に重要です。

**ブラウザから送信先メールアドレスを受け取ってはいけません。**

もし

```
{
 email:"[REDACTED_EMAIL]"
}
```

が送れてしまうと

攻撃者が好きな宛先へ送れるからです。

必ず

```
Host

↓

tenant_id

↓

D1

↓

送信先取得
```

にします。

# Queueを挟む理由

問い合わせは

```
POST
```

された瞬間に

Resendへ送る必要はありません。

まず

```
Queue
```

へ入れます。

```
問い合わせ

↓

Queue

↓

Consumer

↓

Resend
```

こうすると

Resendが落ちても

Queueが保持します。

例えば

```
100件同時問い合わせ
```

でも

Queue

```
100件保持
```

します。

Consumerは

```
1件ずつ
```

送ります。

非常に安定します。

---

# Queue Consumerは何をする？

Consumerは

もう一度

```
tenant_id
```

を確認します。

例えば

```
停止した事務所
```

なら

送信しません。

つまり

```
問い合わせ

↓

Queue

↓

テナント有効？

↓

YES

↓

Resend
```

になります。

これで

停止済みサイトへ送る事故がありません。

# email_delivery_events

これは

問い合わせ本文を保存する場所ではありません。

保存するのは

例えば

|項目|例|
|----|---|
|tenant_id|123|
|status|success|
|resend_id|abc123|
|created_at|2026-07-12|

だけです。

つまり

```
誰へ送ったか

成功したか

失敗したか
```

だけ。

個人情報を大量保存しません。

これは

セキュリティ的にも重要です。

---

# なぜ問い合わせ本文を保存しない？

例えば

```
相談内容

住所

電話番号

家族構成

事故内容
```

などが送られます。

これを全部D1へ保存すると

EnterpriseOSが

```
個人情報データベース
```

になります。

運営リスクが一気に上がります。

問い合わせメールだけ送り

保存しない方が

安全です。

## 私なら1点だけ設計を変更します

現在の案では、問い合わせ時に毎回D1へアクセスしてテナントや宛先を解決しています。1500サイト規模では問題ありませんが、将来的に数万サイトまで拡大するなら、**`tenant_domains` のような「ほとんど更新されないマスターデータ」はCloudflare KVでキャッシュし、D1は正本（SoT: Source of Truth）として使う**構成がさらに効率的です。

```
Host

↓

Cloudflare KV（高速キャッシュ）

↓

（キャッシュが無ければ）

↓

D1

↓

Queue

↓

Resend
```

この構成にすると、問い合わせのたびにD1を参照する必要が減り、レイテンシとD1への負荷を抑えられます。D1は「更新と整合性」、KVは「高速読み取り」という役割分担ができるため、EnterpriseOSのような大規模マルチテナント基盤では採用されることが多いパターンです。
