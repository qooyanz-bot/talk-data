ここでいう**「発見（Discovery）」**は、普通の「検索（Search）」より一段広い概念です。

DataQorixの今後を考えるうえではかなり重要で、私はむしろ **「検索エンジンを作る」より「Discovery Infrastructureを作る」** と定義した方が、長期的な事業価値が大きくなると考えます。

### 検索と発見は何が違うのか

従来のInformation Retrievalは基本的に、

**ユーザーが欲しいものを知っている → Queryを入力 → 関連する情報を返す**

という構造です。IBMの説明でも、IRは「ユーザーのqueryに対して関連情報を取得する」ものとして整理されています。citeturn0search2

例えば、

> 「DeepSeek V4 API 価格」

なら明確なSearchです。

一方、Discoveryは、

> 「安くて日本語性能が高く、商用利用できるLLMは何がある？」

のように、**ユーザー自身が最終的に何を探すべきか完全には分かっていない状態**を扱います。

さらに、

> 「私の用途ならどのLLMを採用すべき？」
>
> 「最近出てきた面白いAI技術は？」
>
> 「この会社が次に買いそうな製品は？」
>
> 「この研究テーマに関係する、まだ知らない論文は？」

まで広がります。

これは情報検索研究では「Exploratory Search」と呼ばれる領域に近く、単純なlookupではなく、**investigate / compare / learn / synthesize**を含みます。citeturn0search1turn0search9

---

## DataQorixに当てはめると重要な違いが出ます

現在考えている8,000万Query＋SERP＋最大8億URL＋Knowledge Graph＋Ontologyは、実はDiscoveryと非常に相性がいいです。

例えば、

**Query**

`生成AI 開発 外注`

から、

**SERP**

→ AI開発会社  
→ SIer  
→ 開発費用記事  
→ RAG開発記事  
→ AI Agent開発記事

を取得する。

さらにWeb本文から、

`生成AI`
→ `RAG`
→ `AI Agent`
→ `MCP`
→ `Vector DB`
→ `LLM`
→ `OpenAI`
→ `Anthropic`

というKnowledge Graphを作る。

ここまでは「検索データ」です。

しかし大量の利用ログが入ると、

`生成AI 開発 外注`
↓
`RAG 開発会社`
↓
`RAG 導入費用`
↓
`社内文書 AI検索`
↓
`MCP Server`
↓
`Claude Enterprise`

のような**人間の情報探索経路**が見えてきます。

これがDiscovery Graphです。

つまり価値が、

**「何がWebに存在するか」**

から、

**「人間・AIが、何から何を発見していくか」**

へ変わります。

---

## 無料検索MCPが重要なのはここです

無料MCPを単なる集客サービスとして考えると、その価値をかなり過小評価します。

本当に欲しいのは利用者そのものより、

**Intent → Query → Retrieval → Entity → Follow-up Query → Outcome**

というデータです。

たとえばAI Agentが、

> 日本で使える安いGPUクラウドを探して

と問い合わせる。

DataQorixが候補を返す。

Agentがさらに、

> H100だけ比較して
>
> 東京リージョンに限定
>
> 時間課金だけ
>
> 法人契約可能なところ

と絞り込む。

これは極めて価値の高い情報です。

最初のQueryだけなら、

`GPU cloud Japan`

程度のキーワードデータです。

ところが一連のセッションを見ると、

**GPU Cloud**
→ location=Japan
→ GPU=H100
→ billing=hourly
→ customer=B2B

という**需要のOntologyそのもの**が生成できます。

したがって、理想的にはQuery Graphだけでなく、

**Intent Graph / Discovery Graph**

まで作るべきです。

---

## ここから広告につながります

Google型広告は基本的には、

**Query → 広告**

です。

例えば、

`東京 ホテル`

→ ホテル広告。

しかしDiscovery Graphを持つともっと手前を取れます。

ユーザー：

> 来月東京へ出張する

AI：

> 何泊ですか？

ユーザー：

> 3泊。品川で会議があります。

ここで既に、

`Business Travel`
→ Tokyo
→ Shinagawa
→ Hotel
→ Transportation
→ Restaurant

という潜在需要が発生しています。

ユーザーがまだ、

> 「品川 ホテル」

と検索していなくてもです。

つまり広告市場で非常に重要なのは、

**Search Intent**

だけではなく、

**Pre-Search Intent**

です。

Google Discoverも明示的な検索クエリなしに、ユーザーの興味・関心に基づいてコンテンツを提示する仕組みです。citeturn0search10

SearchとRecommendationの境界も実際にはかなり連続的です。citeturn0search11

---

## だから「シェア80%」の定義を変更した方がいい

以前の、

> 検索エンジンシェア80%

は、かなり難しいKPIです。

Googleの検索UIそのものを奪う必要はありません。

狙うべきなのは、

> **AI Agent / LLMから発生する外部情報Discovery Requestのシェア**

です。

たとえば、

ChatGPT系アプリ  
Claude系Agent  
OpenClaw  
企業内Agent  
EC Agent  
旅行Agent  
金融Agent  
Vertical AI

などが外部情報を必要としたとき、

```text
AI Agent
   ↓
DataQorix Discovery API
   ↓
Intent理解
   ↓
Query Expansion
   ↓
Search Router
   ↓
Web / DB / Graph
   ↓
Evidence Fusion
   ↓
回答
```

となる。

ここで重要なのは、**ユーザーがDataQorixという名前を知らなくても構わない**ことです。

AWSを知らない一般消費者がAWS上のサービスを毎日利用しているのと同じモデルです。

## そして、8億ページ構想が効いてくる

ここでDataQorixDBとの接続が非常に強くなります。

概念的には、

```text
80,000,000 Queries
        ↓
      SERP
        ↓
最大 800,000,000 URL observations
        ↓
 Crawl / Extract
        ↓
 Knowledge Units
        ↓
 Entity / Relation
        ↓
 Ontology
        ↓
 Query Graph
        ↓
 Discovery Graph
        ↑
        │
Free Search / MCP / API
        │
実際のAI利用データ
```

となります。

このループが回るほど、

**使われる  
→ Discoveryデータが増える  
→ Graphが良くなる  
→ 検索・推薦が良くなる  
→ さらに使われる**

というネットワーク効果が成立します。

これが前の回答で言った**「データ旋回流」**の本質です。

---

### ただし、重要な修正があります

以前の回答にあった「クリック先URLを取得」という考え方は、AI Agent時代には少し狭いです。

人間がリンクをクリックするとは限らないからです。

むしろ取得すべきイベントは、

`query_generated`  
`result_retrieved`  
`source_selected`  
`citation_used`  
`followup_generated`  
`entity_explored`  
`tool_called`  
`conversion/event`

などです。

最終的には、

**Search Graph**

ではなく、

> **Global Discovery Graph**

を資産にする。

ここまで行けば、DataQorixの商材は「検索キーワードデータセット」ではなくなります。

**世界100言語で、人間とAIが「何を知りたいか」「何を比較するか」「次に何を必要とするか」を構造化したDiscovery Intelligence基盤**

になります。

これはデータセット販売、検索API、MCP、RAGだけでなく、最終的には**広告・EC・旅行・金融・B2Bリード・AI Agent Commerce**まで接続できます。

なお、この構想では利用ログの二次利用について、匿名化だけでなく、利用目的の明示、同意・オプトアウト、データ最小化、保存期間、顧客データとの分離を最初から設計する必要があります。ここを後付けするとEnterprise販売時の大きな弱点になります。

**DataQorixの長期的な堀は8億ページそのものではなく、「Query → Knowledge → Discovery → Action」のGraphになる**、というのが「発見」の意味です。
