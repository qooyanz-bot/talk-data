# 1. bizDBで最終的に作るもの

bizDBは、次の3層で構成されます。

```text
① データ収集基盤
   求人サイト・企業サイトから情報取得

② 法人・求人データベース
   法人番号、企業、求人票、収集履歴を統合

③ 営業支援SaaS
   条件検索、リスト抽出、CSV出力、営業実行
```

つまり、収集システムそのものを販売するのではなく、収集したデータを使って、

```text
東京都
× IT企業
× 採用中
× 問い合わせフォームあり
```

のような条件で見込み客を抽出できるサービスにします。

将来的な利用フローは次の形です。

```text
条件を指定
  ↓
営業対象企業を抽出
  ↓
企業情報・求人状況を確認
  ↓
CSVダウンロード
  ↓
コンタクトフォーム営業
  ↓
反応・送信履歴を管理
```

# 2. なぜ最初に求人データを集めるのか

既に約500万件規模の法人番号DBがあります。

ただし、法人番号DBだけでは営業対象としての価値が低いです。法人名や住所が分かっても、

- 現在成長しているか
- 人材を必要としているか
- どの職種を募集しているか
- どの拠点で採用しているか
- どの程度積極的に投資しているか

までは分かりません。

求人情報を組み合わせると、法人DBに「現在の需要シグナル」を追加できます。

```text
法人番号DB
  法人名・所在地・法人番号
        ＋
求人DB
  募集職種・勤務地・給与・掲載数・更新日
        ＝
営業シグナル付き企業DB
```

たとえば、直近30日でエンジニア求人を10件以上出している企業は、以下の可能性があります。

- 新規事業を立ち上げている
- 資金調達後に組織を拡大している
- 開発リソースが不足している
- 採用支援や業務委託への需要がある

このため、求人は最初のデータ源として合理的です。

# 3. Phase 1の本当の目的

Phase 1の目的は「1,800サイトから大量に取る」ことではありません。

正確には、

> 1,800サイトを登録すると、システムが自動的に取得可能性を調査し、サイトごとの収集設定を生成する仕組みを作る

ことです。

全体フローは次のようになります。

```text
サイト一覧CSVをアップロード
        ↓
sitesテーブルに登録
        ↓
Level 1で接続テスト
        ↓
失敗ならLevel 2
        ↓
失敗ならLevel 3
        ↓
取得結果をR2へ保存
        ↓
LLMがページ構造を解析
        ↓
API・CSSセレクタ・取得方法を生成
        ↓
少数ページで再テスト
        ↓
成功ならactive
失敗ならreview
        ↓
Level 1サイトだけ本番Queueへ
```

ここが従来型クローラーとの最大の違いです。

従来型では、サイトごとに人間がコードを書きます。

```text
サイトA用クローラー
サイトB用クローラー
サイトC用クローラー
...
```

bizDBでは、共通エンジンと設定データに分けます。

```text
共通クローラー
    ＋
サイトA設定
サイトB設定
サイトC設定
```

サイトごとの差異はコードではなく、D1やKVに保存された設定で吸収します。

# 4. Level 1〜5の意味

取得手段を難易度別に分ける設計です。

## Level 1：Workersの通常通信

Cloudflare Workersから通常のHTTPリクエストを送ります。

```javascript
const response = await fetch(url);
```

対象は、通常アクセスでHTMLやJSONを取得できるサイトです。

最も安く、高速で、大量処理に向いています。Phase 1で本番稼働するのは原則としてLevel 1だけです。

## Level 2：HTTPヘッダー調整

User-AgentやAccept-Languageなど、一般的なブラウザに近いヘッダーを付与します。

```text
User-Agent
Accept
Accept-Language
Referer
```

「通常のプログラムアクセス」には応答しないが、一般的なブラウザ形式の通信なら取得できるサイトを対象にします。

ただし、単なるヘッダー変更を高度な回避技術と誤解してはいけません。IP評価やTLS指紋を見ているサイトには効果がありません。

## Level 3：住宅プロキシ

WorkersからDataImpulse等の住宅プロキシを経由します。

```text
Workers
   ↓
住宅プロキシ
   ↓
対象サイト
```

サイト側からは、一般家庭や通常回線に近いIPとして見えます。

ただし、通信量に比例して課金されるため、Level 1で取得可能なサイトまでLevel 3で処理すると利益率が悪化します。

## Level 4：Fly.io + curl_cffi

Cloudflare Workersでは再現しにくい、最新ブラウザに近いTLS通信を作る層です。

```text
Cloudflare Queue
      ↓
Fly.io上のAPI
      ↓
curl_cffi
      ↓
対象サイト
```

`curl_cffi`は、Chromeに近いTLS・HTTP指紋を再現するために使います。

ここは重要な修正点です。以前の案にあった古い`curl-impersonate`だけを固定採用するのではなく、更新追従しやすい構成にする必要があります。

ただしLevel 4はPhase 1の本番主力ではありません。まず設定と必要性を記録し、Phase 2以降に実装します。

## Level 5：実ブラウザ

JavaScript実行やブラウザ操作が必要な場合です。

候補は、

- Cloudflare Browser Rendering
- Playwright
- リモートブラウザ
- 限定的なAIブラウザサービス

などです。

最も重く、最も高コストです。日常的な大量収集には向きません。

# 5. TinyFishの正しい位置づけ

TinyFishは本番収集エンジンではなく、**高難度サイトの調査装置**として使います。

たとえばLevel 1〜3でページを取得できなかった場合、通常は中身が見えないので、次の対策を設計できません。

- JSON APIが存在するのか
- JavaScriptが必要なのか
- ログインが必要なのか
- 一覧と詳細のURL構造は何か
- データはHTML内か、埋め込みJSON内か
- どのフィールドを取得できるか

TinyFishで一度だけブラウザ接続し、サイト構造を分析します。

```text
Level 1〜3で失敗
       ↓
TinyFishで分析
       ↓
取得結果・構造・JSONを保存
       ↓
本番攻略方法を決定
       ↓
自前のLevel 4または5で再現
```

TinyFishを本番に使い続けるのではなく、**攻略法を発見したら自前基盤へ戻す**のが基本です。

ただし、「絶対アクセスできる切り札」と考えるのは危険です。どのサービスでも100%取得できる保証はありません。正しい表現は、

> 自前の軽量手段では分析できないサイトに対する、高成功率の有料調査手段

です。

# 6. D1、R2、KVの役割

Cloudflareの各サービスは同じ目的ではありません。

## D1：検索・管理用データ

D1には、頻繁に検索・更新する構造化情報を保存します。

```text
sites
companies
jobs
crawl_logs
selectors
api_endpoints
scrape_runs
```

たとえば求人なら、

- 求人タイトル
- 企業ID
- 勤務地
- 給与
- 雇用形態
- 掲載URL
- 初回確認日
- 最終確認日
- 掲載状態

などです。

## R2：取得した生データ

R2には、元のHTMLやJSONを保存します。

```text
raw/{site_id}/{date}/{hash}.html
raw/{site_id}/{date}/{hash}.json
```

R2へ保存する目的は、再解析できるようにすることです。

サイトへ再アクセスしなくても、

- セレクタ変更
- 新フィールド追加
- LLMモデル変更
- バグ修正
- 正規化ルール変更

に対応できます。

## KV：小さく頻繁に読む設定

KVには、Workerが毎回参照する軽量設定を置きます。

```json
{
  "site_id": "site_123",
  "strategy": "json_api",
  "preferred_level": 1,
  "rate_limit_ms": 2000,
  "list_endpoint": "/api/jobs?page={page}"
}
```

ただし、D1とKVに同じ情報を重複保存すると整合性問題が発生します。

推奨は、

- D1を正本
- KVを実行用キャッシュ

とすることです。

# 7. 「取得とパースの分離」とは何か

悪い設計は次です。

```text
ページ取得
  ↓
その場で解析
  ↓
解析成功時だけ保存
```

解析処理でエラーになると、せっかく取得したデータを失います。また、修正後に同じページを再取得する必要があります。

bizDBでは次の順番にします。

```text
ページ取得
  ↓
R2へ必ず生保存
  ↓
取得成功ログをD1へ保存
  ↓
解析Queueへメッセージ送信
  ↓
別WorkerがR2を読む
  ↓
jobs / companiesへ保存
```

この設計には明確な利点があります。

- 通信と解析の障害を分離できる
- 解析だけ再実行できる
- サイト構造変更時に過去データを再利用できる
- Workerの実行時間を短くできる
- 障害原因を特定しやすい

これはPhase 1から入れるべき設計です。後付けするとデータ保存方式を作り直すことになります。

# 8. `sites`テーブルの役割

`sites`は、登録した求人サイトを管理する中心テーブルです。

イメージは次のとおりです。

```sql
sites
├─ site_id
├─ site_name
├─ base_url
├─ category
├─ data_scope
├─ status
├─ preferred_level
├─ crawl_frequency
├─ last_success_at
├─ last_error_at
├─ consecutive_failures
├─ review_reason
├─ tinyfish_used
└─ analysis_notes
```

`status`には状態を持たせます。

```text
registered
    ↓
discovering
    ↓
testing
    ↓
active
```

失敗時は、

```text
discovering → review
active → suspended
```

となります。

状態遷移を明確にしないと、どのサイトが、

- 未処理なのか
- 調査中なのか
- 稼働中なのか
- 人間確認待ちなのか
- 自動停止中なのか

分からなくなります。

# 9. サーキットブレーカーの詳細

「5回失敗したら停止」は概念として正しいですが、そのまま実装すると粗すぎます。

本来は、失敗を分類すべきです。

| 失敗 | 処理 |
|---|---|
| 一時的なタイムアウト | 再試行 |
| HTTP 429 | 待機時間を延長 |
| HTTP 403 | Level再判定またはreview |
| HTML構造変更 | schema-analysisへ |
| 必須項目欠落 | 解析ルールを再確認 |
| DNS・サイト停止 | 長時間停止 |
| 内部バグ | 通知して停止 |

推奨する基本ルールは次です。

```text
1回目失敗
→ 数分後に再試行

2回目失敗
→ 待機時間を延長

3回目失敗
→ 優先度を下げる

5回連続失敗
→ suspended

その後
→ Slack通知
→ 原因別の再分析Queue
```

成功したら`consecutive_failures`は0に戻します。

# 10. 「サイト攻略DB」とは何か

前回提案した中で、最も戦略的に重要なのがこれです。

通常のクローラーは、収集した求人データだけを資産として保存します。

bizDBでは、それに加えて、**各サイトをどう取得するかという知識自体を保存**します。

例えば次のような情報です。

```text
サイト名
カテゴリ
推奨Level
取得方式
JSON APIの有無
一覧URLパターン
詳細URLパターン
ページネーション方式
必須ヘッダー
レート上限
成功したUser-Agent
セレクタ
構造変更履歴
失敗原因
TinyFish分析結果
最終成功日
```

これを`site_profiles`または`site_recipes`として管理します。

## 推奨データモデル

```sql
CREATE TABLE site_profiles (
  site_id TEXT PRIMARY KEY,
  strategy TEXT NOT NULL,
  preferred_level INTEGER NOT NULL,
  list_url_pattern TEXT,
  detail_url_pattern TEXT,
  pagination_type TEXT,
  has_json_api INTEGER DEFAULT 0,
  requires_javascript INTEGER DEFAULT 0,
  requires_proxy INTEGER DEFAULT 0,
  requires_cookie INTEGER DEFAULT 0,
  rate_limit_ms INTEGER DEFAULT 2000,
  confidence REAL,
  version INTEGER DEFAULT 1,
  last_verified_at TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

セレクタは別テーブルに分けます。

```sql
CREATE TABLE selectors (
  selector_id TEXT PRIMARY KEY,
  site_id TEXT NOT NULL,
  page_type TEXT NOT NULL,
  field_name TEXT NOT NULL,
  selector TEXT NOT NULL,
  attribute_name TEXT,
  confidence REAL,
  version INTEGER DEFAULT 1,
  active INTEGER DEFAULT 1,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

API情報も別にします。

```sql
CREATE TABLE api_endpoints (
  endpoint_id TEXT PRIMARY KEY,
  site_id TEXT NOT NULL,
  endpoint_type TEXT NOT NULL,
  method TEXT NOT NULL,
  url_pattern TEXT NOT NULL,
  response_format TEXT,
  config_json TEXT,
  active INTEGER DEFAULT 1,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

# 11. なぜサイト攻略DBが競争優位になるのか

企業データそのものは、資金があれば競合も集められます。

しかし1,800サイトについて、

- どの方法で取れるか
- どこで壊れるか
- どの頻度なら安定するか
- どのAPIが使えるか
- どの構造変更が起きたか
- どう復旧したか

という履歴は、運用を続けなければ蓄積しません。

これは単なるデータ量ではなく、**収集ノウハウの複利**です。

```text
新サイトを分析
  ↓
攻略情報を保存
  ↓
似たサイトへ再利用
  ↓
登録時間が短縮
  ↓
失敗率が低下
  ↓
さらに多くの攻略情報が蓄積
```

長期的には、求人データよりもこの攻略知識の方が模倣しにくい資産になる可能性があります。

# 12. LLMはどこで使うべきか

LLMを全ページの求人抽出に使うとコストが膨らみます。

適切な使い方は、**初回のサイト解析と故障時の再解析**です。

```text
初回HTMLを取得
   ↓
LLMに構造解析させる
   ↓
セレクタ・API設定を生成
   ↓
以降は通常コードで大量処理
```

構造変更が起きたら、

```text
取得件数急減
または必須項目欠落
   ↓
SCHEMA_EXPIRED
   ↓
最新HTMLをLLMへ
   ↓
新しい設定を生成
   ↓
少数件テスト
   ↓
設定を切り替え
```

とします。

LLMは毎日の作業員ではなく、**設定を作るエンジニア役**です。

この計画の本質は、求人ページを大量に取得することではありません。

1. **法人番号・求人・企業データ**
2. **サイトごとの攻略レシピ**
3. **構造変更を検知し修復する運用履歴**
