「**送信**」の部分を詳しく説明します。

あなたのEnterpriseOSでは、**問い合わせフォームの送信処理**は次のような流れになります。

```text
ユーザー
    │
    ▼
お問い合わせフォーム
    │
    ▼
Cloudflare Pages Functions
(/api/contact)
    │
    ├── Turnstile検証
    ├── 入力値チェック
    ├── Hostから事務所判定
    ├── D1から送信先取得
    ▼
Cloudflare Queue
    ▼
Queue Consumer
    ▼
Resend API
    ▼
事務所のメールアドレス
```

---

## ① フォーム送信

例えば

```
名前
メール
電話番号
お問い合わせ内容
```

を入力すると

```
POST /api/contact
```

へ送信されます。

ブラウザから直接Resendへ送ることはありません。

理由は

- APIキーを隠す
- スパム対策
- テナント判定
- バリデーション

をサーバー側で行うためです。

---

## ② Turnstile検証

Cloudflare Turnstile

```
<div class="cf-turnstile"></div>
```

で取得したトークンを

```
https://challenges.cloudflare.com/turnstile/v0/siteverify
```

へ送ります。

成功しなければ

```
400 Bad Request
```

を返します。

ここでBotを除外します。

---

## ③ Hostから事務所判定

例えば

```
https://ryuho-law.jp
```

から来た場合

```
Host

ryuho-law.jp
```

を取得します。

そのHostを

```
tenant_domains
```

で検索します。

例えば

| hostname | tenant_id |
|------------|-----------|
| ryuho-law.jp | tenant001 |

---

## ④ tenant取得

tenant001

を取得したら

```
tenants
```

を見る。

```
status

active
```

なら続行

```
disabled
```

なら送信しません。

---

## ⑤ D1から宛先取得

例えば

```
contact_recipients
```

には

| tenant_id | email |
|------------|---------------------------|
| tenant001 | [REDACTED_EMAIL] |

があります。

ここから

```
To:
```

を決定します。

ブラウザ側は

```
送信先メールアドレス
```

を一切知りません。

これが重要です。

---

## ⑥ Queueへ投入

ここですぐResendへ送らず

```
Queue
```

へ登録します。

```
{
 tenantId,
 subject,
 body
}
```

だけ保存。

こうすると

- Resend障害
- 一時的429
- 通信失敗

でも問い合わせが失われません。

---

## ⑦ Queue Consumer

Queueから取り出し

もう一度

```
tenant

recipient

status
```

を確認します。

これは途中で

```
事務所停止
```

になっている可能性があるためです。

---

## ⑧ Resend送信

最後に

```
POST https://api.resend.com/emails
```

を実行。

例

```
From:
EnterpriseOS
<[REDACTED_EMAIL]>

To:
[REDACTED_EMAIL]

Reply-To:
[REDACTED_EMAIL]
```

ここで

```
Resend Message ID
```

が返ります。

---

## ⑨ D1へ監査ログ

本文は保存しません。

保存するのは

```
tenant_id

message_id

sent_at

status

provider
```

程度。

これなら

個人情報を最小限しか保持しません。

---

# 送信に必要なSecrets

Cloudflare Pages

↓

Settings

↓

Variables

へ登録します。

```
RESEND_API_KEY

TURNSTILE_SECRET_KEY

CONTACT_FROM_EMAIL

CONTACT_MAIL_ENABLED
```

公開しません。

Gitにも入れません。

---

# 本番ではこう動く

例えば1500事務所あった場合

```
abc-law.jp

↓

tenant=23

↓

contact_recipients

↓

[REDACTED_EMAIL]
```

---

```
xyz-law.jp

↓

tenant=518

↓

contact_recipients

↓

[REDACTED_EMAIL]
```

---

```
aaa-law.jp

↓

tenant=881

↓

contact_recipients

↓

[REDACTED_EMAIL]
```

**コードはすべて共通**で、ドメインごとに送信先だけがD1から切り替わります。

---

## この設計をさらに改善するなら

現在の設計でも十分実用的ですが、1500サイト規模を見据えるなら次の2点を追加するとさらに運用性が上がります。

1. **送信ジョブの状態管理**
   - `queued`
   - `processing`
   - `sent`
   - `failed`
   - `retrying`
   - `dead_letter`

2. **送信履歴テーブル**
   - Resend Message ID
   - Queue ID
   - リトライ回数
   - エラーコード
   - 最終送信時刻

これにより、「この問い合わせは送信されたか」「どこで失敗したか」を追跡できるようになり、1500サイト規模でも運用しやすくなります。
