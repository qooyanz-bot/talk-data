# AI導入・AI Agent案件 顧客ヒアリング項目

## 1. プロジェクト背景・目的

最初に「何を作るか」ではなく「なぜやるか」を確定します。

**質問項目**

- 今回AI導入を検討したきっかけは何ですか？
- 現在、一番困っている業務は何ですか？
- その問題はいつ頃から発生していますか？
- なぜ今まで解決できなかったのでしょうか？
- AIを使わずに改善したことはありますか？
- 既存システム改修ではなくAIを検討している理由は何ですか？
- 経営課題・事業課題としては何に紐づいていますか？
- 売上向上、コスト削減、品質向上、速度向上、人手不足対応のどれが主目的ですか？
- このプロジェクトで最も改善したいKPIは何ですか？
- 6か月後に「成功した」と判断できる状態は何ですか？
- 逆に、どのような結果なら失敗と判断しますか？
- PoCが成功した場合、本番展開する意思・予算はありますか？

ここで重要なのは、

**「AIを導入する」ことを目的にしないことです。**

たとえば、

> 問い合わせ対応をAI化したい

ではなく、

> 平均回答時間を15分→3分にする

まで掘ります。

---

# 2. As-Is：現在の業務フロー

ここがPRD作成の材料として非常に重要です。

まず、

**誰が → 何を受け取って → 何を判断して → 何を操作して → 誰に渡すか**

を順番に聞きます。

### 業務開始

- 何をきっかけに業務が開始しますか？
- メールですか？
- 電話ですか？
- Slack/Teamsですか？
- Webフォームですか？
- 基幹システムですか？
- 定時バッチですか？

### 担当者

- 誰が担当していますか？
- 何人で処理していますか？
- 担当者によってやり方は違いますか？
- 熟練者と新人でどの程度差がありますか？
- 特定の人しかできない業務がありますか？

### 入力情報

- 最初に何の情報を受け取りますか？
- 情報はどこにありますか？
- Excel
- PDF
- Word
- メール
- Web
- CRM
- ERP
- Salesforce
- Google Drive
- SharePoint
- 社内DB
- 紙資料

などを特定します。

### 実際の操作

「問い合わせ対応です」だけでは足りません。

具体的に、

1. メールを開く
2. 顧客名を確認
3. Salesforceを検索
4. 過去問い合わせを確認
5. マニュアルを検索
6. 回答案を書く
7. 上司が確認
8. 顧客へ返信
9. CRMへ履歴登録

という粒度まで分解します。

# 3. 業務量・処理時間

AI導入のROI計算に必要です。

- 1日何件ありますか？
- 月間何件ありますか？
- 繁忙期は何件になりますか？
- 1件あたり平均何分かかりますか？
- 最短・最長では？
- 何人が担当していますか？
- 月間総工数は？
- 残業は発生していますか？
- 外注していますか？
- 外注費はいくらですか？
- 1件あたりの処理コストはいくらですか？
- 業務量は今後増える予定ですか？

例えば、

**20人 × 2時間/日 × 20日 = 800時間/月**

と判明すれば、AI化による経済効果をかなり説明しやすくなります。

### 時間

- 待ち時間が発生する工程は？
- 同じ情報を何度も入力していますか？

### 品質

- ミスが多い工程は？
- 手戻りが多い工程は？

- 社内文書が多すぎて見つからないことはありますか？

### コスト

- 人件費が高い工程は？
- 外注費が高い工程は？
- SaaS/APIなどの既存コストは？

# 5. 「人間が何を判断しているか」

AI Agent案件ではここが特に重要です。

単純作業と**判断作業**を分離します。

例えば営業案件なら、

> 問い合わせ内容を見る  
> ↓  
> 顧客種別を判断  
> ↓  
> 緊急度を判断  
> ↓  
> 過去履歴を確認  
> ↓  
> 対応方針を判断

となります。

そこで聞きます。

- 何を見て判断していますか？
- 判断基準はありますか？
- マニュアル化されていますか？
- 判断基準を言語化できますか？
- 例外はありますか？
- ベテランは何を見ていますか？
- 判断に必要な情報はどこにありますか？
- 判断を間違えると何が起きますか？
- AIが判断してよい範囲はどこまでですか？
- 最終的に人間が承認する必要がありますか？

これはAI Agentの設計に直結します。

# 6. 例外処理

実務では正常系よりこちらが重要です。

質問します。

- 通常フローから外れるケースはありますか？
- どのくらいの頻度ですか？
- 情報不足の場合どうしますか？
- 顧客情報が見つからない場合は？
- 複数の判断が可能な場合は？
- マニュアルにないケースでは？
- 緊急案件の場合は？
- VIP顧客の場合は？
- AIが判断できない場合、誰にエスカレーションしますか？

PRDには、

**Normal Flow**

だけでなく、

**Exception Flow / Escalation Flow**

として落とします。

# 10. AIに「何をさせたいか」

ここで初めてAIの話に入ります。

顧客には例えば、

**Level 1：検索**

「必要な情報をAIが探す」

↓

**Level 2：生成**

「回答案を作る」

↓

**Level 3：判断支援**

「分類・優先順位・推奨アクションを提示」

↓

**Level 4：Agent**

「システムを操作して処理まで行う」

という形で説明すると分かりやすいです。

聞くべきなのは、

- AIは提案だけですか？
- 自動実行させますか？
- 人間の承認を挟みますか？
- どの操作までAIに許可しますか？
- メール送信まで可能ですか？
- DB更新まで可能ですか？
- 顧客への直接回答は可能ですか？

です。

# 11. AI精度・Evaluation

普通のシステム要件定義との大きな違いです。

「精度が高いAIにしてください」

では要件になりません。

- 何をもって正解としますか？
- 正解データはありますか？
- 過去事例はありますか？
- 100件程度の評価用ケースを用意できますか？
- 誤回答はどの程度許容できますか？
- False PositiveとFalse Negativeのどちらが危険ですか？
- 回答根拠は必要ですか？
- 引用元表示は必要ですか？
- AIが分からないと回答することを許容しますか？

ここから、

**Evaluation Dataset**

を作ります。

---

# 12. Human-in-the-loop

AIに100%任せる必要はありません。

例えば、

**Confidence > 95%**
→ 自動処理

**70〜95%**
→ 人間確認

**<70%**
→ エスカレーション

という設計もできます。

ヒアリングでは、

- どの処理なら完全自動化できますか？
- どの処理は人間確認必須ですか？
- 誰が承認しますか？
- 承認時間のSLAは？
- AI回答を修正した場合、その修正を保存しますか？

を確認します。

最後の「修正結果」は将来の評価・改善データとして非常に価値があります。

# 17. 優先順位

最後に全部を作ろうとしないことが重要です。

単なる職歴紹介ではなく、

したがって、

というポジションを明確にします。

から入ります。

# 3. As-Is / To-Be

### As-Is

現在の業務状態です。

例えば問い合わせ対応なら、

**問い合わせ受信**
→ 担当者確認
→ CRM検索
→ マニュアル検索
→ 回答案作成
→ 上司確認
→ 送信
→ CRM登録

まで分解します。

見るポイントは、

**Actor / Action / Input / Output / System / Time / Decision**

です。

### To-Be

AI導入後の理想状態です。

例えば、

問い合わせ
→ AI分類
→ CRM取得
→ RAG検索
→ 回答案生成
→ 人間承認
→ 送信
→ CRM自動登録

です。

面談では、

> As-Isを理解せずにTo-Beを作らない

と言えることが重要です。

# 4. PRD

**Product Requirements Document**です。

単なる仕様書ではありません。

説明するなら、

> 「誰の、どの問題を、なぜ解決し、プロダクトとして何を実現するのかを定義する文書」

と理解しておけばいいです。

最低限、

- Background
- Problem
- Objective
- Target User
- Use Case
- User Story
- Functional Requirements
- Non-functional Requirements
- KPI
- Acceptance Criteria
- Scope / Out of Scope
- Risk

を説明できるようにします。

生成AIを使うなら、

**ヒアリング**
→ 構造化
→ PRD初稿
→ 不足/矛盾抽出
→ PjMレビュー
→ 顧客合意

という使い方です。

# 5. 要件定義

PRDとの違いを聞かれる可能性があります。

大雑把には、

**PRD**
＝何を・なぜ作るか

**要件定義**
＝それを実現するシステムに何が必要か

です。

例えば、

PRD：

> 社内規程についてAIに質問できる。

要件定義：

> PDF/Wordを取り込み、部署ごとのアクセス権を維持したRAG検索を行い、回答には参照文書名と該当箇所を表示する。

ここまで具体化します。

# 6. AI案件特有の要件定義

ここを説明できると評価が上がります。

普通のWebシステムなら、

> ボタンを押したら保存される

は基本的に決定論的です。

ところがLLMは確率的です。

同じ入力でも結果が完全には固定されません。

したがってAI案件では通常要件に加えて、

**Model**
**Prompt**
**Context**
**RAG**
**Tool**
**Evaluation**
**Guardrails**
**Human Approval**
**Fallback**
**Observability**
**Cost**

などを考える必要があります。

特に、

> 「AIが正確に回答する」

では要件になりません。

例えば、

> 評価データセット200件で定義済み評価基準の90%以上を満たす

など、評価可能な状態へ変換します。

# 7. LLM / Generative AI

最低限説明できれば十分です。

LLMは大量のテキスト等から言語パターンを学習し、入力Contextを基に次のTokenを予測しながら出力を生成するモデルです。

重要なのは限界も理解することです。

LLMは、

**「もっともらしい文章を生成する」**

のであって、

**「必ず事実を返すデータベース」**

ではありません。

そのため企業システムではRAG、Tool、Structured Output、Evaluation、Human Reviewなどと組み合わせます。

---

# 8. Prompt Engineering

「プロンプトを工夫します」だけでは弱いです。

基本構造として、

**Role**
+
**Context**
+
**Task**
+
**Constraints**
+
**Input**
+
**Output Format**
+
**Examples**

くらいを覚えておけば十分です。

重要なのは、プロンプト改善を感覚でやらないことです。

Prompt AとPrompt Bを、

**同じEvaluation Dataset**

に対して実行して比較します。

つまり、

> Prompt EngineeringもEvaluation Drivenで行う

という考え方です。

---

# 9. RAG

**Retrieval-Augmented Generation**

です。

LLMが回答する前に外部情報を検索し、その情報をContextとして回答させます。

基本構成は、

**Document**
→ Chunking
→ Index / Embedding
→ Retrieval
→ Reranking
→ LLM
→ Answer / Citation

です。

用途としては、

**社内文書**
**製品マニュアル**
**FAQ**
**契約・規程**
**最新情報**

などがあります。

重要なのは、

> RAGを使えばHallucinationがゼロになるわけではない

こと。

検索自体が間違う可能性があります。

したがって、

**Retrieval Precision**
と
**Generation Quality**

を分けて評価します。

# 10. AI Agent

今回の求人ではかなり重要です。

Chatbotとの違いを説明できるようにします。

Chatbot：

**User → LLM → Answer**

Agent：

**User**
→ LLM
→ 判断
→ Tool/API
→ 結果取得
→ 再判断
→ Action

例えば、

> 「昨日問い合わせしてきた顧客を調べて、優先順位を付けて、返信案を作って」

という指示に対して、

AgentがCRM検索→顧客情報取得→問い合わせ確認→分類→回答生成

まで実行します。

構成要素として、

**Model / Instructions / Tools / State / Control Flow / Guardrails**

を理解しておけば十分です。

---

# 11. Human-in-the-loop

AI Agentを企業導入するときの重要概念です。

AIに全部やらせるのではなく、

**AI**
→ 処理
→ **Human Approval**
→ 実行

という構造にします。

例えば、

「返信案を作る」
→ AI

「顧客へ送信する」
→ 人間承認

と分離します。

判断基準は、

**Risk × Confidence × Reversibility**

で考えると説明しやすいです。

「失敗時の影響が大きく、取り消せない操作ほど人間承認を入れる」という考え方です。

# 12. Evaluation

この案件でかなり重要です。

従来型システムなら、

> Expected = 100  
> Actual = 100

のようなテストができます。

LLMではそれだけでは評価できません。

そこで、

**Evaluation Dataset**

を作ります。

例えば100〜200件の、

**Input**
+
**Expected Result / Rubric**

を準備。

そこに、

Model A
Prompt A
RAG A

を実行します。

そして、

**Accuracy**
**Relevance**
**Groundedness**
**Citation correctness**
**Latency**
**Cost**

などを比較します。

つまり、

> 「なんとなく良くなった」ではなく、数字でAI品質を判断する

ということです。

# 13. AI PoC

PoCは「とりあえずChatGPTを触る」ではありません。

基本フローを覚えてください。

**Business Problem**

↓

**Use Case**

↓

**Baseline**

↓

**Evaluation Dataset**

↓

**Prototype**

↓

**Evaluation**

↓

**ROI**

↓

**Go / No-Go**

です。

例えば問い合わせ対応なら、

現在15分/件

↓

AI導入3分/件

↓

回答品質95%

↓

人間確認率30%

↓

1件あたりAIコスト10円

などを測定します。

**技術的に動いたかではなく、業務価値があるかを検証する**のがPoCです。

# 14. AIリスク・セキュリティ

最低限、以下は説明できるようにします。

**Hallucination**
根拠のない回答。

**Prompt Injection**
入力や外部コンテンツによってAIの指示・Tool利用などを不正誘導する攻撃。

**Data Leakage**
機密情報・個人情報の漏洩。

**Excessive Agency**
Agentに必要以上の権限を与える問題。

**Access Control**
RAGでも元データのアクセス権を維持する。

対策の基本は、

**Least Privilege**
+
**Human Approval**
+
**Tool Allowlist**
+
**Data Classification**
+
**Audit Log**
+
**Evaluation / Monitoring**

です。

「LLMだから特別」というより、従来のセキュリティ原則にAI固有リスクを追加すると考えると理解しやすいです。

# 15. プロジェクト推進・トラブル対応

最後はPjM本来の能力です。

面談で、

> 「開発が2週間遅れています。どうしますか？」

と聞かれたとします。

「頑張って取り戻します」はNGです。

基本フレームは、

**① Fact**
何が遅れているか

↓

**② Root Cause**
なぜ遅れたか

↓

**③ Impact**
何に影響するか

↓

**④ Options**
Scope / Resource / Schedule / Qualityの選択肢

↓

**⑤ Decision**
Stakeholderと決定

↓

**⑥ Re-plan**
計画更新

↓

**⑦ Monitoring**
再発防止・監視

です。

例えば、

> 「まずCritical Pathへの影響を確認します。そのうえで、Must要件を守ってCould要件を後続Releaseへ回す案、リソース追加案、納期変更案をImpactとともに提示し、顧客と意思決定します。」

まで言えるとPjMらしくなります。
