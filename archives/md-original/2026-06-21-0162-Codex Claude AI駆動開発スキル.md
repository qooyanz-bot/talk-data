# AIにコードを書かせる前に知っておきたい、AI駆動開発の基礎スキル

AIに「この機能を作って」と頼めば、複数ファイルにまたがる実装、テスト、Pull Requestの作成まで進めてくれる時代になりました。CodexやClaude Codeは、単なる補完ツールではなく、コードを読み、編集し、コマンドを実行して検証する開発エージェントです。 citeturn266054view2turn266054view6

ただし、AIに任せる範囲が広がるほど、開発者に必要なのは「速くコードを書く技術」だけではなくなります。重要になるのは、**何を作るかを明確にし、AIの仕事を検証し、チームの品質基準に接続する力**です。

この記事では、CodexやClaude Codeを使ってAI駆動開発を始める前に身につけておきたい基礎スキルを、実践的な順番で整理します。

---

## AI駆動開発は「AIに丸投げすること」ではない

AI駆動開発では、人間が実装のすべてを手で書く場面は減っていきます。一方で、人間が担う役割はより上流と下流に移ります。

- 目的と制約を定義する
- 既存システムとの整合性を判断する
- 実装方針をレビューする
- テストと検証の基準を決める
- セキュリティや運用上のリスクを判断する

つまり、AI駆動開発で価値が高まるのは「実装速度」だけではなく、**良い仕事を定義し、良い成果物かを見極める力**です。

Codexの公式ガイドでも、成果を安定させる要素として、タスクの文脈、明確なプロンプト、再利用可能な指示、検証手順が挙げられています。 citeturn955797view0turn955797view1

---

## スキル1：要望を「実装可能な仕様」に変換する力

AIに対する依頼は、雑談ではなくIssueや設計メモに近い形で渡すと精度が上がります。

たとえば、次の依頼では情報が足りません。

> ログイン画面を改善して

これでは、AIは「改善」の意味を推測するしかありません。

代わりに、目的・対象・制約・完了条件を分けて渡します。

```text
目的:
ログイン失敗時に、ユーザーが原因を理解できるようにする。

対象:
src/features/auth/LoginForm.tsx

変更内容:
- メールアドレス未入力時のメッセージを追加
- パスワード未入力時のメッセージを追加
- 認証失敗時は、アカウントの存在有無を推測できない文言にする

制約:
- 既存のフォームライブラリを使う
- 文言は日本語
- デザイン変更は最小限
- API仕様は変更しない

完了条件:
- 既存テストが通る
- バリデーションのユニットテストを追加する
- 手動確認手順を最後に報告する
```

Codexの公式ドキュメントでも、プロンプトには「Goal（目的）」「Context（文脈）」「Constraints（制約）」「Done when（完了条件）」を含めることが推奨されています。 citeturn955797view0

AIを使いこなす人は、長いプロンプトを書く人ではありません。**曖昧さを減らし、判断基準を渡せる人**です。

---

## スキル2：既存コードを読む力

AIがコードベースを読めるようになっても、開発者がコードを理解しなくてよいわけではありません。

むしろ、AIが作った変更が正しいか判断するために、次の観点が必要になります。

- この処理はどこから呼ばれるのか
- データはどこで生成・更新・保存されるのか
- 似た実装はすでに存在するか
- 変更によって壊れる画面やAPIはないか
- このプロジェクト固有の設計ルールは何か

CodexやClaude Codeは、未知のコードベースを探索し、データフローや関連モジュールを整理する用途でも使えます。まずは「書かせる」よりも、「説明させる」ことから始めるのがおすすめです。 citeturn266054view1turn266054view4

最初に使いやすい依頼例です。

```text
このリポジトリの認証処理について説明してください。

- エントリーポイント
- ログイン後のセッション管理
- 権限チェックの場所
- 関連するテスト
- 変更時に影響しそうな箇所

を、ファイルパス付きで整理してください。
まだコードは変更しないでください。
```

この段階で得たいのは、答えそのものではありません。AIの説明を材料に、自分で設計と影響範囲を確認できる状態です。

## スキル3：いきなり実装させず、まず計画を作らせる力

複雑な変更では、最初から「実装して」と頼むよりも、計画を出させてからレビューするほうが安全です。

Codexには計画を先に作るためのPlan modeがあり、Claude Codeにも変更前に計画を確認するワークフローがあります。どちらも、実装前に認識違いを減らすための考え方です。 citeturn955797view0turn266054view4

たとえば、次のように依頼します。

```text
次の要件を実装する前に、変更計画を作成してください。

- 変更対象のファイル
- 各ファイルで行う変更
- 既存実装との整合性
- 想定されるリスク
- 追加・更新すべきテスト
- 実装を小さく分ける場合の順番

この段階ではコードを変更しないでください。
```

計画を見て、「そのファイルを変更するのはなぜか」「既存の実装パターンと合っているか」「仕様の抜け漏れはないか」を確認します。

AI駆動開発では、コードレビューだけでなく、**計画レビュー**が重要になります。

---

## スキル4：プロジェクトの知識をファイルに残す力

毎回チャットで同じことを説明していると、AIの品質は安定しません。

たとえば、次のような情報です。

- 起動・テスト・Lintのコマンド
- ディレクトリ構成
- 命名規則
- 設計上の禁止事項
- PR作成時のルール
- セキュリティ上の注意点
- 「完了」と見なす条件

Codexでは`AGENTS.md`、Claude Codeでは`CLAUDE.md`が、こうした持続的な指示を置く代表的な場所になります。Codexのガイドは`AGENTS.md`にリポジトリ構成、ビルド・テスト手順、規約、禁止事項、検証方法を記載することを勧めています。Claude Codeでも、`CLAUDE.md`にビルド手順、設計判断、命名規則、共通ワークフローなどを置けます。 citeturn955797view0turn955797view5

最初は、次のような最小構成で十分です。

```md
# 開発ルール

## 基本コマンド
- 開発起動: `npm run dev`
- テスト: `npm test`
- Lint: `npm run lint`
- 型チェック: `npm run typecheck`

## 実装ルール
- 新規APIは `src/api/` に追加する
- DBアクセスは直接書かず、Repository層を経由する
- UI文言はハードコードせず、翻訳ファイルを使う
- 既存の設計パターンを優先する

## 禁止事項
- `.env` を変更しない
- マイグレーションを勝手に実行しない
- 依存パッケージを追加する前に理由を報告する

## 完了条件
- テスト、Lint、型チェックを実行する
- 変更内容と確認結果を最後に要約する
- 未確認事項や残るリスクを明記する
```

大切なのは、立派なドキュメントを最初から作ることではありません。AIが同じミスを二度したときに、その学びをルールへ変換していくことです。Codex、Claude Codeの公式ドキュメントも、指示は短く具体的に保ち、実際に起きた摩擦をもとに改善する考え方を示しています。 citeturn955797view1turn955797view5

## スキル5：大きな仕事を「レビュー可能な単位」に分ける力

AIは大規模なタスクも扱えます。しかし、人間が安全に確認できる単位に分解するほど、失敗の影響を小さくできます。

おすすめは、次の順番です。

1. 現状を調査する  
2. 設計案を作る  
3. 変更対象を絞る  
4. 最小実装を作る  
5. テストを追加する  
6. 差分をレビューする  
7. Pull Requestとして説明できる形に整える  

たとえば「決済機能を追加する」という大きな仕事を、そのまま渡す必要はありません。

```text
Phase 1:
既存の注文確定フローと、外部サービス呼び出しの設計を調査してください。
コードは変更しないでください。

Phase 2:
決済状態を保存するためのデータモデル案を提示してください。
既存のマイグレーション方針に従ってください。

Phase 3:
決済開始APIだけを実装してください。
Webhook処理や画面改修はまだ対象外です。
```

一度に変更する範囲が狭いほど、レビューは速くなり、ロールバックもしやすくなります。

AIを速く動かすほど、人間は**止めやすい設計**を意識する必要があります。

---

## スキル6：テストを「AIへの依頼」ではなく「品質の契約」にする力

「テストも追加して」と言うだけでは不十分です。

重要なのは、何を守りたいのかを明示することです。

```text
以下の観点でテストを追加してください。

- 正常なメールアドレスとパスワードでログインできる
- パスワードが不正な場合、アカウントの存在を推測できない
- レート制限時は適切なエラーを返す
- 例外発生時に認証トークンが発行されない
- 既存のセッション更新処理に影響しない
```

Claude Codeの公式ワークフローでも、未テスト部分の特定、テストの土台作成、境界値やエラー条件の追加、テスト実行と失敗修正という順番が紹介されています。 citeturn955797view4

AIはテストコードを生成できます。しかし、どの失敗を防ぐべきかは、ドメイン知識を持つ人間が決める必要があります。

テストは「AIが書いたコードを確認する作業」ではなく、**チームが守りたい振る舞いを言語化する作業**です。

---

## スキル7：差分をレビューし、権限を管理する力

AIが生成したコードは、見た目が自然でも、要件に合っているとは限りません。

レビュー時は、少なくとも次を確認します。

- 要件にない変更が入っていないか
- エラー処理が不足していないか
- 認可・入力検証・機密情報の扱いに問題がないか
- 依存関係が不用意に増えていないか
- テストが「通るだけ」になっていないか
- ログや監視に必要な情報が残るか
- 既存の振る舞いを壊していないか

特に、AIエージェントにコマンド実行、外部アクセス、Pull Request作成などを許可する場合は、権限を必要最小限に保つべきです。Anthropicの公式ドキュメントでも、AIによるコンピュータ操作にはプロンプトインジェクションなどのリスクがあり、信頼できる環境、最小権限、重要操作の人間による監督が推奨されています。 citeturn266054view5

便利だからこそ、次の線引きを最初に決めておくと安心です。

```text
AIに任せてよいこと
- 調査
- 影響範囲の整理
- テスト追加
- 小規模なリファクタリング
- 下書きのPull Request作成

人間が必ず判断すること
- 本番環境への変更
- 権限・認証・課金に関する設計
- 機密情報の取り扱い
- データ削除や大規模マイグレーション
- 外部サービスへの重要な操作
```

## 最初の1週間で試したい実践メニュー

いきなり大きな機能開発を任せる必要はありません。

まずは、失敗しても影響が小さい仕事から始めるのがおすすめです。

### 1日目：コードベースを説明させる

```text
このプロジェクトの構成、主要な機能、起動方法、テスト方法を説明してください。
不明な点は推測せず、不明と明記してください。
```

### 2日目：小さなバグを調査させる

```text
このエラーの原因候補を調査してください。
修正はまだ行わず、関連ファイルと再現手順を整理してください。
```

### 3日目：テストを書かせる

```text
この関数の現在の振る舞いを確認し、境界値と異常系を含むテストケース案を作成してください。
```

### 4日目：小さな修正を任せる

```text
このバグを修正してください。
変更範囲は最小限にし、テストを追加してください。
変更後は、実行したコマンドと結果を報告してください。
```

### 5日目：`AGENTS.md`または`CLAUDE.md`を整える

繰り返し説明した内容、レビューで指摘した内容、AIが迷った内容を記録します。

### 6日目：Pull Requestのレビュー補助に使う

```text
この差分をレビューしてください。
以下の観点で確認してください。

- 要件との不一致
- 例外処理
- セキュリティ
- テスト不足
- 将来的な保守性
```

### 7日目：振り返りをする

「AIが助けになった場面」と「人間の確認が必要だった場面」を分けて記録します。

ここで得た学びが、次の指示ファイルやチームルールの材料になります。

## まとめ：AI駆動開発で最初に鍛えるべきもの

CodexやClaude Codeを使い始めると、コードを書く速度は確実に変わります。

しかし、AI駆動開発の本質は「実装を速くすること」だけではありません。

重要なのは、次の7つです。

1. 要望を実装可能な仕様に変換する  
2. 既存コードと設計を読み解く  
3. 実装前に計画をレビューする  
4. プロジェクトの知識を指示ファイルに残す  
5. 仕事を小さく、レビュー可能な単位に分ける  
6. テストを品質の契約として設計する  
7. 差分と権限を人間が責任を持って管理する  

AIは優秀な実装者になりつつあります。

だからこそ、開発者に求められるのは「AIへ正しく仕事を渡し、成果を見極め、よりよい開発環境を作る力」です。

まずは、AIにコードを書かせる前に、AIが迷わず働けるプロジェクトと依頼の形を整えるところから始めてみてください。
