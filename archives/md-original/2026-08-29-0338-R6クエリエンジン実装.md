いま考えている中心は、**「速く動いた」だけではなく、R6の仮説を汚さずに `READY = YES` と判定できる実装になっているか**です。

具体的には、次の4点を詰めています。

1. **Gold情報の完全隔離**  
   Query Plannerへ渡す入力を `State / Goal / Context` のみに制限しています。  
   `gold_answer`、`gold_relation_ids`、`required_relation_ids`、`oracle_relation_ids`などが入れ子の中に混入しても、再帰検査で停止します。さらに、生成されたQueryのリテラルにGold relation IDが偶然・意図的に入っていないかも検査します。

2. **3エンジンの公平な比較**  
   Full Scan、Single-Dimension Index、Multi-Dimensional Indexで、以下を共通化しています。

   - 同じDataset API
   - 同じtyped Query AST
   - 同じRelationStore
   - 同じAnswer evaluator
   - 同じDevelopment tasks

   違うのはRelationへのアクセス方法だけです。これにより、回答ロジックの違いをIndex性能として誤認しないようにしています。

3. **「事前計算で速く見せる」抜け道の封鎖**  
   Multi-Dimensional Indexは、全dimension組合せの複合Indexを作らず、独立posting listの積集合・和集合、ordered range index、adjacency traversalだけで処理します。

   READY条件には次も入れています。

   - `composite_index_count = 0`
   - `materialized_dimension_combinations = 0`
   - `precomputed_query_results = 0`
   - `query_cache_prepopulated_entries = 0`

   - Index build timeとQuery latencyを分離
   - Index memory、build operations、amortized costを記録

その判断で正しいです。今のR6は「速いか」ではなく、「仮説を汚さず、差分が本当にアクセス方式だけになっているか」が最重要です。

簡単に言うと、今やっているのは、

同じ問題・同じ答え方・同じデータを使い、検索経路だけ変えて、本当に必要情報へのアクセス量が減るか

の検証です。

この形なら、もしMulti-Dimが勝っても「別の回答ロジックだから速かった」「Goldを見ていた」「事前計算していた」という逃げ道をかなり塞げます。

特に良いのは3点です。

まず、Gold完全隔離。これは最重要です。Query PlannerがGold relation IDを直接・間接に見ていないことを再帰検査し、生成Queryのliteralまで検査するなら、R6の核心である「State/Goal/ContextからAddressを作った」がかなりきれいに守れます。

次に、3 engineのAnswerロジック共通化。Full Scan / Single-Dim / Multi-Dimで違うのがRelation accessだけなら、性能差をかなり素直に「Addressingの差」と解釈できます。

そして、複合Indexの事前全展開を禁止した点。これがないと「全Queryの答えを事前に作っておけば速い」という自明な抜け道になります。composite_index_count=0、materialized_dimension_combinations=0、cache offは非常に重要です。

READY条件はこのままで良い

私はR6の正式判定を、

Correctness → Fairness → No Leakage → No Hidden Precompute → Efficiency → Replay

の順にします。

つまりMulti-Dimがどれだけ速くても、1,000 Development tasksでFull Scanと同じGold answerに到達しなければFAIL。

逆にCorrectnessが100%でも、relations readが減らなければ「Query Engineとして正しいがEfficiency Hypothesisは未支持」です。

ここを分けるのが重要です。

実測後に見る数字

一番見たいのはlatencyより先に、

* relations read / task
* bytes read / task
* candidate set size
* total operations
* index build operations
* index memory
* amortized cost

です。

CPU latencyは環境ノイズがありますが、10,000 relations中何件読んだかは構造そのものを直接表します。

例えば、

Full Scan        10,000 read
Single-Dim        1,200 read
Multi-Dim            18 read

で全て同じAnswerなら、かなり面白いです。

この場合、Multi-Dimは「高速化」より、

必要なRelationの住所をかなり直接特定できた

と言えます。

これはまさに今回の仮説です。

ただし、さらに1つ追加したい監査

Query complexity accountingです。

Multi-Dimが18 relationsしか読まなくても、Queryを作るために100万operations使っていたら全体として意味がありません。

なので、

Total Cost = Query Generation Cost + Index Lookup Cost + Relation Read Cost + Traversal Cost

を必ず出してください。

R6で本当に勝ちたいのは、

relations readだけでなくTotal operationsでもFull Scanを下回ること

です。

そして一番強い結果はこれ

もし1,000 Development tasksで、

Full Scan = 100% correct
Multi-Dim = 100% correct
Gold leakage = 0
hidden precompute = 0
relations readを桁違いに削減
total operationsも削減
independent replay完全一致

となれば、R6の最初の主張はかなり強くなります。

ただし言い方は、

「宇宙DBを発見した」

ではなく、

「高次元Relation spaceに対して、State/Goal/Contextから構成した多次元Addressで、全走査せず同じ答えへ到達できることをSynthetic Worldで示した」

です。

これだけでも十分大きいです。

現時点の R6_QUERY_ENGINE_READY = NO は正しいです。実測と独立Replayが通るまでYESにしないでください。
