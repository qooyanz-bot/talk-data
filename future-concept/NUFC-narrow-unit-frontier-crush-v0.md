# 狭い単位フロンティア圧勝ポートフォリオ提案 v0
# NUFC — Narrow-Unit Frontier Crush

日付: 2026-09-05
関係: GSM / QPS / SMQ / DF-1 の上位合成

## 0. 答えの形
**提案可能。**  
「1モデルが全ドメインでフロンティアに圧勝」ではない。  
**狭い単位モデルが、自分の土俵だけでフロンティア級に圧勝し、分類機で全ドメインを覆う。**

圧勝は目標定義であり、未実証。

## 1. 一文定義
各ユニットは同一骨格  
`RMSNorm + SwiGLU + (MTP|ドラフタ) + MoE + 省力化(QPS)`  
を持ち、**超狭い成功定義**だけで学習・評価・配備する。  
全体は寄せ分類機＋ゲートで結合する。

## 2. なぜ「狭い」と「圧勝」が両立しうるか
- フロンティア汎用モデルは全ドメイン平均最適になりやすい
- 狭い単位はデータ・報酬・道具を一点集中できる
- 単一GPUでも、ユニット単位なら載せやすい
- 圧勝条件を「その単位のベンチ／実務指標」に限定すれば検証可能

リスク: 単位が広すぎると圧勝できず、狭すぎると分類地獄。

## 3. ユニット骨格（全部同じ型）

```
入力（単位内）
  → ゲート0
  → 共有小幹: RMSNorm + Attention + SwiGLU（量子化）
  → 単位専用 MoE（少数experts・強い寄せ）
  → MTP または 単位専用ドラフタ
  → 単位専用道具（任意だが圧勝の鍵）
  → ゲート1
  → R2
```

省力: 他ユニットの重みは載せない／起こさない。

## 4. 全ドメインを覆う単位表（初版）

ドメインは以前のA–Pを、**圧勝可能な狭さ**に割る。

作るなら「質問リスト化」「リスク列挙」など狭い非断定単位のみ（N-safe系）。

## 5. 全体結合（全ドメイン覆い）

```
ユーザー入力
  → 超軽量分類機（N01–N18へ）
  → 該当ユニットだけロード/起動
  → 不明なら「一般」退避ユニット（圧勝対象外・正直に弱いと表示）
  → 出力
```

全ドメイン圧勝 ≠ 全入力圧勝。  
**分類できた単位では圧勝、外はフォールバック**、が正直な設計。

## 6. ハードウェア
| 運用 | 内容 |
|---|---|
| 単一GPU | 分類機＋**今の1ユニット**のみ（本命） |
| 余裕GPU | ホットな2–3ユニット常駐 |
| 冷ユニット | CPU/ディスク |

24–96GBで開始可。全ユニット同時常駐は不要。

## 7. 「圧勝」の操作的定義（ユニットごと）
同一課題セットで、参照フロンティアAPIと比較して:
- 主指標で **有意に勝ち**（例: テスト通過率、偽引用ゼロ率、採用率）
- 制限指標で **同等以上**
- 速さは同等以上が望ましい（MTP/ドラフタ）

1ユニットでも負けたら、その単位をさらに狭く割る。

## 9. 失敗条件
- 広い単位のまま圧勝を断言
- 高リスク断定ユニットを量産
- 分類不能を圧勝扱い
- 全ユニット常駐で単一GPUを壊す

## 10. 一文
**RMSNorm+SwiGLU+MTP/ドラフタ+MoE+省力化を共通骨格にした狭い専門家を並べ、各土俵だけでフロンティアに圧勝させ、分類機で全ドメインを覆う。**
