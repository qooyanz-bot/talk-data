# ある程度寄せたMoE × QPS（量子化・省力）× GSM

日付: 2026-09-05 / 作業仮説（未実証）
関連: GSM-v0, QPS提案, RunPod机上テスト

## 1. 目標の言い直し（過大宣言を避ける）

| ラベル | 意味 | 単一GPU |
|---|---|---|
| F★ | 閉源ChatGPTそのもの | **狙わない**（単一では非現実） |
| **F1-S** | 単一GPUで、主要ドメインの束がオープン準フロンティア級 | **本提案の目標** |
| F0-GSM | 最小単位のみ実用 | 既に可能 |

成功定義: U1–U4（＋必要ならU5/U6）で、参照フロンティアAPIとの要点一致が目標帯、かつ制限テストを落とさない。速度は「対話実用」。

## 2. 提案アーキテクチャ名
**SMQ** — *Steered MoE + QPS*（寄せMoE＋量子化省力）

```
入力
  → 極小分類機（寄せ先ドメイン d を決める）
  → Steered-MoE 核（共有幹＋ドメインexperts）
       ・活性は top-k のみ（省力）
       ・experts はドメイン寄せ済み（ある程度Steer）
  → QPS
       ・Q1 静的: experts/幹を INT4〜FP8
       ・Q2 動的: 難問だけ高精度パス
       ・Q3: 未使用expertsはVRAM外（CPU DRAM）可
  → RAG/ツール（任意）
  → L3ゲート
  → R2
```

## 3. 「ある程度寄せたMoE」の中身

通常MoE: トークンごとに専門家を選ぶ（タスク意味が弱いことが多い）。
**寄せMoE**: 専門家を **GSMドメイン（U1–U6）に対応づけ**、分類機が先にドメインを寄せる。

- **共有幹（shared）**: 言語の共通能力（薄く量子化）
- **E_U1 … E_U6**: 各ドメインに寄せたexperts（LoRAでも稠密でも可）
- **ゲートexperts**: 安全・拒否寄りの経路（U危険域）

ルーティング規則（仮説）:
1. 分類機がドメイン \(d\) を出す（ハード寄せ）
2. MoEは \(d\) のexpertsを優先（ソフトに近傍ドメインも可）
3. 常時起こすのは共有幹＋少数expertsのみ → **単一GPUの省力**

これで「巨大一枚岩を1枚に載せる」のではなく、**載せている総知識のうち今使う切片だけ起こす**。

## 4. QPSの当て方（単一GPU用）

| 部品 | 推奨（机上） | 理由 |
|---|---|---|
| 分類機 | 1B前後 or 規則+小LM | ほぼ誤差・超軽い |
| 共有幹 | 3B–14B級相当の活性 / INT4〜FP8 | 常時オン |
| ドメインexperts | LoRA or 小FFN experts INT4 | VRAM主犯を削る |
| 難問パス Q2 | 一時的にビット上げ or 大きめexpert | 「ある程度」以上が必要なときだけ |
| KV | 文脈短め既定、長さはドメイン別 | 単一GPUの同時数・安定 |

## 6. なぜ複数枚フル405Bより単一SMQがありうるか
- ChatGPT級の体感は「全パラメータ常時活性」ではなく、**適切に寄せた応答＋道具＋検証**でも出ることがある
- 単一GPUの勝ち筋は総容量競争ではなく **活性FLOPsとVRAMの局部最適**
- 失敗するとただの弱い小モデル束になる → テストセット必須

## 7. 最小実験（検証手順）
1. 分類機＋共有14B INT4（1GPU）
2. U1/U2だけLoRA experts追加
3. 60問のうちU1/U2だけ測定（寄せ・制限）
4. 参照APIと要点一致
5. 足りなければ Q2（難問だけ厚く）を足す
6. U3/U4へ拡張

停止条件: 3サイクル改善停止、または$/品質がAPIより悪い。

## 8. 失敗条件
- 単一GPUでF★断言
- 分類ミスで危険域の薄いexpertへ
- 量子化で制限テストが崩れる
- expertsを全部いつもVRAMに載せて省力崩壊

## 9. 一文の提案
**ある程度寄せたMoE（ドメイン優先ルーティング）とQPS（必要精度だけの量子化・動的パス）を組み合わせれば、単一の96GB級GPU上で、全タスクのChatGPT置換ではなく、GSMドメイン束における準フロンティア級（F1-S）を狙える。**
