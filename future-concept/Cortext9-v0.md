# Cortext9 v0
# 分散NUFC配備アーキテクチャ

- 版: v0
- 日付: 2026-09-05 (JST)
- 状態: **K指示により正本保存**（名称固定: Cortext9）
- 位置づけ: NUFC（狭い単位フロンティア圧勝）の **配備・分散・増減** 形
- 関連: GSM, QPS, SMQ, DF-1, CSR-1, NUFC

## 1. 一文定義
**Cortext9** は、小さい受付・回答モデルが質問を受け、内部APIで外部の担当機能モデルに処理を任せ、結果をまとめて返す分散アーキテクチャである。担当機能モデルは別CPU/GPUに配置でき、需要に応じて台数を増減する。

## 2. なぜこの名前か
作業名称。皮質（cortex）的に「受付と機能野が分かれる」イメージと、世代・版の作業ラベル **9** を合わせたもの。学術標準用語ではない。

## 3. 構成

```
ユーザー
  → [Gate0] ポリシー / 秘密 / 危険の一次止め
  → [Reception] 小モデル（分類・言い換え・要約・オーケストレーション・最終文整形）
  → 内部API（認証付き）
  → [Function Units] 担当機能モデル × N
        ・各ユニットは NUFC 狭い単位（RMSNorm+SwiGLU+MoE+QPS+MTP/ドラフタ 等）
        ・別CPU / 別GPU に分散可
        ・需要でレプリカ増減
  → Reception が集約
  → [Gate1] 幻覚・B5・二次ゲート
  → R2
```

### 3.1 Reception（受付・回答モデル）
- **小さくてよい**（分類と顔が主仕事）
- やること: 意図分類、担当選択、引数組み立て、タイムアウト処理、口調の統一、ユーザー向け最終R2
- やらないこと: 全ドメインの重い推論を一人で抱える、Concept最終確定（B5）

### 3.2 Function Units（担当機能モデル）
- NUFCの狭い圧勝単位（例: 関数実装、根拠付き要約、changelog下書き…）
- ユニットごとに最適デバイス（CPU寄り / GPU寄り）を選んでよい
- ホットな単位は常駐、冷たい単位はスケールゼロ可

### 3.3 内部API
- スキーマ固定（request/response JSON など）
- 認証・認可・監査ログ
- 期限・再試行・サーキットブレーカ
- 失敗時フォールバック（退避ユニット or 正直な「担当なし」）

## 4. スケーリング規則（需要増減）
| 信号 | 行動 |
|---|---|
| キュー待ち時間↑ | 当該ユニットのレプリカ↑ |
| GPU利用率低＋要求少 | レプリカ↓ / スケールゼロ |
| エラー率↑ | トラフィック退避・ロールバック |
| 新ドメイン需要 | 新ユニット追加（NUFCの単位分割規則に従う） |

## 5. ハードウェア配置の型
| 層 | 配置例 |
|---|---|
| Reception | 小GPU or CPU |
| 軽ユニット | CPU / 小GPU |
| 重ユニット（コード等） | 単一中〜大GPU |
| 冷ユニット | ディスク＋起動時ロード |

全ユニットを1枚に常駐させない（Cortext9の省力の本体）。

## 6. ゲート（H1 / FC）
- Gate0/Gate1 を Reception 側に必須
- 危険担当はそもそも持たないか、非断定単位のみ（NUFCと同じ）
- 正本変更は §17（K承認）

## 7. 成功指標
- 分類精度（正解担当へ振る率）
- 単位ごとの圧勝指標（NUFC）
- 端到端レイテンシ
- $/要求
- 制限テスト（危険依頼）成功率
- スケールイベントの安定性

## 8. 失敗条件
- Receptionが巨大化して単一障害点かつ肥大モデル化
- 内部API無認証
- 分類ミスを隠して圧勝と偽る
- 全担当を常時フル起動してコスト爆発
- 担当間で口調・規範が破綻し Gate1 なし
