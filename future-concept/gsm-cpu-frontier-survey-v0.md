# GSM × 分類機 × 最小単位モデル — CPUフロンティア級可能性調査 v0

日付: 2026-09-05 / 仮説調査（未実証）

## 問い
ドメイン分類機 + 寄せ済み最小単位モデル群で、CPU中心に「フロンティア級相当」になり得るか。

## 結論（いま）
- **全面・全タスクでフロンティアをCPU単独超え**: 可能性は低い（観測上も主張しない）
- **狭いドメインの束で、体感・指標の一部がフロンティア級に近づく／勝つ**: **調査継続の価値あり（条件付きYes寄り）**
- 鍵は巨大一枚岩ではなく **分類→最小専門家→ゲート**（GSMそのもの）

## 技術的根拠（公開情報の要約）
1. **MoE**: 総パラ大きくても活性は小さい。フロンティアもMoE多用。ただし全expertsのメモリは重い。
2. **CPU/GPUハイブリッドMoE推論**: KTransformers等。CPU DRAMにexperts、GPUに高強度部。純CPUより現実的な「ローカル級」。
3. **LoRA専門家のルーティング**: HotMoE / LoRA-Mixer / Hard-Routed MoR-LoRA 等。小さく差し替え可能な専門家をルーターで選ぶ発想はGSMと相性が良い。
4. **小モデル+RAG+ツール**: 知識を重みに全部載せない。CPU向き。

※個別ベンチ数値は環境依存。ここでは原理の可否が主。

## アーキテクチャ案（調査用）
```
入力 → 軽量ドメイン分類機（超小モデル or 規則+小LM）
     → ドメイン別最小単位モデル（量子化SLM / LoRA）
     → 必要ならRAG・ツール
     → L3ゲート
     → R2
```

純CPUパス: 分類機 + 1〜少数の活性SLM（3B級前後量子化など）を想定。
ハイブリッドパス: 上記 + 必要時だけ较大expertsをCPU DRAMから。

## 採用する「ある程度寄せた」最小ドメイン（初版）
寄せやすく、検証しやすく、高リスク帯を最初に背負わないもの。

これらはゲート厚め・人間最終。最小単位は「質問リスト化・リスク列挙」までに留める。

## 「フロンティア級」の定義（この調査用・仮）
全面置換ではなく、次の **ドメイン限定SLO** で定義する。
- 品質: 当該Uのテストセットで、参照フロンティアAPIとの要点一致が目標帯
- 速度: 交互用途で実用レイテンシ（例: 数十tok/sは環境次第、目標は後で実測）
- 拘束: 危険セットの制限率がフロンティア方針と同等以上

全部のUで同時に勝つ必要は最初から要求しない。**ポートフォリオでカバー**する。

## 可能性マトリクス（仮説）

| シナリオ | CPU純 | CPU+小GPU | 見込み |
|---|---|---|---|
| U1〜U4の日常〜工学の一部 | 中 | 中高 | 寄せ+RAGで接近しうる |
| 長大エージェント・多モーダル最先端 | 低 | 中 | フロンティア本体が有利 |
| U5/U6（作法・運用） | 高 | 高 | モデルサイズよりゲート設計 |

## 次の実測ステップ（提案）
1. U2（コード）と U1（文書）で最小SLM候補を1つずつ固定
2. 超軽量分類機（規則→小モデル）を作る
3. 正当寄せ10+制限10のテストセット
4. 同一セットをフロンティアAPIと比較（品質のみ先、速度は後）
5. 結果を本ファイルに追記（版上げ）

## 失敗条件
- 「CPUでフロンティア全面超え」を実証前に断言
- 高リスクドメインを最初の成功定義に入れる
- 分類ミスで危険ドメインのゲートが薄い専門家に流す
